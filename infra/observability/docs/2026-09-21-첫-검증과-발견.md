# 로그 수집 첫 검증과 그 과정에서 찾은 것

**일자** 2026-09-21 · **대상** 로그 수집 계층(Loki·Alloy·Grafana) · **상태** 검증 완료, 후속 작업 제안

수집 계층을 올린 뒤 처음으로 Grafana에서 실제 로그를 조회했다. README의 검증 항목 넷을 돌렸고
셋은 통과했다. 어긋난 하나를 파고들다가 **로그와 무관한 응답 매핑 결함**을 찾았다.

이 문서는 검증 결과와 그 결함, 그리고 뒤집힌 가설들을 남긴다.

---

## 1. 요약

| | 결과 |
| --- | --- |
| 수집 자체 | 정상. `service` 라벨 8개가 전부 적재되어 있다 |
| 재배포 견디기 | **통과.** 이 작업의 목적이 실제로 달성됐다 |
| 서명 URL 가림 | **통과.** 30일 범위에 원본 서명값이 하나도 없다 |
| 아는 사건 재발견 | **실패.** 찾기는 했으나 **셀 수가 없다** |

마지막 항목을 추적하다가 다음을 찾았다.

> **AI가 409로 정확한 실패 원인을 알려주는데, 백엔드가 그것을 버리고 뭉뚱그린 메시지로 바꿔
> 사용자에게 내보낸다.**

로그 문제가 아니라 응답 매핑 문제다. 로그를 보지 않았으면 드러나지 않았을 것이다.

## 2. 검증 결과

### 2-1. `service` 라벨 8개 전부 존재

Explore의 Builder 모드에서 `service` 드롭다운을 열어 확인했다.

```
ai  backend  frontend  jenkins  mysql  nginx  redis  worker
```

문서에 적힌 8개와 일치한다. 없을 것으로 의심했던 `jenkins`와 `worker`도 있다.

**다만 `worker`는 7일 통틀어 4줄이고 전부 09-18 것이다.** 라벨은 살아 있으나 그 뒤로 유입이
없다.

이것을 "워커 가동 문제"로 읽으면 안 된다. `alloy-config.alloy` 4번 절에 적혀 있듯 워커 로그는
**사람이 파일을 서버에 놓아야 들어오는 구조**다.

```
/var/log/gshared-workers/worker-<식별자>-<YYYYMMDD>.log
```

워커가 정상 가동 중이어도 아무도 파일을 올리지 않으면 로그는 들어오지 않는다. 워커 생사는
Loki가 아니라 백엔드 쪽 접속 기록으로 확인해야 한다.

> **2026-09-24 정정** — 위 진단은 절반만 맞다. 더 근본적인 이유가 따로 있다.
> `system/worker/gshared_worker/logging_setup.py:73` 이 로그 레벨을 `WARNING` 으로 잡고,
> 바로 위 주석이 의도를 밝힌다.
>
> ```python
> log.setLevel(logging.WARNING)   # "a healthy run writes nothing."
> ```
>
> **정상 가동 중인 워커는 로그를 한 줄도 쓰지 않는다.** 진행 상황은 전부 DEBUG 라 기록되지
> 않는다. 설령 매일 파일을 올렸어도 거의 비어 있었을 것이다.
>
> 그래서 워커 로그 수집을 자동화하기 전에 **레벨을 INFO 로 내릴지부터 정해야 한다.** 지금
> 구조로는 옮겨 와도 볼 것이 없다. 그리고 `logging_setup.py:67` 이 `FileHandler` 라 상한이
> 없어, 레벨을 내리면 공급자 PC 에서 파일이 무한정 자란다. 회전 설정이 함께 필요하다.

```logql
{service="backend"} |= "worker"
```

### 2-2. 재배포를 견딘다 — 이 작업의 목적

| | 가장 오래된 줄 | 가장 최근 줄 |
| --- | --- | --- |
| `source="container"` | 2026-09-21 17:21 | 지금 |
| `source="file"` | 2026-09-14 23:29 | 지금 |

`container`는 오늘 17시 21분, 곧 마지막 재배포 시점에서 끊기고 그 이전이 없다. `file`은 7일
전까지 이어진다. **재배포 이전 기록이 남는다는 것이 실제로 확인됐다.**

타임스탬프도 함께 봤다. 파일 쪽 가장 오래된 줄이 다음과 같이 09-14 시각으로 정확히 찍혀 있다.

```
2026-09-14T14:29:28.092Z  WARN ... 필수 파라미터 누락: expires
```

전부 수집 시각으로 뭉치는 현상이 없다. `backend_timestamp` 단계가 정상 동작한다.

### 2-3. 서명 URL 가림

30일 범위로 확인했다.

| 질의 | 결과 |
| --- | --- |
| `{service="nginx"} \|= "sig="` | 12줄 |
| `{service="nginx"} \|= "sig=" != "sig=REDACTED"` | **0줄** |

원본 서명값이 남은 줄이 30일 안에 하나도 없다. 백엔드 쪽에도 `REDACTED` 18줄이 따로 있으니
nginx `log_format`과 Alloy `redact` 단계가 양쪽 다 걸려 있다.

## 3. 어긋난 항목 — `no_feasible_gpu`

README 4번은 "이미 아는 사건을 다시 찾는다"이고, 예시로 2026-09-18 오전 VRAM 부족으로 **주문
다섯 건**이 거절된 일을 든다.

```logql
{service="backend"} |= "no_feasible_gpu"
```

09-18 하루로 범위를 잡으면 **23줄**이 나온다. 09:57:38부터 10:01:44까지 4분간이고 전부 같은
형태다.

```
WARN [http-nio-8080-exec-N] c.g.back.global.client.SchedulerClient
  : [Scheduler] /scheduler/recommend 응답 409 CONFLICT body={"detail":[{"type":"no_feasible_gpu",...
```

**5건인지 23건인지 가릴 방법이 없다.** 로그에 식별자가 없다.

스레드 이름 `[http-nio-8080-exec-N]`으로 나누는 것은 안 된다. 톰캣 스레드는 요청이 끝나면
풀로 돌아가 재사용되므로 같은 이름이 같은 요청이라는 보장이 없다. 시각으로 묶는 것도 4분 안에
재시도 간격과 요청 간격이 뒤섞여 경계를 그을 수 없다.

### 왜 세는 것이 중요한가

같은 로그를 두고 정반대 결론이 나온다.

| 해석 | 실제 상황 | 필요한 조치 |
| --- | --- | --- |
| 5건 × 재시도 4~5회 | 특정 요청 몇 개가 까다로운 조건을 걸었다 | 개별 대응 |
| 23건이 각각 실패 | **공급자 풀이 구조적으로 부족하다** | GPU를 더 모아야 한다 |

하나는 "별일 아님"이고 하나는 "서비스가 성립하지 않음"이다.

## 4. 추적하다 찾은 것 — 409가 엉뚱한 메시지로 나간다

식별자를 어디에 넣을지 보려고 호출 경로를 따라가다 드러났다.

### 4-1. AI는 정확히 알려준다

`ai/app/api/scheduler.py:188`

```python
status_code=status.HTTP_409_CONFLICT,
    "type": "no_feasible_gpu",
```

주석에도 이렇게 적혀 있다.

> **409** -- 요청도 모델도 멀쩡한데 이 후보들 중에 Job을 돌릴 수 있는 GPU가 (없다)

### 4-2. 백엔드가 그것을 버린다

`back/.../global/client/SchedulerClient.java:68-75`

```java
} catch (RestClientResponseException e) {
    log.warn("[Scheduler] {} 응답 {} body={}", path, e.getStatusCode(), e.getResponseBodyAsString());
    if (e.getStatusCode().is4xxClientError()) {
        throw new BusinessException(SchedulerErrorCode.SCHEDULER_REJECTED);   // ← 409 가 여기로
    }
    throw new BusinessException(SchedulerErrorCode.SCHEDULER_UNAVAILABLE);
}
```

409는 4xx이므로 `SCHEDULER_REJECTED`로 뭉뚱그려진다. 본문의 `type: "no_feasible_gpu"`는
로그에만 남고 버려진다.

### 4-3. 그래서 사용자가 보는 메시지가 틀린다

`SchedulerErrorCode`

| 코드 | 메시지 |
| --- | --- |
| `SCHEDULER_REJECTED` | "Scheduler가 요청을 거절했습니다." |
| `NO_FEASIBLE_GPU` | "이 설정으로 실행 가능한 GPU가 없습니다." |

AI가 "GPU가 없다"고 알려줬는데 사용자는 **"Scheduler가 요청을 거절했습니다"**를 본다. 무엇을
바꿔야 할지 알 수 없는 문구다. 정작 딱 맞는 `NO_FEASIBLE_GPU`는 이 경로에서 쓰이지 않는다.

### 4-4. 같은 결과에 이르는 경로가 둘인데 하나는 로그가 없다

`NO_FEASIBLE_GPU`가 실제로 던져지는 곳은 따로 있다.

`JobEstimateService:154`, `JobService:157`

```java
// 2xx 지만 추천이 비어있는 경우
if (response.rankings() == null || response.rankings().isEmpty()) {
    throw new BusinessException(SchedulerErrorCode.NO_FEASIBLE_GPU);
}
```

정리하면 이렇다.

| | 조건 | 사용자가 보는 메시지 | 로그 |
| --- | --- | --- | --- |
| 경로 A | AI가 **409** + `no_feasible_gpu` | "Scheduler가 요청을 거절했습니다" ← **틀림** | `log.warn` 있음 |
| 경로 B | AI가 **2xx**인데 `rankings` 비어 있음 | "실행 가능한 GPU가 없습니다" | **없음** |

> **2026-09-24 정정** — 처음에 "경로 B는 로그를 한 줄도 남기지 않는다"고 적었으나 **사실과 다르다.**
> `GlobalExceptionHandler.java:26` 이 모든 `BusinessException` 을 `log.warn` 으로 받는다.
>
> ```java
> log.warn("비즈니스 예외: {} - {}", errorCode.name(), errorCode.getMessage());
> ```
>
> 다만 남는 것은 **에러 코드 이름과 고정 메시지뿐**이다. jobId 도, 견적인지 생성인지도, 어떤
> 요청이었는지도 없다. 찾을 수는 있지만 **셀 수도 추적할 수도 없다.** 과제의 성격은 "없는 로그를
> 만드는 것"이 아니라 **"맥락 없는 한 줄을 쓸 만한 줄로 바꾸는 것"** 이다.

## 5. 호출 경로가 둘이라는 점도 로그에 안 드러난다

`/scheduler/recommend`를 부르는 곳은 둘이다.

| 호출부 | 단계 | 실패의 의미 |
| --- | --- | --- |
| `JobEstimateService:149` | **견적** | 정상에 가깝다. 사용자가 조건을 탐색 중이다 |
| `JobService:152` | 작업 생성 | 진짜 실패다. 사용자가 확정했는데 못 했다 |

로그에는 둘 다 `/scheduler/recommend`로만 찍힌다. 구분이 불가능하다.

견적 실패와 생성 실패를 합산하면 실패율이 무의미해진다. 견적 20 + 생성 3이면 실제 실패는
3건인데 23건으로 보인다.

`orderId`로는 이 문제가 풀리지 않는다. **견적 단계에는 주문 자체가 존재하지 않기 때문이다.**

## 7. 해야 할 일

> **2026-09-29 진행 상태** — 브랜치 `be-fix/scheduler-409-mapping`
>
> | | 상태 | 어떻게 |
> | --- | --- | --- |
> | (1) 409 매핑 | **완료** | `SchedulerClient` 가 409 이면서 본문 `type` 이 `no_feasible_gpu` 일 때만 `NO_FEASIBLE_GPU`. `SchedulerClientTest` 가 실제 HTTP 로 409·422·503 을 받아 확인한다. 수정 전에는 409 테스트가 `expected NO_FEASIBLE_GPU but was SCHEDULER_REJECTED` 로 실패했다 |
> | (2) 경로 B 맥락 | **완료** | `GlobalExceptionHandler` 가 비즈니스 예외마다 `[메서드 URI]` 를 붙인다. 쿼리스트링은 뺀다(서명 값) |
> | (3) 견적과 생성 구분 | **완료, 방법 변경** | MDC·로그 패턴 대신 (2)의 URI 로 가른다. `/estimate`·`/gpu-options` 는 견적, `POST /api/jobs` 는 주문. 패턴을 건드리지 않아 `backend_timestamp` 정규식 영향이 없다 |
> | (4) 요청 식별자 | **안 함** | 이제 줄 하나가 실패한 요청 하나다. 다만 같은 사용자의 재시도를 한 건으로 묶지는 못한다 |
>
> 대시보드 「주문 거절」 칸은 `source` 를 가리지 않아 컨테이너·파일 두 경로의 같은 줄을 **두 번** 세고 있었다.
> `source="file"` 로 좁히고 견적과 주문을 따로 센다. 「오류 (24시간)」 칸도 같은 이중 집계가 남아 있다.

우선순위 순이다. 위 둘은 로깅과 무관한 결함이다.

### (1) 409를 `NO_FEASIBLE_GPU`로 매핑한다 — 버그

AI가 준 `detail.type`을 보고 갈라야 한다. 지금은 4xx를 통째로 `SCHEDULER_REJECTED`로 보낸다.

- 영향: 사용자가 원인을 알 수 없는 메시지를 본다
- 범위: `SchedulerClient.call()` 예외 처리
- 담당: `SchedulerClient` 전체를 작성한 autumn

### (2) 경로 B에 로그를 남긴다 — 관측 공백

`rankings`가 비어 `NO_FEASIBLE_GPU`를 던지는 두 곳은 `GlobalExceptionHandler` 가 받아
`log.warn` 한 줄을 남긴다. 그런데 그 줄에 **에러 코드 이름과 고정 메시지밖에 없다.**

```
비즈니스 예외: NO_FEASIBLE_GPU - 이 설정으로 실행 가능한 GPU가 없습니다.
```

jobId 도 없고 견적인지 생성인지도 없다. 23줄이 몇 건인지 셀 수 없는 이유가 이것이다.

- 범위: `JobEstimateService:154`, `JobService:157`, `GlobalExceptionHandler.java:26`

### (3) 견적과 생성을 로그에서 구분한다

MDC를 쓰면 `SchedulerClient`를 건드리지 않아도 된다. 진입점에서 한 번 넣으면 그 요청의 모든
로그에 붙는다.

```java
MDC.put("flow", "estimate");   // 또는 "create"
```

`logback.xml`을 새로 만들 필요는 없다. 이미 쓰고 있는 yml에 패턴만 더하면 된다.

```yaml
logging:
  pattern:
    file: "%d{yyyy-MM-dd'T'HH:mm:ss.SSSXXX} %-5level [%X{flow:-}] %logger{36} - %msg%n"
```

**단, 패턴을 바꾸면 Alloy의 `backend_timestamp` 정규식이 여전히 맞는지 확인해야 한다.** 시각이
줄 맨 앞에 오는 형태를 유지하면 문제없다.

### (4) 요청 식별자

시도 횟수를 세려면 요청 단위 식별자가 필요하다. `flow`와 같은 MDC 자리에 넣는다. 주문이 있는
경우에는 `orderId`도 함께 넣는다. (3)을 하면 자연히 따라오므로 별도 작업이 아니다.

## 8. 운영 관점에서 로그를 어떻게 둘 것인가

이번에 드러난 공백을 일반화하면 넷이다. 이 프로젝트에 필요한 만큼만 적는다.

### 원칙 1 — 실패하는 모든 경로가 로그를 남긴다

경로 B가 정확히 이것을 어겼다. 예외를 던지는 자리에 로그가 없으면 그 실패는 존재하지 않는
것과 같다.

기준은 단순하다. **`throw` 옆에 로그가 없으면 의심한다.**

### 원칙 2 — 셀 수 있어야 한다

식별자가 없으면 23줄이 몇 건인지 모른다. 로그는 읽는 것만이 목적이 아니라 **세는 것**도
목적이다. 세지 못하면 지표를 만들 수 없고, 지표가 없으면 대시보드가 틀린 숫자를 보여 준다.

**틀린 숫자는 없는 것보다 나쁘다.** 없으면 모른다는 것을 알지만, 틀린 숫자가 있으면 안다고
착각한다.

### 원칙 3 — 원인을 버리지 않는다

AI가 `type: "no_feasible_gpu"`로 원인을 특정해 줬는데 백엔드가 그것을 `SCHEDULER_REJECTED`로
뭉갰다. 외부 호출의 응답을 좁힐 때는 **원인 정보가 사라지지 않는지** 본다.

### 원칙 4 — 자격 증명과 개인정보를 남기지 않는다

이미 지켜지고 있다. nginx `log_format`과 Alloy `redact` 두 겹으로 서명 URL을 가린다. 새 수집원을
붙일 때 `redact` 단계를 반드시 거치게 한다는 규칙도 `alloy-config.alloy`에 적혀 있다.

### 레벨을 쓰는 기준

지금 `application-prod.yml`은 `root: warn`, `com.gshared.back: info`다. 이 설정은 적절하다.
다만 무엇을 어느 레벨로 남길지는 정해 두는 편이 낫다.

| 레벨 | 무엇을 | 예 |
| --- | --- | --- |
| `error` | 사람이 개입해야 하는 것 | 외부 연동 불능, 데이터 불일치 |
| `warn` | 처리는 됐으나 비정상 | 스케줄러 4xx·5xx, 재시도 |
| `info` | 사건의 흐름 | 작업 생성·완료, 상태 전이 |
| `debug` | 개발 중에만 | 운영에서는 꺼 둔다 |

**견적 실패를 `warn`으로 두는 것은 재고할 만하다.** 사용자가 조건을 탐색하는 정상 흐름인데
`warn`으로 쌓이면 경고가 소음이 된다. (3)의 `flow` 구분이 들어가면 레벨을 갈라 줄 수 있다.

## 9. 대시보드는 아직이다

패널로 고정할 기준을 셋으로 둔다.

```
[ ] 같은 질의를 세 번 이상 썼다
[ ] 그 질의가 실제로 데이터를 반환한다
[ ] 매일 또는 사건마다 볼 이유가 있다
```

지금 만들면 두 가지가 걸린다.

- `worker` 패널은 유입이 없어 빈 패널이 된다
- 실패 건수 패널은 견적과 생성이 섞인 **틀린 숫자**를 보여 준다

(1)~(3)을 처리한 뒤에 만들면 셀 수 있는 지표가 생긴다. 그때 만든 패널이 실제로 쓰인다.
