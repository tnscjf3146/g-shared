# 수집을 붙이면서 밟은 함정

2026-09-21 에 로그 수집 계층을 세우면서 실제로 겪은 것들이다. 설정 파일의 주석에도 각 자리에
적어 두었지만, 왜 그렇게 됐는지는 여기에 모은다.

**여덟 개 중 셋은 오류 없이 조용히 실패했다.** 지표도 로그도 정상이라고 말하는데 데이터만
없는 상태가 가장 오래 걸렸다.

---

## 1. 보존 기간보다 짧은 수용 나이가 배치 전체를 떨어뜨렸다

`reject_old_samples_max_age` 를 7일로, `retention_period` 를 30일로 두었다. 앞뒤가 맞지 않는다.

`loki.source.docker` 는 컨테이너 로그를 **처음부터** 읽는다. Redis 와 Jenkins 는 9월 3일부터
돌고 있어 18일치가 쌓여 있었고, 7일보다 오래된 줄이 배치를 400 으로 떨어뜨렸다.

**그 배치에 함께 실려 있던 최신 줄까지 같이 버려졌다.** 그래서 nginx 말고는 아무것도 들어오지
않았다. 한 줄 때문에 배치 전체를 잃는 구조다.

→ 수용 나이는 보존 기간과 같게 둔다.

## 2. `(?i)` 는 매칭만 무시할 뿐 캡처값은 원문이다

레벨을 `(?i)(?P<level>ERROR|WARN|INFO)` 로 뽑았더니 Spring 의 `INFO` 와 nginx 의 `info` 가
서로 다른 라벨이 됐다. 같은 서비스가 스트림으로 갈리고, `{level="error"}` 로 질의해도 `ERROR`
가 잡히지 않는다.

→ `stage.template` 으로 소문자로 맞추고 `WARNING` 은 `warn` 으로 통일한다.

## 3. nginx 접근 로그에 레벨을 뽑으면 본문의 단어를 레벨로 착각한다

스캐너가 `/roundcube/logs/errors.log` 를 요청한 줄이 `level=error` 로 분류됐다. **접근 로그에는
레벨이 없다.** 그런데 레벨 추출을 태우면 경로나 User-Agent 에 들어 있는 단어를 집는다.

→ 접근 로그와 오류 로그를 나누고, 접근 로그는 레벨 추출을 건너뛴다. 정규식도 "레벨처럼 생긴
자리"(줄 시작이나 공백 뒤, 뒤에는 콜론이나 공백)에서만 잡도록 좁힌다.

## 4. 스택 트레이스에는 시각이 없어 "지금"으로 밀린다

자바 예외 하나가 수십 줄로 퍼지는데, 이어지는 `\tat org.hibernate...` 줄에는 시각이 없다.
정규식이 실패하면 `stage.timestamp` 가 읽은 시각을 쓰므로 **그 줄들만 현재로 밀린다.**

→ `stage.multiline` 으로 시각으로 시작하지 않는 줄을 앞 항목에 붙인다. 예외 하나가 한 덩어리가
되어 시각도 레벨도 제대로 붙고, Grafana 에서도 흩어지지 않는다.

## 5. 압축본을 안 풀고 압축된 바이트를 그대로 보낸다 — 오류 없이

`back.log.*.gz` 를 경로에 넣었더니 Alloy 가 읽기는 했다. `tail routine: started` 까지 찍혀서
성공한 줄 알았는데, Loki 에 들어간 것은 이런 것이었다.

```
5?%l?6????]u-?P憘,9??h???m?E??$˥v7???|?B')W"?J?➨ǭ?Z]
```

**오류가 나지 않는다.** 읽기는 성공했으니 Alloy 는 할 일을 했다고 본다.

→ `loki.source.file` 에 `decompression` 블록을 켠다. 켜면 `component=decompressor` 가 로그에
찍히므로 그것으로 확인한다.

## 6. 같은 서비스인데 시각 표기가 두 가지다

2026-09-18 의 `[be-fix] 서버 시각 UTC→Asia/Seoul`(V20) 을 경계로 백엔드 로그 형식이 바뀌었다.

```
2026-09-18T00:21:56.265Z        ← V20 이전
2026-09-21T13:08:53.372+09:00   ← V20 이후
```

**오늘 로그만 보고 정규식을 만들면 과거를 놓친다.** 실제로 놓쳤고, 9월 18일 이전 줄이 전부
읽은 시각으로 밀렸다.

→ 정규식을 `(?:Z|[+-]\d{2}:\d{2})` 로 넓힌다. `RFC3339Nano` 는 두 표기를 다 파싱한다.

## 7. 파이썬의 쉼표 밀리초를 Go 레이아웃이 받지 않는다

워커는 파이썬 `logging` 기본 포맷이라 `09:45:12,101` 처럼 쉼표를 쓴다. Go 의 시각 레이아웃은
소수점 자리에 마침표만 받는다.

→ 밀리초를 버리고 초까지만 잡는다. 진짜 밀리초는 본문에 그대로 남아 있다.

그리고 워커 로그에는 시간대 표기가 없다. `location` 을 주지 않으면 UTC 로 읽혀 **아홉 시간이
밀린다.**

## 8. 항목이 적으면 조각이 안 내려가 조회에 나오지 않는다

**가장 오래 헤맸고, 운영에서도 만날 것이라 README 에도 적어 두었다.**

워커 로그 파일을 놓고 확인했더니 0건이었다. 원인을 찾겠다고 정규식, 시각 형식, `location`,
`multiline` 을 차례로 의심하며 여러 번 고쳐 봤지만 전부 아니었다.

지표는 전부 정상이라고 말했다.

```
Alloy 드롭      0
Loki 거절       0
오류 로그       없음
컴포넌트 상태   healthy
```

Alloy 를 거치지 않고 손으로 직접 밀어 넣어도 조회되지 않았다. **그때 Alloy 문제가 아니라는
것이 드러났다.**

힌트는 색인과 조각이 갈린 상태였다.

```
label/service/values  →  worker 가 있다      ← 접수는 됐다
series 조회           →  빈 배열              ← 조각은 없다
```

Loki 는 항목을 모아 **조각(chunk)** 으로 저장하고, 조각은 가득 차거나 `max_chunk_age`(기본
2시간)가 지나야 조회 가능한 곳으로 내려간다. 워커 항목 셋은 조각을 채우지 못했고, 시험할
때마다 몇십 초 뒤에 조회하고 `down -v` 로 지웠으니 내려갈 기회가 없었다.

백엔드 압축본은 한 파일에 수십 건씩 있어 바로 내려갔다. **그 차이가 "백엔드는 되는데 워커는
안 된다"로 보였다.**

→ 적은 양을 시험할 때는 `POST /flush` 로 강제로 내린다.

```bash
docker exec obs-grafana wget -qO- --post-data="" http://loki:3100/flush
```

## 되짚어 보면

여덟 개 중 **다섯 개가 시각에 얽혀 있다.** 로그 수집에서 가장 자주 어긋나는 것이 시각이라는
뜻이다. 형식이 서비스마다 다르고, 같은 서비스도 시간이 지나면 바뀌고(6번), 시간대 표기가
없기도 하고(7번), 이어지는 줄에는 아예 없다(4번).

그리고 **조용한 실패가 셋**이었다(1·5·8번). 오류를 내는 실패보다 훨씬 오래 걸린다. 수집기를
붙일 때 "돌아간다"를 로그 메시지로 판단하면 안 되고, **들어간 건수를 원본과 대조**해야 한다.
