# 로그 수집

배포 서버의 로그를 한곳에 모아 검색하는 계층이다. `infra/nginx/`, `infra/backup/` 과 마찬가지로
**서버 운영 구성**이며, 서비스 compose 와 별도 프로젝트로 돌아간다.

## 왜 필요한가

**재배포하면 로그가 사라진다.** `docker compose up -d --build` 는 컨테이너를 새로 만들기 때문에
이전 컨테이너의 로그 파일이 함께 지워진다.

2026-09-18 에 실제로 겪었다. 프론트엔드에서 `ECONNREFUSED` 가 반복되는 것을 확인하고 원인을
추적하던 중에 배포가 한 번 돌았고, **근거로 삼던 로그가 통째로 없어졌다.** 남은 것은 기동 배너
다섯 줄뿐이었다.

```
▲ Next.js 16.3.4
✓ Ready in 0ms
```

백엔드만 `logs/back.log` 로 파일 로그를 따로 남겨서 살아남는다. 프론트엔드, AI, MySQL, Redis 는
그렇지 않다.

두 번째 이유는 **흩어져 있다는 것**이다. 작업 하나가 브라우저에서 백엔드, AI, 워커, 컨테이너,
체인까지 여섯 구간을 지난다. 지금은 문제가 생기면 여섯 곳을 따로 열어 시각을 눈으로 맞춰야 한다.

## 구성

```
Alloy  ──모은다──▶  Loki  ──쌓는다──▶  Grafana  ──본다
```

| | 하는 일 | 포트 |
| --- | --- | --- |
| **Alloy** | 도커 소켓과 로그 파일을 읽어 Loki 로 보낸다 | 공개하지 않음 |
| **Loki** | 라벨을 붙여 저장한다. 보존 30일 | 공개하지 않음 |
| **Grafana** | 질의하고 보여 준다 | `127.0.0.1:3001` 만. 밖에서는 nginx `/grafana` 경유 |

수집기로 **Promtail 이 아니라 Alloy** 를 쓴다. Grafana 가 Promtail 을 유지보수 모드로 돌리고
Alloy 를 후계로 지정했으며 Promtail 은 수명이 끝났다. 튜토리얼과 블로그 글은 대부분 Promtail 로
쓰여 있으니 검색해서 나온 대로 따라가지 않는다.

## 라벨 정책 — 이 구성에서 가장 중요한 결정

**Loki 는 라벨만 색인한다.** 본문은 색인하지 않고 질의할 때 훑는다. 그리고 **라벨 조합 하나가
스트림 하나**다. 스트림이 폭발하면 Loki 가 느려지다 죽는다.

그래서 라벨은 값의 가짓수가 적고 유한한 것만 둔다.

| 라벨 | 값 | 왜 |
| --- | --- | --- |
| `service` | backend, frontend, ai, mysql, redis, jenkins, nginx, worker | 항상 첫 필터다 |
| `level` | error, warn, info, debug, trace | "오류만 보기"가 가장 흔한 질의다 |
| `source` | container, file | 서버와 워커를 가른다 |

**라벨로 두지 않는 것: `jobId`, `workerId`, `traceId`.** 값이 무한하거나 계속 늘어난다.

여기가 헷갈리는 지점이다. **검색하고 싶은 것과 라벨로 둘 것은 정반대일 수 있다.** `jobId` 로
찾고 싶지만 `jobId` 를 라벨로 두면 안 된다. 이렇게 쓴다.

```logql
{service="backend"} |= "jobId=10"
```

라벨로 스트림을 좁히고, 본문은 문자열 필터로 훑는다.

## 무엇을 모으는가

| 대상 | 방법 | `source` |
| --- | --- | --- |
| compose 컨테이너 5개 (backend, frontend, ai, mysql, redis) | 도커 소켓 | `container` |
| Jenkins | 도커 소켓 | `container` |
| nginx access·error | `/var/log/nginx/` 마운트 | `file` |
| **백엔드 `logs/back.log*`** | 마운트 | `file` |
| 워커 `gshared-debug.log` | 사람이 아래 규칙대로 놓으면 읽는다 | `file` |

### 백엔드 로그를 두 경로로 받는 이유

도커 로그와 파일 로그는 내용이 겹치지만 **중복이 아니다.**

| | 도커 로그 | `back.log` |
| --- | --- | --- |
| 범위 | 컨테이너 생성 이후만 | 50MB 씩 **14일** |
| 재배포하면 | **사라진다** | 남는다 |

겹치는 구간은 두 번 들어가지만 `source` 라벨로 갈린다.

```logql
{service="backend", source="container"}   지금 컨테이너 것만
{service="backend", source="file"}        재배포를 견딘 과거까지
```

> **첫 설계에서 이것을 "도커 로그와 같은 내용"이라며 빼 놓았다.** 이 작업을 시작한 이유가
> "재배포하면 로그가 사라진다"인데 정작 그 소실을 견디는 유일한 파일을 제외한 셈이었다.
> 2026-09-18 의 409 기록을 찾으려다 드러났다. 도커 쪽에는 없고 압축본에만 23건이 있었다.

### nginx 회전본은 왜 안 모으는가

백엔드와 같은 이유로 붙였다가 **뺐다.** 같은 이유가 통하지 않았기 때문이다.

백엔드 압축본이 제대로 들어간 것은 `backend_timestamp` 로 시각을 뽑아 주기 때문이다.
**nginx 블록에는 그 스테이지가 없다.** 실시간 tail 은 읽은 시각이 곧 기록된 시각이라
문제가 없지만, 회전본은 9월 7일 기록이 "지금"으로 들어간다. 날짜로 못 찾으면 모을 이유가
없다. 실제로 14일치 67,738건이 한 시각에 뭉쳐 들어갔다.

여기에 둘이 더 겹친다.

| | |
| --- | --- |
| **매일 전체 재적재** | 이 서버의 logrotate 는 `dateext` 없이 숫자를 민다(`2.gz`→`3.gz`). Alloy 는 경로로 위치를 기억하므로 회전할 때마다 같은 경로가 다른 내용이 된다. 시각까지 매번 달라지니 Loki 의 중복 제거도 안 걸린다 |
| **레벨 누락** | 회전본은 `add_level` 을 타지 않는다. 한 경로에 접근과 오류가 섞여 있어 지금 구조로는 나눌 수도 없다 |

과거 nginx 로그가 필요하면 **한 번만 밀어 넣는 백필**이라야 한다. 상시 수집으로는 위 셋이
전부 따라온다. 왜 그런지는 `docs/수집-함정.md` 의 10번, **어떻게 하는지는
`docs/과거-로그-백필.md`** 에 있다.

**이 스택이 뜬 뒤의 nginx 기록은 실시간 tail 만으로 빠짐없이 남는다.** 회전은 Alloy 가
알아서 따라간다.

**모으지 않는 것**

- **관제 스택 자신의 로그(`obs-*`).** Alloy 가 자기 로그를 보내고 그것을 다시 읽는 되먹임이
  생기면 소음이 계속 불어난다. `discovery.relabel` 에서 걸러 낸다.

### 워커 로그를 놓는 규칙

공급자 PC 의 `gshared-debug.log` 를 받아 서버의 아래 경로에 이 이름으로 놓는다.

```
/var/log/gshared-workers/worker-<식별자>-<YYYYMMDD>.log
```

자동 전송은 하지 않는다. 워커에 새 기능이 필요하고, 고객 데이터셋을 다루는 로그가 서버로
넘어오는 문제라 팀 합의가 먼저다. 지금은 사람이 옮긴다.

**오래된 파일은 조용히 버려질 수 있다.** Loki 가 `reject_old_samples_max_age`(7일)보다 오래된
줄을 거절한다. 그때는 `loki-config.yaml` 의 그 값을 잠시 늘렸다가 되돌린다.

## 실행

```bash
cp .env.example .env     # GRAFANA_ADMIN_PASSWORD 를 채운다
docker compose -p observability up -d
```

**서비스 컨테이너는 재시작되지 않는다.** 프로젝트 이름이 달라 컨테이너도 네트워크도 따로 생긴다.

### 접근

브라우저에서 아래 주소로 들어간다. 계정은 `admin` 이고 암호는 `.env` 의
`GRAFANA_ADMIN_PASSWORD` 다.

```
https://j15e204.p.ssafy.io/grafana
```

nginx 가 `/grafana` 를 `127.0.0.1:3001` 로 넘긴다. **Grafana 자체는 여전히 루프백에만 묶여
있어서**, 인터넷에서 들어오는 길은 이 경로 하나뿐이다. 포트를 직접 두드려서는 닿지 않는다.

`infra/nginx/default` 는 서버 설정의 기록본이라 저장소를 고쳐도 자동으로 반영되지 않는다.
서버에서 한 번 복사하고 `nginx -t` 로 검사한 뒤 `systemctl reload nginx` 를 해야 한다.
절차는 `infra/nginx/README.md` 에 있다.

nginx 를 손대지 않고 확인하고 싶을 때는 SSH 터널도 그대로 쓸 수 있다.

```bash
ssh -i ~/.ssh/J15E204T.pem -L 3001:127.0.0.1:3001 ubuntu@j15e204.p.ssafy.io
# 브라우저에서 http://localhost:3001
```

#### 무엇이 공개되는지

`/grafana` 를 열면 **인터넷 누구나 로그인 화면까지는 닿는다.** 로그에는 접속자 IP, 요청 경로,
작업 식별자, 지갑 주소가 들어 있으므로 **관리자 암호 하나가 유일한 장벽**이 된다.

그래서 세 가지를 지킨다.

| | |
| --- | --- |
| 암호 | 짐작할 수 없는 것으로 길게 둔다. 시험용으로 쓰던 것을 그대로 쓰지 않는다 |
| 가입 | `GF_USERS_ALLOW_SIGN_UP=false` 로 막혀 있다 |
| 익명 열람 | 켜지 않는다. Grafana 는 기본이 꺼짐이다 |

더 조이려면 nginx 에서 basic auth 를 한 겹 더 두거나 접속 대역을 제한할 수 있다. 지금은
필요가 확인되지 않아 두지 않았다.

## 검증

설치했다는 것과 쓸모 있다는 것은 다르다. 아래 넷을 확인한다.

| # | 확인할 것 |
| --- | --- |
| 1 | 컨테이너 여섯 개의 로그가 Grafana 에 보인다 |
| 2 | nginx 접근·오류 로그가 보인다 |
| 3 | **`docker restart` 뒤에도 이전 로그가 남아 있다** |
| 4 | 이미 아는 사건을 다시 찾는다 |

**3번이 진짜 기준이다.** 재배포로 로그가 날아가는 문제를 푸는 것이 목적이다.

4번 예시로 2026-09-18 오전에 VRAM 부족으로 주문 다섯 건이 거절된 일이 있다.

```logql
{service="backend"} |= "no_feasible_gpu"
```

## 확인이 안 될 때 — 조각이 아직 안 내려갔을 수 있다

**로그를 넣고 바로 조회하면 안 나올 수 있다.** 특히 워커 파일처럼 항목이 몇 개뿐일 때 그렇다.

Loki 는 항목을 모아 **조각(chunk)** 으로 저장하고, 조각은 가득 차거나 `max_chunk_age`(기본
2시간)가 지나야 조회 가능한 곳으로 내려간다. 그 전까지는 **접수는 됐지만 조회에는 안 나온다.**

색인과 조각이 갈린 상태가 그 신호다.

```bash
# 라벨에는 있는데
docker exec obs-grafana wget -qO- "http://loki:3100/loki/api/v1/label/service/values?start=...&end=..."

# series 는 비어 있다
docker exec obs-grafana wget -qO- "http://loki:3100/loki/api/v1/series?start=...&end=...&match[]={service=\"worker\"}"
```

강제로 내리면 바로 나온다.

```bash
docker exec obs-grafana wget -qO- --post-data="" http://loki:3100/flush
```

**지표는 이때도 전부 정상이라고 말한다.** Alloy 드롭 0, Loki 거절 0, 오류 없음, 컴포넌트
healthy. 그래서 "설정이 틀렸다"고 오해하기 쉽다. 설정을 고치기 전에 이것부터 확인한다.

## 세는 방법 — `limit` 이 아니라 집계 질의로

`query_range` 에 `limit` 을 주고 세면 **실제보다 적게 나온다.** 같은 파일이 `info`·`warn`·
`error` 로 갈려 여러 스트림이 되는데, 한도가 그 사이에 나뉘기 때문이다.

```bash
# 이렇게 세면 틀린다
.../query_range?query={filename="..."}&limit=1000

# 이렇게 센다
.../query?query=count_over_time({filename="..."}[25d])
```

## 로그 내용이 곧 자격 증명이 될 수 있다

**Grafana 를 `/grafana` 로 공개하면서 전제가 바뀌었다.** 터널로만 볼 때는 "서버에 들어올 수
있는 사람"이 곧 독자였지만, 이제는 Grafana 계정을 가진 사람이 독자다.

그래서 **로그에 무엇이 적히는지가 접근 통제의 일부**가 됐다.

### 서명 URL

`/api/storage/**` 의 서명 URL 에는 `sig=` 가 들어 있고, 유효 시간이 다운로드 2시간,
업로드 1시간이다. nginx 기본 포맷은 요청 줄을 통째로 남기므로 그것이 그대로 적힌다.

**로그를 읽는 사람이 그 줄을 복사해 그대로 쓰면** 데이터셋과 결과물을 가져갈 수 있고,
complete 이전 작업이라면 `result.tar` 를 덮어쓰는 PUT 까지 된다. 백엔드가 서명과 봉인으로
막아 둔 것을 로그 경로가 우회시켜 주는 셈이다.

두 겹으로 막는다.

| 어디 | 무엇 |
| --- | --- |
| `infra/nginx/default` | `log_format gshared` 가 `sig=` 값을 `REDACTED` 로 바꿔 **애초에 안 적는다** |
| `alloy-config.alloy` 의 `loki.process "redact"` | 쓰기 직전 한 곳에서 다시 가린다. 이미 디스크에 남은 과거분과, 백엔드가 서명 URL 을 찍는 경우까지 걸린다 |

**한 겹으로 두지 않은 이유**는 새 수집원을 붙일 때 빠뜨리기 쉽기 때문이다. 모든 경로가
`redact` 를 지나 Loki 로 간다.

> 이미 디스크에 쌓인 `access.log` 에는 가리기 전의 서명이 남아 있다. 그 파일은 `root` 만
> 읽을 수 있고 서버 접근 권한이 있어야 하므로, Grafana 공개와는 성격이 다른 위험이다.

### Loki 의 쓰기·삭제 API

Loki 는 `auth_enabled: false` 로 돌고, Grafana 의 데이터소스 프록시는 임의 경로를 그대로
넘긴다. 즉 **Grafana 계정을 쥔 쪽이 Loki 의 관리 API 에 닿는다.**

삭제는 `deletion_mode: disabled` 로 껐다. 훔친 뒤 흔적을 지우는 조합을 막기 위해서다.
보존 기간 삭제는 compactor 가 따로 하므로 영향이 없다.

**쓰기(`/loki/api/v1/push`)는 여전히 닿는다.** 지금은 계정이 `admin` 하나뿐이고 가입이
막혀 있어 실질적 위험이 낮다고 보지만, **조회 전용 계정을 만들 때 이 문제를 먼저 풀어야
한다.** 그 계정은 로그를 위조할 수 있기 때문이다.

## 감수한 위험 — 도커 소켓

Alloy 에 `/var/run/docker.sock` 을 마운트한다. **도커 소켓을 읽을 수 있는 컨테이너는 사실상
호스트를 장악할 수 있다.** 읽기 전용(`:ro`)으로 붙였지만 그것은 완화이지 해결이 아니다.

대안은 Alloy 를 컨테이너가 아니라 호스트에 직접 설치하는 것이다. 그러면 소켓 마운트가 없어지는
대신 apt 로 설치한 것을 따로 관리해야 한다. nginx 가 이미 그런 상태다.

이 규모에서는 마운트로 간다. **다만 Grafana 를 공개하면서 이 판단의 전제도 바뀌었다.**
Alloy 자체는 밖에서 닿지 않지만, 같은 호스트에 소켓을 쥔 컨테이너가 있다는 사실은 그대로다.
Grafana 관리자 암호가 사실상 이 스택 전체의 유일한 장벽이므로 **짐작할 수 없는 값으로 두고
시험용 암호를 절대 재사용하지 않는다.**

## 디스크

`loki-data` 볼륨에 **용량 상한이 없다.** 보존은 시간(30일)으로만 건다. 수집량이 갑자기
늘거나 같은 내용을 되풀이 적재하는 버그가 생기면 디스크를 밀어낼 수 있다 —
`docs/수집-함정.md` 의 10번이 실제로 그런 경우였다.

지금은 하루 수십 MB 에 여유가 266GB 라 상한을 두지 않는다. **대신 가끔 확인한다.**

```bash
docker system df -v | grep observability
```

## 되돌리기

```bash
docker compose -p observability down        # 컨테이너만
docker compose -p observability down -v     # 쌓인 로그까지
```

서비스 compose 와 무관하다.

## 하지 않는 것

- **알림.** 임계치를 걸어 사람을 부르는 것이 관제의 최종 목표이지만, 먼저 로그가 모여야 한다.
- **로그 형식 통일과 `jobId` 심기.** 모든 도메인 담당자가 자기 코드를 고쳐야 하는 일이라 별도
  합의가 필요하다. 수집이 먼저인 이유는, 돌아가는 화면을 보여 주고 부탁하는 편이 훨씬 잘
  통하기 때문이다.
- **도커 로그 회전 설정.** 서비스 compose 를 고치는 일이라 컨테이너 재생성이 따른다. 별건이다.
