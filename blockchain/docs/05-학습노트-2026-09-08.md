# 학습 노트 · 2026-09-08

오늘 코드로 배운 것만 담았다. 일반론이 아니라 **우리 컨트랙트에서 실제로 겪은 것**이다.

각 절 끝에 **스스로 답해 볼 질문**이 있다. 답은 그 아래 접혀 있다.

---

## 1. 컨트랙트는 스스로 실행되지 않는다

`acceptJob` 이 이 줄을 실행한다.

```solidity
job.deadline = uint64(block.timestamp) + executionTimeout;
```

**이건 "1시간 뒤에 환불해라" 는 예약이 아니다.** `1757300000` 같은 숫자를 저장해 둔 것뿐이다. 알람이 아니라 메모다.

EVM 은 **트랜잭션이 들어올 때만** 코드를 돌린다. 블록이 수만 개 지나가도 컨트랙트 안의 코드는 한 줄도 실행되지 않는다. 크론도 타이머도 없다.

누군가 `settleTimeout(jobId)` 을 보내야 그제서야 깨어나서 확인한다.

```solidity
if (block.timestamp <= job.deadline) revert DeadlineNotReached();
```

### 그래서 시한은 두 부분이다

| | 무엇 | 누가 |
|---|---|---|
| 기록 | 언제부터 처리 가능한지 저장 | 컨트랙트 |
| **발동** | 실제로 처리를 요청 | **바깥의 누군가** |

**둘째 줄을 채울 사람이 없으면 시한은 없는 것과 같다.** 이게 백엔드 키퍼가 존재하는 이유 전체다.

> **질문** — 시한이 지난 작업이 100개 쌓여 있다. 컨트랙트는 이걸 알고 있을까?

<details><summary>답</summary>

모른다. 컨트랙트는 "지금 몇 시" 도 스스로 확인하지 않는다. 누가 특정 `jobId` 로 물어봐야 그 하나만 계산해서 답한다. 밀린 작업 목록 같은 것은 존재하지 않는다. 그건 백엔드가 따로 들고 있어야 한다.
</details>

## 2. 예치가 트랜잭션 두 번인 이유

```
1) client → token.approve(escrow, 10)      GCoin 장부에 한도가 적힌다. 토큰은 안 움직인다
2) client → escrow.fundJob(1)              escrow 가 transferFrom 으로 끌어온다
```

**ERC-20 에는 밀어넣기가 없다.** 토큰 컨트랙트는 `escrow` 라는 컨트랙트를 모른다. 그래서 의뢰자가 먼저 한도를 열고, 에스크로가 그 안에서 끌어온다.

장부를 둘로 나눠 보면 분명해진다.

| 단계 | GCoin 장부 | Escrow 장부 |
|---|---|---|
| `createJob` | 변화 없음 | `jobs[1]` 생성 |
| `approve` | **`allowance` 만 바뀜** | 아무것도 모름 |
| `fundJob` | 잔액이 실제로 이동 | 상태가 `FUNDED` |

### 토큰은 Job 이 아니라 Escrow 주소로 간다

`Job` 은 지갑이 아니라 **에스크로 안의 장부 한 줄**이다. 작업이 여럿이면 돈은 한 통에 섞여 있고, 누구 몫인지는 에스크로가 기억한다.

> **질문** — 잔액이 0 인 지갑으로 `approve(escrow, 100)` 을 부르면 실패할까?

<details><summary>답</summary>

성공한다. `approve` 는 **한도 설정**이지 예약이 아니다. "가져가도 좋다" 고 적을 뿐 실제로 있는지는 안 본다. 나중에 `transferFrom` 할 때 잔액이 모자라서 실패한다.
</details>

## 3. 돈 나가는 경로의 권한을 손해 보는 사람에게만 주면 죽은 코드가 된다

이렇게 만들었다고 해 보자.

```solidity
function settleTimeout(uint256 jobId) external {
    require(msg.sender == jobs[jobId].client);   // 의뢰자만
```

공급자가 결과를 제출했고 승인 시한이 지났다. 이제 정산하면 **공급자에게 대금이 간다.**

**의뢰자가 그걸 부를까?** 부르면 자기 돈이 나간다. 안 부른다.

그러면 공급자는 일을 다 하고도 영원히 못 받는다. **코드에 함수는 있지만 없는 것과 같다.**

### 그래서 권한을 열었다

```solidity
function settleTimeout(uint256 jobId) external nonReentrant {   // 누구나
```

열어도 안전한 이유는 **호출자가 바꿀 수 있는 게 하나뿐**이기 때문이다.

| 호출자가 정할 수 있는가 | |
|---|---|
| 돈이 **누구에게** 가는가 | ❌ 상태가 정한다 |
| **언제** 처리되는가 | ❌ 시한이 정한다 |
| **얼마가** 나가는가 | ❌ `job.price` 가 정한다 |
| 부를지 말지 | ⭕ **이것뿐** |

### 권한 배치의 기준 한 줄

> **컨트랙트가 스스로 판정할 수 있으면 열고, 사람의 판단이 필요하면 닫는다.**

| 함수 | 권한 | 왜 |
|---|---|---|
| `approveResult` | 의뢰자만 | 결과가 만족스러운지는 사람이 판단한다 |
| `settleTimeout` | 누구나 | 시각 비교 하나뿐이라 기계가 대신할 수 있다 |

> **질문** — `cancelJob` 은 왜 의뢰자만 부를 수 있나?

<details><summary>답</summary>

"아직 필요 없어졌다" 는 판단은 의뢰자만 할 수 있다. 시각이나 상태로 기계가 정할 수 없다. 그래서 닫는다.
</details>

## 4. 정산 방향을 잘못 잡으면 잠수가 최적 전략이 된다

`ASSIGNED` 만료(공급자가 제출 안 함)를 **공급자 지급**으로 정한다면?

```
10:00  acceptJob 호출          가스 몇 백 원
       GPU 는 켜지 않는다
11:00  시한 경과
11:01  settleTimeout 호출  →  대금 전액 수령
```

**일을 하나도 안 하고 돈을 받는다.** `submitResult` 를 부를 이유조차 없다. 오히려 결과를 내면 이의를 받을 수 있으니 안 내는 쪽이 유리하다.

### 왜 이게 가능한가

컨트랙트는 **GPU 가 돌았는지 볼 수 없다.**

```
볼 수 있는 것    상태, 시각, 저장된 해시, 잔액
볼 수 없는 것    GPU 가 켜졌는지, 계산이 맞는지
```

`settleTimeout` 의 검사에는 **"일을 했는지" 묻는 줄이 없다.**

### 그래서 방향은 이렇게 잡았다

| 만료 상황 | 방향 | 이유 |
|---|---|---|
| `ASSIGNED` 만료 | 의뢰자 환불 | 공급자가 일을 안 했다 |
| `SUBMITTED` 만료 | 공급자 지급 | 공급자가 일을 했다 |

**잘못한 쪽이 손해를 본다.** 그리고 각 경로마다 **이득 보는 쪽이 곧 호출자**가 되므로 설계가 스스로 굴러간다.

> **질문** — `resultHash` 를 제출하면 올바르게 계산했다는 증명이 되나?

<details><summary>답</summary>

안 된다. 아무 32바이트나 넣어도 컨트랙트는 통과시킨다. `resultHash` 가 증명하는 것은 **"이 결과가 내 결과다" 라고 공급자가 자기 지갑으로 서명했다** 는 사실뿐이다. 부인 방지와 봉인이다.

실제 검증은 의뢰자가 결과 파일을 받아 해시를 대조하는 방식으로 오프체인에서 한다. **그래서 이의 제기 기능이 필요하다.**
</details>

## 5. `block.timestamp` 는 블록 제안자가 적는다

트랜잭션에는 **시각 필드가 없다.**

```
nonce · gasPrice · gasLimit · to · value · data · 서명
```

보낸 시각도 기록되지 않는다. `mempool` 에서 몇 초를 기다릴 수도 몇 분을 기다릴 수도 있다.

**시각은 블록을 만드는 사람이 헤더에 적는다.**

### 결과 둘

**같은 블록의 트랜잭션은 전부 같은 시각을 본다.** 100개가 들어 있으면 100개가 같은 값을 읽는다.

**제안자가 몇 초 조작할 수 있다.** 부모 블록보다 크고 너무 먼 미래가 아니면 통과한다.

### 우리한테는 무해하다

시한이 분·시간 단위라 15초가 흔들려도 의미가 없다. 그리고 제안자가 남의 에스크로 시한을 앞당겨 얻을 이득이 없다.

**위험한 자리는 난수를 만들 때다.**

```solidity
uint256 index = uint256(keccak256(abi.encode(block.timestamp))) % N;  // 위험
```

제안자가 값을 조금씩 바꿔 보면서 자기에게 유리한 결과를 고를 수 있다. 검증 표본을 고를 때 이 문제가 걸린다.

> **질문** — 시한 검사에는 써도 되는데 난수에는 쓰면 안 되는 이유가 뭔가?

<details><summary>답</summary>

시한 검사는 **"넘었나 안 넘었나" 를 볼 뿐**이라 15초 차이가 결과를 뒤집지 않는다.

난수는 **값 하나하나가 다른 결과를 만든다.** 제안자가 여러 값을 시도해 보고 원하는 결과가 나오는 것을 고를 수 있다.
</details>

## 6. 같은 블록 경쟁 — 구간을 겹치지 않게 자른다

공급자가 시한 직전에 제출했는데 `mempool` 에서 밀려 시한이 지났다. 같은 블록에 `settleTimeout` 도 담겼다.

**둘 다 유효하면 순서에 따라 결과가 뒤집힌다.**

| 먼저 실행 | 결과 |
|---|---|
| `submitResult` | 작업이 정상 진행 |
| `settleTimeout` | 환불되고 공급자는 계산하고도 못 받음 |

### 해법은 구간을 겹치지 않게 만드는 것

```solidity
acceptJob      if (block.timestamp >  job.deadline) revert DeadlineExpired();
submitResult   if (block.timestamp >  job.deadline) revert DeadlineExpired();
settleTimeout  if (block.timestamp <= job.deadline) revert DeadlineNotReached();
```

| 블록 시각 | 정상 함수 | `settleTimeout` |
|---|---|---|
| 시한 이하 | ⭕ | ❌ |
| 시한 초과 | ❌ | ⭕ |

**정각은 정상 함수 쪽이다.** 동시에 유효한 순간이 없으므로 순서가 결과를 못 바꾼다.

**확률을 낮춘 게 아니라 가능성을 없앤 것이다.** 이게 이 문제를 푸는 좋은 방식이다.

> **질문** — `cancelJob` 에는 왜 경계 검사를 안 넣었나?

<details><summary>답</summary>

시한이 지난 뒤 `cancelJob` 과 `settleTimeout` 이 같은 블록에 와도 **결과가 같다.** 둘 다 의뢰자 환불이고 `CANCELLED` 로 끝난다.

**경계 검사가 필요한 곳은 결과가 갈리는 자리뿐이다.**
</details>

## 7. CEI 와 재진입 — 그리고 CEI 로 안 막히는 것

### 같은 함수 재진입은 CEI 로 막힌다

```solidity
job.state = JobState.COMPLETED;                 // Effects  상태 먼저
paymentToken.safeTransfer(job.provider, price); // Interactions 송금 나중
```

순서를 바꾸면 이렇게 털린다.

```
송금 → 공격자가 토큰을 받는 순간 콜백
     → 다시 approveResult 호출
     → state 가 아직 SUBMITTED 라 통과 → 또 송금 → 반복
```

**실제로 확인했다.** 순서를 뒤집으니 테스트가 이렇게 실패했다.

```
Error: attacker drained extra funds: 1010 != 1000
```

공격자가 **피해자 예치금 10 GSC 를 가져갔다.**

### 그런데 교차 함수 재진입은 CEI 로 안 막힌다 — 오늘 가장 큰 배움

```
악성 의뢰자 → escrow.fundJob()
                job.state = FUNDED           ← CEI 대로 상태 먼저
                token.safeTransferFrom()
                    토큰이 보내는 쪽에 콜백
                        → escrow.cancelJob() 재진입
                            require(job.client == msg.sender)  ✅ 본인이 맞다
                            require(job.state == FUNDED)       ✅ 방금 바꿔 놨다
                            → 통과
```

**CEI 가 오히려 통과 조건을 만들어 준다.** 상태를 미리 `FUNDED` 로 바꿔 놨기 때문에 `cancelJob` 의 검사를 그대로 통과한다.

그래서 `nonReentrant` 를 붙였다. 떼어 보니 실제로 뚫렸다.

```
nonReentrant 를 뗀 상태
Error: cross-function reentrancy was NOT blocked
```

| 방어 | 막는 것 |
|---|---|
| **CEI** | 같은 함수로 다시 들어오는 것 |
| **`nonReentrant`** | **다른 함수로 들어오는 것까지** |

> **질문** — 재진입 테스트에 왜 피해자 예치금을 미리 넣어 두었나?

<details><summary>답</summary>

에스크로에 공격자 돈만 있으면 두 번째 인출이 **잔액 부족으로** 실패한다. 그러면 "CEI 덕분에 막힌 것" 인지 "돈이 없어서 막힌 것" 인지 구분할 수 없다.

**남의 돈이 있어야 진짜 도둑질이 성립하고, 그걸 막는지를 볼 수 있다.**
</details>

## 8. 테스트가 진짜인지 확인하는 법 — 변이 검증

**통과하는 테스트가 사실은 아무것도 검사하지 않는 경우가 흔하다.**

그래서 오늘 두 번 했다.

```
CEI 순서를 뒤집는다        → 재진입 테스트가 실패한다  ✅ 진짜다
nonReentrant 를 뗀다      → 교차 함수 테스트가 실패한다 ✅ 진짜다
```

**고의로 망가뜨렸을 때 테스트가 잡아내야 그 테스트를 믿을 수 있다.**

여기에 하나 더 있다.

```solidity
function test_hookTokenActuallyCallsBack()
```

**콜백이 실제로 불렸는지**를 먼저 확인한다. 공격이 시도조차 안 됐는데 "막혔다" 고 넘어가는 상황을 막는다.

> **질문** — "테스트 78건이 통과합니다" 라는 말은 무엇을 증명하나?

<details><summary>답</summary>

**"78개의 주장이 지금은 거짓이 아니다" 만 증명한다.**

그 주장들이 중요한 것인지, 검사할 값을 제대로 보는지는 별개다. 변이 검증이 그 부분을 메운다.
</details>

## 9. 가스 — 스토리지가 비싸다

측정한 값이다.

| 함수 | 가스 |
|---|---:|
| `createJob` | **61,847** |
| `fundJob` | 40,452 |
| `acceptJob` | 23,947 |
| `submitResult` | 24,122 |
| `approveResult` | 32,522 |
| `cancelJob` | **10,397** |

### `createJob` 이 토큰을 안 옮기는데 제일 비싸다

```
빈 슬롯에 처음 쓰기   20,000 가스
이미 쓴 슬롯 고치기    5,000 가스
```

**스토리지에 처음 쓰기 때문이다.** 여기서 구조체 배치가 값을 한다.

```solidity
address  client;    // 20바이트  ┐
JobState state;     //  1바이트  ├─ 29바이트 → 32바이트 슬롯 하나
uint64   deadline;  //  8바이트  ┘
```

**따로 뒀다면 슬롯이 둘 늘어 4만 가스가 더 들었다.**

### 환불이 지급보다 세 배 싸다

```
cancelJob          10,397   의뢰자에게 환불
settle SUBMITTED   34,244   공급자에게 지급
```

**받는 사람의 잔액 슬롯 상태가 다르기 때문이다.** 의뢰자는 원래 토큰이 있어서 슬롯이 채워져 있고(고치기 5,000), 공급자는 처음 받는 것이라 빈 슬롯에 쓴다(20,000).

**같은 공급자의 두 번째 정산부터는 싸진다.**

> **질문** — 함수 하나를 싸게 만들려면 무엇부터 봐야 하나?

<details><summary>답</summary>

**스토리지를 몇 번 건드리는지**를 먼저 본다. 계산이나 반복문보다 슬롯 쓰기가 압도적으로 비싸다. 그다음이 변수 배치를 붙여서 슬롯 수를 줄이는 것이다.
</details>

| `vm.prank(addr)` | **다음 한 줄만** 그 주소가 부른 것으로. 계속하려면 `startPrank`/`stopPrank` |
| `vm.warp(t)` | 블록 시각을 옮긴다. 2시간을 실제로 기다릴 수 없으니 |
| `vm.chainId(n)` | 체인 번호를 바꾼다. 배포 가드 테스트용 |
| `vm.expectRevert(선택자)` | 다음 줄이 되돌아갈 것을 예고 |
| `vm.expectEmit(...)` | 다음 줄이 이벤트를 낼 것을 예고 |
| `SafeERC20` | 반환값을 안 주는 토큰까지 안전하게 다룬다 |
| `ReentrancyGuard` | `nonReentrant` 로 재진입 차단 |

---

## 오늘 내가 두 번 틀렸다

기록해 둔다. 같은 실수를 반복하지 않으려는 것이다.

**첫째, `deadline` 을 남기자고 했다.** ABI 호환성을 근거로 들었는데, 배포하지 않을 버전이라 지킬 호환성이 없었다. 안 쓰이는 필드가 이벤트에 남으면 백엔드가 타임아웃이 보장된다고 오해한다.

**둘째, `nonReentrant` 를 과잉 방어라고 했다.** CEI 로 충분하다고 봤는데 교차 함수 재진입이 뚫렸다. **CEI 는 같은 함수만 막는다.**

두 번 다 **"이미 안전하다" 는 판단이 근거보다 앞섰다.** 안전 주장은 테스트로 확인하기 전까지는 가설이다.
