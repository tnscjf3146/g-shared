## 3. 숫자가 말해 주는 것 넷

### 3-1. `createJob` 이 가장 비쌉니다

토큰을 하나도 안 옮기는데 **67,153** 으로 제일 큽니다. 이유는 **스토리지에 처음 쓰기 때문**입니다.

```
빈 슬롯에 처음 쓰기   20,000 가스
이미 쓴 슬롯 고치기    5,000 가스
```

`Job` 구조체가 슬롯 셋을 차지하고(`client+state+deadline`, `provider`, `price`, `resultHash`), 거기에 `nextJobId` 증가가 더해집니다.

**구조체 배치를 한 슬롯에 맞춘 것이 여기서 값을 합니다.** `client(20) + state(1) + deadline(8) = 29바이트` 를 따로 뒀다면 슬롯이 둘 더 늘어 4만 가스가 더 들었을 것입니다.

### 3-2. 공급자 지정이 가스를 앞으로 옮겼습니다

의뢰자가 예치할 때 공급자를 지정하도록 바꾸면서 비용의 위치가 달라졌습니다.

| 함수 | 이전 | 지금 | 차이 |
|---|---:|---:|---:|
| `fundJob` | 38,488 | 61,337 | **+22,849** |
| `acceptJob` | 27,278 | 7,137 | **−20,141** |

`provider` 슬롯에 처음 쓰는 20,000 가스가 `acceptJob` 에서 `fundJob` 으로 옮겨 갔을 뿐입니다. 한 바퀴 총액은 거의 그대로입니다.

**대신 부담하는 사람이 바뀌었습니다.** 공급자가 내던 몫을 의뢰자가 냅니다. 우리 체인은 가스 가격이 0 이라 실제 차이는 없지만, 공개 체인에 올린다면 따져 볼 대목입니다.

### 3-3. 환불이 지급보다 훨씬 쌉니다

```
cancelJob             10,397   의뢰자에게 환불
settle SUBMITTED      34,256   공급자에게 지급
```

**세 배 넘게 차이 납니다.** 하는 일은 비슷한데 왜 그럴까요.

| | 환불 | 지급 |
|---|---|---|
| 받는 사람 잔액 | 이미 있음 → **고치기** 5,000 | 0 에서 시작 → **처음 쓰기** 20,000 |
| 에스크로 잔액 | 0 이 됨 → **환급 발생** | 0 이 됨 → 환급 발생 |

**의뢰자는 원래 토큰을 갖고 있어서 잔액 슬롯이 이미 채워져 있습니다.** 공급자는 처음 받는 것이라 빈 슬롯에 쓰게 됩니다.

즉 **같은 공급자가 두 번째 작업을 받을 때는 훨씬 쌉니다.** 첫 정산만 비쌉니다.

### 3-4. 검증 단계를 붙여도 여유가 있습니다

이더리움 블록 가스 한도가 3천만입니다. 한 바퀴가 **21만** 이니 여유가 큽니다.

앞으로 붙일 것들을 대략 잡아 보면 이렇습니다.

| 추가 예정 | 예상 |
|---|---|
| `raiseDispute` (예치금 이동 + 상태) | 5~6만 |
| `submitVerdict` (판정 + 분배) | 6~8만 |
| 머클 증명 검증 (깊이 20 기준) | 6~7만 |

**전부 붙여도 한 작업이 50만 가스를 넘지 않을 것으로 보입니다.** 설계 문서가 주장한 "검증 비용 = 원 연산의 1%" 는 **온체인 가스가 아니라 재실행 연산량** 이야기지만, 온체인 쪽도 병목이 아니라는 근거는 됩니다.
