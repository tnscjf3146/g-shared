## 2. Q1~Q4 반영 내역

### Q1 · 시한 기준 — `block.timestamp`, 상태 전이 시점 기산

```solidity
fundJob        job.deadline = uint64(block.timestamp) + acceptDeadline;
acceptJob      job.deadline = uint64(block.timestamp) + execDeadline;
submitResult   job.deadline = uint64(block.timestamp) + approveDeadline;
```

**`acceptDeadline` 을 신설**해 `FUNDED` 구멍을 막았습니다. 지적해 주신 부분입니다.

`deadline` 필드는 하나만 두고 상태마다 덮어씁니다. 한 작업은 한 번에 한 상태에만 있고, 구조체가 `client(20) + state(1) + deadline(8) = 29바이트` 로 여전히 한 슬롯에 들어갑니다.

`CREATED` 에는 시한을 두지 않았습니다. 예치 전이라 잠길 자금이 없습니다.

### Q2 · 호출 권한 — 누구나, 인자는 `jobId` 뿐

```solidity
function settleTimeout(uint256 jobId) external
```

수령자·금액·정산 방향을 인자로 받지 않습니다. 전부 `fromState` 와 `job` 에서 컨트랙트가 결정합니다.

검증 테스트 둘을 두었습니다.

| 테스트 | 확인하는 것 |
|---|---|
| `test_settleTimeout_callableByStranger` | 제3자가 불러도 결과가 같다 |
| `test_settleTimeout_callerGetsNothing` | 제3자 잔액이 0 이다. 아무것도 못 가져간다 |

E2E 두 흐름에서도 **당사자가 아닌 `keeper` 계정이 호출**하고, 매번 `keeper` 잔액 0 을 확인합니다.

### Q3 · 정산 방향

| 만료 상황 | 방향 | 상태 전이 |
|---|---|---|
| `FUNDED` 만료 | 의뢰자 환불 | → `CANCELLED` |
| `ASSIGNED` 만료 | 의뢰자 환불 | → `CANCELLED` |
| `SUBMITTED` 만료 | 공급자 지급 | → `COMPLETED` |

앞의 둘은 처리가 같아 코드에서 한 갈래로 묶었습니다. 둘 다 공급자가 결과를 만들어내지 못한 경우입니다.

`JobTimedOut(jobId, fromState)` 를 함께 발생시켜 **어느 상태에서 끝났는지**를 알립니다. `JobCancelled` 만으로는 의뢰자 취소인지 시한 만료인지 구분할 수 없습니다.

### Q4 · 경계 조건 — 구간을 겹치지 않게

```solidity
acceptJob      if (block.timestamp >  job.deadline) revert DeadlineExpired();
submitResult   if (block.timestamp >  job.deadline) revert DeadlineExpired();
settleTimeout  if (block.timestamp <= job.deadline) revert DeadlineNotReached();
```

| 블록 시각 | 정상 함수 | `settleTimeout` |
|---|---|---|
| `timestamp <= deadline` | 가능 | 실패 |
| `timestamp > deadline` | 실패 | 가능 |

유예 블록을 두지 않았습니다. 같은 블록에서 둘이 동시에 유효한 순간이 없으므로 트랜잭션 순서가 결과를 바꾸지 못합니다.

## 4. 임의로 판단한 것 둘 — 확인 부탁드립니다

### 4-1. `acceptJob` 에 시한 검사를 넣었습니다

리뷰 문서에 없던 항목입니다. 경계 원칙을 그대로 적용했습니다.

```solidity
if (block.timestamp > job.deadline) revert DeadlineExpired();
```

없으면 이렇게 됩니다.

```
14:00  fundJob     수락 시한 16:00
16:30  시한 경과   settleTimeout 으로 환불 가능한 상태
16:31  acceptJob   막지 않으면 통과
       → ASSIGNED 로 바뀌고 시한이 17:31 로 새로 걸림
       → 의뢰자 환불이 한 시간 더 밀린다
```

**만료된 작업을 되살려 환불을 계속 미룰 수 있습니다.** 악의가 없어도 우연히 발생합니다.

### 4-2. `cancelJob` 에는 시한 검사를 넣지 않았습니다

경계 검사가 필요한 곳은 **결과가 갈리는 자리**뿐이라고 판단했습니다.

| 함수 | 시한 후 결과 |
|---|---|
| `cancelJob` (FUNDED) | 의뢰자 환불 · `CANCELLED` |
| `settleTimeout` (FUNDED) | 의뢰자 환불 · `CANCELLED` |

둘이 같아서 어느 쪽이 먼저 실행되든 상관없고, 나머지는 `require` 에 걸립니다. 이 판단을 `test_cancelJob_stillWorksAfterAcceptDeadline` 으로 못박아 두었습니다.

`cancelJob` 은 `FUNDED` 에서만 동작합니다. `CREATED` 취소는 자금 안전 경로가 아니라고 하셔서 범위에서 뺐습니다.

## 6. 재진입 — 공격자를 다시 짰습니다

### 옛 공격자는 자금 안전을 증명하지 못했습니다

구 브랜치 공격자는 `submitResult` 로 재진입했는데, **그 함수는 토큰이 움직이지 않습니다.** 막혀도 증명되는 것이 없었습니다.

돈이 나가는 자리는 넷이고 받는 쪽은 둘이라, 공격자를 둘로 나눴습니다.

| 공격자 | 역할 | 재진입 통로 |
|---|---|---|
| `ReentrantClient` | 악성 의뢰자 | 환불받는 순간 `cancelJob` 재호출 |
| `ReentrantProvider` | 악성 공급자 | 대금받는 순간 `settleTimeout` 재호출 |

### 피해자 예치금을 함께 넣어 둡니다

에스크로에 공격자 돈만 있으면 두 번째 인출이 **잔액 부족으로** 실패합니다. 그러면 CEI 덕분에 막힌 것인지 구분할 수 없습니다. 남의 돈이 있어야 도둑질이 성립하고, 그걸 막는지를 볼 수 있습니다.

### 변이 검증을 했습니다

CEI 순서를 **일부러 뒤집어** 테스트가 실제로 공격을 잡는지 확인했습니다.

```solidity
bool ok = paymentToken.transfer(job.client, refund);   // 송금 먼저
job.state = JobState.CANCELLED;                        // 상태 나중
```

```
1) test_cancelJob_reentrancyIsBlocked()
   Error: attacker drained extra funds: 1010 != 1000
```

**공격자가 피해자 예치금 10 GSC 를 가져갔습니다.** 순서를 되돌리면 통과합니다. 지금 통과가 우연이 아님을 확인했습니다.

`test_hookTokenActuallyCallsBack` 으로 **콜백이 실제로 불렸는지**도 먼저 확인합니다. 공격이 시도조차 안 됐는데 통과하는 상황을 막습니다.

## 7. E2E 3건

지시대로 세부 조건을 반복하지 않고 전체 흐름만 남겼습니다.

```
정상 흐름     예치 → 수락 → 제출 → 승인 → 공급자 지급
환불 흐름     수락 후 미제출, 시한 경과 → 의뢰자 환불
무응답 지급   제출 후 의뢰자 무응답, 시한 경과 → 공급자 지급
```

`GCoin` 과 `GPUJobEscrow` 를 같은 네트워크에 함께 배포하고, 지갑 넷(`deployer`·`client`·`provider`·`keeper`)을 씁니다. 정산 두 건은 `keeper` 가 호출하고 매번 잔액 0 을 확인합니다.
