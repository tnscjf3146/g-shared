## 2. 리뷰 반영 내역

### 범위 축소

`CANCELLED` 상태, `cancelJob`, `settleTimeout`, `JobCancelled`, `JobTimedOut` 을 제거했습니다. 226줄에서 162줄이 되었습니다.

### 체인 가드

```solidity
uint256 private constant SSAFY_CHAIN_ID = 31221;

error SsafyDeploymentBlocked();

constructor(address paymentToken_) {
    if (block.chainid == SSAFY_CHAIN_ID) revert SsafyDeploymentBlocked();
    require(paymentToken_ != address(0), "Escrow: token is zero");
    paymentToken = IERC20(paymentToken_);
}
```

테스트 2건을 붙였습니다. `test_constructor_revertsOnSsafyChain` 위에 **"취소·환불·타임아웃 구현이 끝나면 이 테스트와 가드를 함께 지운다"** 를 주석으로 남겼습니다.

### `deadline` 제거

말씀대로 필드와 이벤트 인자를 뺐습니다. **여기에 더해 `execDeadline`·`approveDeadline` immutable 두 개와 생성자 인자도 함께 뺐습니다.** `deadline` 이 없으면 계산할 대상이 사라져 죽은 코드가 되고, 남겨 두면 "타임아웃이 있다" 는 같은 오해를 부르기 때문입니다.

결과적으로 생성자가 `constructor(address paymentToken_)` 한 줄이 되었습니다. **이 판단이 과했으면 되돌리겠습니다.**

## 3. `forge-std` 도입 시 주의점 두 가지

Solidity 테스트를 돌리려고 `forge-std` 를 넣으면서 함정을 만났습니다. 다른 분들도 겪을 수 있어 적어 둡니다.

### npm 의 `forge-std` 는 비공식 미러입니다

`npm install forge-std` 로 받으면 개인이 올린 패키지가 설치됩니다. 버전이 1.1.2 로 낡았고 `Test.sol` 위치가 달라 Hardhat 이 해석하지 못합니다. 공식 저장소를 써야 합니다.

```json
"forge-std": "github:foundry-rs/forge-std#v1.9.7"
```

### npm 12 는 git 의존성을 기본 차단합니다

```
npm error code EALLOWGIT
npm error Fetching packages of type "git" have been disabled
```

`allow-git` 기본값이 `none` 이라 `--allow-git=all` 을 붙여야 합니다.

```bash
npm ci --allow-git=all
```

**npm 11 에서는 필요 없습니다.** README 실행법에 한 줄 적어 두면 좋겠습니다.

### lockfile 이 주소를 `git+ssh` 로 바꿉니다

버전을 커밋 SHA 로 고정하라는 지적을 반영했습니다.

```json
"forge-std": "https://github.com/foundry-rs/forge-std.git#77041d2ce690e692d6e03cc812b57d1ddaa4d505"
```

그런데 `package.json` 에 https 로 적어도 **npm 이 lockfile 에는 `git+ssh://git@github.com/...` 로 정규화해서 기록합니다.** GitHub SSH 키가 없는 팀원은 `npm ci` 가 실패합니다.

각자 아래 한 줄을 걸어 두면 해결됩니다.

```bash
git config --global url."https://github.com/".insteadOf "ssh://git@github.com/"
```

npm 설정으로는 못 바꾸는 부분이라 git 쪽에서 처리해야 합니다. README 에 함께 적겠습니다.

## 4. 확인 요청 4건

취소·타임아웃 착수를 막고 있는 항목입니다.

### Q1 · 시한의 기준 시각

**제안** — `block.timestamp` 를 쓰고, 상태가 바뀌는 시점부터 기산합니다. 수락하면 `execDeadline`, 제출하면 `approveDeadline` 을 더합니다.

**근거** — 블록 번호 기준으로 하면 블록 시간이 흔들릴 때 실제 경과 시간이 달라집니다. 타임스탬프는 제안자가 몇 초 조작할 수 있지만 시한이 분·시간 단위라 무해합니다.

**갈리는 지점** — 기산점을 예치 시점으로 잡으면 아무도 수락하지 않는 구간에도 시한이 걸리고, 상태 전이 시점으로 잡으면 걸리지 않습니다.

### Q2 · 시한 정산의 호출 권한

**제안** — 누구나 호출할 수 있게 합니다.

**근거** — 당사자로 제한하면 정산 방향에 따라 **호출할 사람이 부를 동기가 없어집니다.** 예를 들어 승인 시한이 지나 공급자에게 지급해야 하는데 의뢰자만 호출할 수 있다면, 의뢰자는 부르지 않습니다. 부르면 자기 돈이 나가기 때문입니다. 그러면 함수가 있어도 죽은 코드가 됩니다.

컨트랙트가 시한과 상태를 직접 검사하므로 호출자는 **수신자도 시점도 금액도 바꿀 수 없습니다.** 결정할 수 있는 것이 "부를지 말지" 하나뿐이라 열어도 안전합니다.

**따라오는 문제** — 아무도 가스를 내고 부르지 않으면 실제로는 정산이 안 일어납니다. 소액 작업에서 특히 그렇습니다. 백엔드에 키퍼를 두는 방안을 백엔드 담당자와 협의해야 합니다.

### Q3 · 미제출 만료의 정산 방향

**제안** — 두 방향을 다르게 잡습니다.

| 만료 상황 | 정산 방향 | 이유 |
|---|---|---|
| `ASSIGNED` 만료 (공급자가 제출 안 함) | **의뢰자 환불** | 공급자가 일을 안 했다 |
| `SUBMITTED` 만료 (의뢰자가 승인 안 함) | **공급자 지급** | 공급자가 일을 했다 |

**근거** — `ASSIGNED` 만료를 공급자 지급으로 잡으면 **수락하고 잠수하는 것이 최적 전략**이 됩니다. 컨트랙트는 GPU 가 돌았는지 볼 수 없고, 시한 경과만 검사하기 때문입니다.

```
10:00  acceptJob 호출          가스 몇 백 원
       GPU 는 켜지 않는다
11:00  시한 경과
11:01  settleTimeout 호출  →  대금 전액 수령
```

`submitResult` 를 부를 이유조차 없어집니다. 오히려 결과를 내면 이의를 받을 수 있으니 안 내는 쪽이 유리해집니다. 봇이 모든 `FUNDED` 작업을 자동 수락하고 시한만 기다리면 서비스가 무너집니다.

### Q4 · 시한 경계에서 제출과 정산이 같은 블록에 담길 때 (신규)

**문제** — 공급자가 시한 직전에 `submitResult` 를 보냈는데 mempool 에서 밀려 시한이 지났다. 같은 블록에 `settleTimeout` 도 담기면 **블록 안 순서에 따라 결과가 뒤집힌다.**

| 먼저 실행된 것 | 결과 |
|---|---|
| `submitResult` | 상태가 `SUBMITTED` 로 넘어가고 작업이 정상 진행된다 |
| `settleTimeout` | 의뢰자에게 환불되고, **공급자는 계산을 다 하고도 한 푼도 못 받는다** |

블록 안 순서는 제안자가 정하며 보통 가스 값 순이다. 즉 **공급자가 가스를 적게 내면 손해를 본다.**

**선택지**

| 안 | 내용 | 대가 |
|---|---|---|
| **(가)** | 시한을 넉넉히 잡는다 (예상 소요의 3배 등) | 잠수한 공급자를 오래 기다린다 |
| (나) | 유예 구간 — 시한 후 N블록은 `settleTimeout` 을 막는다 | 시한이 두 겹이 되어 상태 기계가 복잡해진다 |
| (다) | 문서화만 하고 넘어간다 | 공급자가 손해를 본다 |

**제안** — (가). 상태 기계를 건드리지 않으면서 경계 상황 자체를 드물게 만든다. Q1 의 시한 값 결정과 함께 정하면 된다.

## 5. 팀 차원 문제 3건 — 주인이 없습니다

### 문제 1 · "자금 동결 없음" 이 코드에 없습니다

기획 단계에서 이 서비스의 특장점 중 하나로 **"모든 대기 상태에 타임아웃이 있고, 타임아웃 전이는 누구나 호출 가능해서 상대가 잠수해도 자금이 영구 동결되지 않는다"** 를 내세웠습니다.

**지금 구현에는 그 기능이 없습니다.** 취소·타임아웃 작업에서 복구하겠습니다. 우선순위를 높게 잡는 이유입니다.

### 문제 2 · 공급자 노드가 온체인에 서명할 방법이 정해지지 않았습니다

한 바퀴 흐름을 따라가면 여기서 끊깁니다.

```
공급자 노드가 GPU 계산을 끝냈다
        ↓
submitResult(jobId, hash) 를 온체인에 보내야 한다
        ↓
??? 노드가 무슨 지갑으로 서명하는가
```

`blockchain-skeleton.md` 8장이 **"Backend가 사용자 대신 자금 트랜잭션을 서명하지 않는다"** 로 정했으니, 공급자 노드가 자기 키를 가져야 합니다. **키를 어떻게 만들고 어디에 두는지 정해진 바가 없고, Jira 에도 해당 항목이 없습니다.**

`acceptJob` 도 같은 문제입니다. 노드가 일감을 수락하려면 온체인 트랜잭션을 보내야 합니다.

### 문제 3 · GSC 배분 방법이 없습니다

GSC 100만 개가 전부 배포 지갑(`0xbEB1...2595`)에 있습니다. **시연할 때 의뢰자 계정이 GSC 를 어떻게 받는지 정해진 게 없습니다.** 수동 전송인지, faucet 함수를 붙이는지, 초기 배분을 스크립트로 하는지 결정이 필요합니다.

에스크로 실체인 테스트에도 잔액이 필요해서 저도 막힙니다.

## 7. 나중에 다시 볼 것 — 표본 선정에 블록 해시를 쓰는 문제

이번 작업 범위는 아니지만 이의 제기·판정을 붙일 때 반드시 걸립니다.

`block.timestamp` 와 블록 해시는 **시한 검사에는 안전하지만 난수 생성에는 위험합니다.** 블록 제안자가 값을 몇 초 범위에서 조작할 수 있어서, 자기에게 유리한 결과가 나올 때까지 시도해 볼 수 있습니다.

```solidity
uint256 index = uint256(keccak256(abi.encode(block.timestamp))) % N;  // 조작 가능
```

검증 단계에서 "어느 표본을 검사할지" 를 블록 해시로 정하기로 되어 있는데, 그 방식이 미정으로 남아 있습니다. 검증자 선정 방식을 정할 때 함께 다뤄야 합니다.
