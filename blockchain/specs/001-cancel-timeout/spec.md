# Feature Specification: 취소와 타임아웃으로 자금 회수 경로 열기

**Feature Branch**: `bc-feature/escrow-cancel-timeout` (아직 생성하지 않음)

**Created**: 2026-09-08

**Status**: Draft — 미결 3건이 확정되어야 계획 단계로 넘어간다

**Input**: 현재 에스크로는 예치금이 빠져나가는 경로가 `approveResult` 하나뿐이라, 상대가 응답하지 않으면 자금이 영구히 잠긴다. 헌법 원칙 II 를 위반하는 활성 예외 EX-1 을 해소한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 아무도 잡지 않은 일감을 거두어들인다 (Priority: P1)

의뢰자가 대금을 예치했는데 며칠이 지나도 아무 공급자가 수락하지 않는다. 의뢰자는 작업을 취소하고 예치금 전액을 돌려받는다.

**Why this priority**: 상대방이 아직 없으므로 분쟁의 여지가 없고, 셋 중 가장 단순하다. 그리고 가장 흔하게 발생한다. 이것만 있어도 "예치했다가 영영 못 찾는" 최악의 상황이 사라진다.

**Independent Test**: 작업을 만들고 예치한 뒤 수락 없이 취소해서, 의뢰자 잔액이 예치 전으로 돌아오고 에스크로 잔액이 0 이 되는 것으로 검증한다.

**Acceptance Scenarios**:

1. **Given** 대금이 예치된 작업(FUNDED)이 있고 아직 수락되지 않았을 때, **When** 의뢰자가 취소하면, **Then** 예치금 전액이 의뢰자에게 돌아가고 작업이 종료 상태가 된다
2. **Given** 대금을 아직 예치하지 않은 작업(CREATED)이 있을 때, **When** 의뢰자가 취소하면, **Then** 토큰 이동 없이 작업만 종료된다
3. **Given** 이미 수락된 작업(ASSIGNED)이 있을 때, **When** 의뢰자가 취소를 시도하면, **Then** 거부된다
4. **Given** 예치된 작업이 있을 때, **When** 의뢰자가 아닌 사람이 취소를 시도하면, **Then** 거부된다

---

### User Story 2 - 잠수한 공급자에게서 대금을 되찾는다 (Priority: P2)

공급자가 일감을 수락해 놓고 결과를 제출하지 않는다. 시한이 지나면 의뢰자가 예치금을 돌려받는다.

**Why this priority**: 취소와 달리 상대가 이미 개입한 상태라 판정 기준이 필요하다. P1 이 없으면 이 경로도 의미가 약해지므로 뒤에 둔다.

**Independent Test**: 수락까지 진행한 뒤 시간을 시한 너머로 옮기고 정산을 호출해, 의뢰자에게 환불되는 것으로 검증한다.

**Acceptance Scenarios**:

1. **Given** 수락된 작업(ASSIGNED)의 제출 시한이 지났을 때, **When** 누군가 정산을 호출하면, **Then** 예치금이 의뢰자에게 환불되고 작업이 종료된다
2. **Given** 수락된 작업의 시한이 아직 남았을 때, **When** 정산을 호출하면, **Then** 거부된다
3. **Given** 시한이 지난 작업이 있을 때, **When** 당사자가 아닌 제3자가 정산을 호출하면, **Then** 당사자가 호출한 것과 같은 결과가 나온다

---

### User Story 3 - 승인하지 않는 의뢰자로부터 대금을 받아낸다 (Priority: P3)

공급자가 결과를 제출했는데 의뢰자가 승인도 이의 제기도 하지 않는다. 시한이 지나면 공급자가 대금을 받는다.

**Why this priority**: 공급자 보호 장치다. 세 경로 중 발생 빈도가 가장 낮고, 이의 제기 기능이 붙으면 의미가 달라질 수 있어 마지막에 둔다.

**Independent Test**: 제출까지 진행한 뒤 시간을 승인 시한 너머로 옮기고 정산을 호출해, 공급자에게 지급되는 것으로 검증한다.

**Acceptance Scenarios**:

1. **Given** 제출된 작업(SUBMITTED)의 승인 시한이 지났을 때, **When** 누군가 정산을 호출하면, **Then** 대금이 공급자에게 지급되고 작업이 완료된다
2. **Given** 제출된 작업의 시한이 아직 남았을 때, **When** 정산을 호출하면, **Then** 거부된다

---

### Edge Cases

- 시한 경계에서 정확히 같은 시각일 때 통과인가 거부인가
- 이미 종료된 작업에 취소나 정산을 다시 호출하면 거부되어야 한다
- 취소와 정산이 같은 블록에 들어오면 먼저 처리된 쪽이 이기고 나머지는 거부되어야 한다
- 토큰 전송이 실패하면 상태 변경까지 함께 되돌아가야 한다
- 존재하지 않는 작업 번호로 호출하면 거부되어야 한다
- 수락 직후 시한이 걸리기 전에 정산을 호출하는 경우

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 의뢰자는 수락되기 전의 작업을 취소하고 예치된 대금 전액을 돌려받을 수 있어야 한다
- **FR-002**: 취소는 의뢰자만 호출할 수 있어야 하며, 수락된 이후에는 거부되어야 한다
- **FR-003**: 모든 대기 상태에는 시한이 있어야 하며, 시한이 지나면 자금이 회수되는 경로가 존재해야 한다 *(헌법 원칙 II)*
- **FR-004**: 시한 경과 처리는 컨트랙트가 시한을 직접 검사해, 누가 호출하든 같은 결과를 내야 한다
- **FR-005**: 공급자가 제출 시한을 넘기면 예치금이 의뢰자에게 환불되어야 한다
- **FR-006**: 의뢰자가 승인 시한을 넘기면 예치금이 공급자에게 지급되어야 한다
- **FR-007**: 종료된 작업은 어떤 경로로도 다시 정산되지 않아야 한다
- **FR-008**: 모든 종료 경로에서 그 작업 몫의 에스크로 잔액이 0 이 되어야 한다 *(헌법 원칙 I)*
- **FR-009**: 취소와 시한 정산은 각각 이벤트를 발생시켜, 외부 시스템이 종료 사유를 구분할 수 있어야 한다
- **FR-010**: 자금이 이동하는 모든 새 경로는 상태를 먼저 바꾼 뒤 토큰을 보내야 한다 *(헌법 원칙 III)*
- **FR-011**: 시한의 기준 시각은 [NEEDS CLARIFICATION: 블록 타임스탬프인가 블록 번호인가. 그리고 기산점이 예치 시점인가 수락 시점인가 제출 시점인가]
- **FR-012**: 시한 경과 처리의 호출 권한은 [NEEDS CLARIFICATION: 헌법 원칙 II 와 설계 문서는 "누구나" 를 요구하지만, 블록체인 담당자가 미확정으로 분류함. 누구나인가, 당사자 둘로 제한하는가]
- **FR-013**: 수락 후 미제출 상태에서 시한이 지났을 때의 정산 방향은 [NEEDS CLARIFICATION: 설계확정 3-2-b 는 의뢰자 환불로 잡았으나, 블록체인 담당자가 공급자 지급 가능성도 열어 둠]

### Key Entities

- **작업(Job)** — 당사자 둘, 대금, 현재 상태, 그리고 현재 상태의 시한을 가진다. 시한은 상태가 바뀔 때마다 갱신된다
- **시한 정책** — 상태별로 얼마의 시간을 허용할지 정하는 값. 배포 시점에 정해지며 작업마다 달라지지 않는다
- **종료 사유** — 승인, 취소, 미제출 만료, 미승인 만료 넷을 외부에서 구분할 수 있어야 한다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 대기 상태 셋(`FUNDED`, `ASSIGNED`, `SUBMITTED`) 모두에서 자금 회수 경로가 존재한다. 헌법 활성 예외 EX-1 이 닫힌다
- **SC-002**: 종료 경로 넷 전부에서 의뢰자 지출과 수령자 수령의 합이 일치하고, 정산 후 에스크로 잔액이 0 이 된다
- **SC-003**: 당사자가 아닌 제3자가 시한 정산을 호출해도 결과가 같다 *(FR-012 확정에 따름)*
- **SC-004**: 체인 가드(`SsafyDeploymentBlocked`)와 그 테스트가 제거되고, SSAFY 체인 배포가 가능한 상태가 된다
- **SC-005**: 시한 경계 조건이 Solidity 단위 테스트로 검증되고, 취소와 두 만료 경로가 각각 E2E 한 건씩을 가진다

## Assumptions

- **1단계 범위다.** 공급자 담보는 0 이고 소각분과 플랫폼 수수료가 없다. 대금 전액이 한쪽으로 간다
- **이의 제기와 판정은 범위 밖이다.** `raiseDispute`·`submitVerdict`·`VERIFYING`·`SLASHED` 는 별도 작업에서 다룬다
- **결제 토큰은 GCoin(GSC, decimals 18)이다.** 컨트랙트는 생성자에서 주소를 받으므로 토큰에 종속되지 않는다
- **시한 값은 배포 인자로 받는다.** 현재 버전에서 제거했던 생성자 인자를 되살리되, 실제 값은 배포 시점에 정한다
- **테스트 계층은 확정된 방침을 따른다.** 조건 하나는 Solidity 단위 테스트, 전체 흐름만 TypeScript E2E 에 둔다
- **이벤트 시그니처를 지금 확정한다.** 이 작업 이후 SSAFY 체인 배포가 열리므로, 여기서 정한 이벤트가 백엔드 연동의 기준이 된다
