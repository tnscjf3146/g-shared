# GPU 분산 서비스와 블록체인 결합 연구 노트

> 주제: 서로 다른 GPU 노드를 블록체인 기반의 하나의 분산 컴퓨팅 네트워크로 구성할 수 있는가?
>
> 작성일: 2026-08-28

## 1. 문제 정의

목표는 단순히 GPU 사용료를 토큰으로 결제하는 서비스가 아니다. 서로 신뢰하지 않는 GPU 노드들이 네트워크에 자율적으로 참가하고, 작업을 나누어 수행하며, 어떤 계산 결과가 올바른지 공동으로 결정하는 시스템을 구상한다.

여기서 먼저 구분해야 할 개념은 다음과 같다.

- **GPU 간 연결**: 텐서, 모델, gradient, activation 등을 실제로 전송하는 통신
- **분산 작업 조정**: 어떤 GPU가 어떤 계산을 맡는지 정하는 과정
- **결과 합의**: 여러 GPU가 제출한 결과 중 무엇을 공식 결과로 인정할지 정하는 과정
- **경제적 보안**: 정직한 계산에는 보상하고 부정행위에는 불이익을 주는 구조

블록체인은 첫 번째인 데이터 통신에는 적합하지 않다. 그러나 나머지 세 가지를 신뢰할 중앙 운영자 없이 처리하려는 경우에는 핵심 프로토콜이 될 수 있다.

## 2. 가장 중요한 결론

**블록체인은 GPU를 물리적으로 연결하는 네트워크가 아니라, GPU 계산의 상태와 정당성을 합의하는 분산 상태 머신으로 사용해야 한다.**

블록체인 노드도 실제 통신에는 TCP, QUIC, libp2p 같은 네트워크를 사용한다. 따라서 “GPU를 블록체인으로 연결한다”는 표현을 기술적으로 풀면 다음과 같다.

> GPU 노드들이 P2P로 계산 데이터를 교환하고, 블록체인을 통해 작업 배정·계산 증명·결과 확정·보상을 합의한다.

블록체인을 제거해도 중앙 DB나 스케줄러로 동일한 신뢰 수준을 제공할 수 있다면 블록체인을 사용할 이유가 없다. 반대로 참여자들이 서로를 신뢰하지 않고, 누구나 허가 없이 참여하며, 단일 운영자 없이 계산 결과를 확정해야 한다면 블록체인의 역할이 생긴다.

## 3. 블록체인이 불필요한 경우

다음 조건에서는 Kubernetes, Ray, Slurm, PyTorch Distributed 또는 일반적인 P2P 시스템이 더 적합하다.

- 모든 GPU를 한 회사 또는 신뢰 가능한 조직이 운영하는 경우
- GPU 노드의 가입과 퇴출을 중앙 관리자가 통제하는 경우
- 작업 결과를 중앙 서버가 최종 판정해도 되는 경우
- 결제와 정산을 기존 결제 시스템으로 처리할 수 있는 경우
- 지연 시간이 매우 중요한 학습 루프에 글로벌 합의를 넣으려는 경우

온체인 노드 목록, 단순 에스크로, 사용량 기록만 추가한 구조는 블록체인이 없어도 구현할 수 있다. 이 경우 블록체인은 비싼 레지스트리나 결제 DB가 되기 쉽다.

## 4. 블록체인이 필요한 조건

블록체인을 정당화하려면 적어도 다음 문제 중 하나를 본질적으로 해결해야 한다.

1. **공통 상태:** 중앙 운영자 없이 모든 참여자가 동일한 작업 상태를 공유해야 한다.
2. **결과 확정:** 서로 불신하는 GPU들이 어느 계산 결과를 공식 결과로 인정할지 합의해야 한다.
3. **Sybil 저항성:** 공격자가 가짜 GPU 노드를 대량 생성하여 작업이나 검증을 장악하는 것을 막아야 한다.
4. **경제적 보안:** 거짓 결과를 제출했을 때 예치 자산을 삭감하고 정직한 계산을 보상해야 한다.
5. **무허가 참여:** 특정 회사의 허가 없이 GPU 제공자와 사용자가 네트워크에 참여할 수 있어야 한다.
6. **검열 저항성:** 특정 운영자가 작업 제출이나 결과 확정을 임의로 차단할 수 없어야 한다.

## 5. 제안 구조: GPU 계산을 실행 계층으로 사용하는 체인

GPU 서버마다 호스트 프로세스인 `GPU Agent`를 실행한다. GPU 자체가 지갑이나 네트워크 스택을 직접 구동하는 것이 아니라, 에이전트가 GPU를 대표하여 서명·통신·작업 실행을 담당한다.

### 구성요소

| 구성요소 | 역할 |
| --- | --- |
| GPU Agent | GPU 자원 탐지, 작업 실행, 결과 서명, P2P 통신 |
| P2P Network | 모델, 입력, 텐서, checkpoint 등 대용량 데이터 전송 |
| Blockchain | 작업 상태, 노드 지분, 계산 commitment, 검증 결과 합의 |
| Scheduler/Matcher | 작업 요구사항에 맞는 GPU 후보 선정 |
| Validator Committee | 작업 결과 검증 및 attestations 제출 |
| Storage Layer | 모델과 데이터 저장; content hash로 무결성 확인 |
| Smart Contract/Runtime | 작업 상태 전이, 보상, 분쟁, slashing 집행 |

### 블록체인 네이티브 모델

- **GPU 노드:** 계산 작업자이자 필요에 따라 검증자
- **트랜잭션:** 계산 작업 요청 또는 작업 상태 변경 요청
- **블록:** 작업 배정, 계산 commitment, 검증 서명, 분쟁 결과의 묶음
- **합의:** 어떤 계산 결과와 상태 전이를 유효하다고 인정할지 결정
- **보상:** 확정된 유효 계산에 대해 지급
- **Slashing:** 거짓 계산, 이중 서명, 데이터 미제공 등에 대한 패널티

## 6. 작업 상태 모델

하나의 계산 작업은 다음 상태를 가진다.

```text
Submitted
  -> Assigned
  -> Running
  -> Committed
  -> Verified | Challenged
  -> Finalized | Rejected
```

각 상태의 의미는 다음과 같다.

| 상태 | 의미 |
| --- | --- |
| Submitted | 사용자가 작업 사양과 입력 commitment를 제출함 |
| Assigned | 프로토콜이 작업자 또는 작업자 위원회를 선택함 |
| Running | GPU가 오프체인에서 계산 중임 |
| Committed | 작업자가 결과 hash 또는 Merkle root를 제출함 |
| Verified | 검증 조건과 정족수를 충족함 |
| Challenged | 다른 노드가 결과에 이의를 제기함 |
| Finalized | 결과가 공식 상태로 확정되고 보상이 지급됨 |
| Rejected | 거짓 결과로 판정되고 패널티가 집행됨 |

중요한 점은 **블록체인 합의가 매번 GPU kernel 실행 사이에 들어가면 안 된다는 것**이다. 학습 step이나 추론 token마다 합의하면 지연 시간과 비용 때문에 실용성이 사라진다. 합의는 작업, epoch, checkpoint 또는 검증 가능한 큰 단위의 경계에서 수행해야 한다.

## 7. 온체인과 오프체인 데이터 구분

### 온체인에 기록할 데이터

```text
job_id
requester_id
model_hash
input_commitment
execution_spec_hash
worker_ids
result_commitment
checkpoint_root
validator_attestations
challenge_deadline
final_status
reward_and_penalty
```

### 오프체인에서 전송할 데이터

- 모델 weight
- 학습 데이터와 추론 입력
- gradient와 activation
- 중간 tensor
- 전체 checkpoint
- 로그와 상세 실행 trace
- 최종 결과 원본

체인에는 원본 데이터 대신 content hash, Merkle root, 서명, proof를 기록한다. 원본을 온체인에 넣으면 비용, 처리량, 개인정보 보호 문제가 발생한다.

## 8. GPU 간 실제 통신

블록체인은 데이터 전송 계층이 아니므로 계산 목적에 맞는 별도 채널이 필요하다.

| 사용 사례 | 적합한 통신 방식 |
| --- | --- |
| 동일 데이터센터의 분산 학습 | NCCL, NVLink, InfiniBand, RDMA |
| 인터넷상의 GPU 노드 | QUIC, gRPC, libp2p |
| 독립적인 추론 작업 분배 | RPC, 메시지 큐, P2P task protocol |
| Pipeline parallelism | 지속적인 저지연 RPC 스트림 |
| 모델·checkpoint 배포 | Content-addressed storage, object storage, P2P distribution |

인터넷에 흩어진 GPU는 데이터센터 GPU처럼 동작하지 않는다. 높은 지연 시간, 낮은 대역폭, 노드 이탈 때문에 tight synchronous training보다 독립 작업, 비동기 학습, 전문가 모델 라우팅, 렌더링 또는 batch inference가 초기 사용 사례로 더 현실적이다.

## 9. Proof of Useful Compute 아이디어

기존 Proof of Work의 해시 계산 대신 실제 GPU 작업을 네트워크 보안 또는 블록 생성과 연결하는 접근이다.

가능한 흐름은 다음과 같다.

1. 사용자가 검증 가능한 계산 작업을 제출한다.
2. 프로토콜이 stake, 성능, 평판, 무작위성을 기준으로 작업자를 선택한다.
3. 작업자가 GPU 계산을 수행하고 결과 commitment를 제출한다.
4. 무작위 검증자들이 전체 또는 일부 계산을 다시 실행한다.
5. 검증 정족수를 충족한 결과만 체인 상태로 확정한다.
6. 유효 계산은 보상하고 거짓 결과는 stake를 삭감한다.
7. 확정된 출력은 후속 작업의 입력 commitment가 될 수 있다.

그러나 `Proof of Useful Compute`에는 근본적인 문제가 있다.

- 계산이 실제로 수행되었는지 저렴하게 검증하기 어렵다.
- 검증자가 전체 계산을 다시 하면 계산 비용이 중복된다.
- AI 연산은 하드웨어와 정밀도에 따라 결과가 조금씩 달라질 수 있다.
- 유용한 작업의 수요가 블록 생성 주기와 항상 일치하지 않는다.
- 작업 난이도를 합의 알고리즘에 맞게 정규화하기 어렵다.
- 공격자가 검증자와 작업자를 동시에 장악할 수 있다.

따라서 “유용한 계산량이 많으면 바로 블록을 생성한다”는 단순 설계보다, 기존 PoS 합의 위에 검증된 GPU 계산 시장 또는 계산 상태 머신을 올리는 방식이 초기 구현에는 더 현실적이다.

## 10. 계산 검증 방법

GPU 네트워크의 핵심 난제는 계산 수행이 아니라 **결과 검증**이다.

| 방법 | 장점 | 단점 | 적합한 용도 |
| --- | --- | --- | --- |
| 중복 실행 | 구현이 단순함 | 비용이 2배 이상 증가 | 결정론적·고가치 작업 |
| 무작위 샘플 검증 | 비용을 줄일 수 있음 | 전체 부정행위를 놓칠 수 있음 | 큰 작업의 부분 검사 |
| Optimistic challenge | 정상 상황에서 저렴함 | 분쟁 해결이 느림 | 배치 작업 |
| TEE 원격 증명 | 실행 환경을 증명 가능 | 하드웨어 신뢰와 취약점 의존 | 비공개 모델·데이터 |
| zkML | 강한 암호학적 검증 | proof 생성 비용과 모델 제약 | 고가치 결정론적 추론 |
| 결과 다수결 | 이해하기 쉬움 | 담합과 Sybil 공격에 취약 | stake 기반 위원회와 결합 |
| 평판 시스템 | 반복 참여에서 효과적 | 신규 노드 평가와 조작 문제 | 보조 신뢰 신호 |

현실적인 초기 조합은 다음과 같다.

> Stake + 무작위 작업자 선정 + 결과 commitment + 일부 중복 실행 + challenge window + slashing

TEE나 zkML은 모든 작업의 기본값보다 특정 보안 등급의 작업에 선택적으로 적용하는 편이 적합하다.

## 11. 학습과 추론에서의 차이

### 독립 추론 작업

노드별 작업이 독립적이므로 네트워크 지연의 영향을 덜 받는다. 결과 검증도 같은 입력을 소수 노드에 재실행하여 비교할 수 있다. 초기 MVP에 가장 적합한 형태다.

### 하나의 모델을 여러 GPU로 분할한 추론

GPU 사이에 activation을 지속적으로 전송해야 하므로 지연 시간과 노드 안정성이 중요하다. 인터넷상의 임의 노드로 구성하기 어렵고, 가까운 노드끼리 서브클러스터를 구성해야 한다.

### 분산 학습

gradient 교환량이 많고 느린 노드 하나가 전체 학습을 지연시킬 수 있다. 비동기 학습, local SGD, federated learning, Mixture-of-Experts처럼 통신 빈도를 줄이는 알고리즘이 필요하다. 체인에는 step마다 기록하지 않고 epoch 또는 checkpoint 단위로 commitment를 올려야 한다.

## 12. 현실적인 MVP 제안

첫 버전은 “블록체인이 GPU를 빠르게 묶어 하나의 거대한 GPU처럼 동작시킨다”보다, **서로 불신하는 GPU들이 독립적인 결정론적 작업을 수행하고 결과를 합의하는 네트워크**로 범위를 제한하는 것이 좋다.

### MVP 범위

- 작업 유형: deterministic image rendering, 특정 버전의 모델 batch inference 또는 검증 가능한 행렬 연산
- 노드: GPU Agent가 설치된 5~20개 서버
- 체인: 기존 PoS 체인의 스마트 컨트랙트 또는 간단한 app-chain
- 데이터: 오프체인 object storage/P2P, 체인에는 hash만 기록
- 검증: 두 작업자의 중복 실행과 제3 검증자의 분쟁 판정
- 보안: stake, timeout, 결과 불일치 slashing
- 확정 단위: 개별 batch 또는 checkpoint

### MVP에서 확인할 핵심 지표

- 작업 완료 시간 대비 합의 지연 시간
- 중복 검증으로 추가되는 GPU 비용
- 정상 노드와 악성 노드의 판별 정확도
- 노드 이탈 시 작업 복구 시간
- 네트워크 전송량과 GPU 실제 활용률
- 한 작업당 온체인 비용
- 결과의 결정성 및 허용오차 설정 가능 여부

## 13. 설계 시 피해야 할 패턴

- 학습 step 또는 추론 token마다 온체인 트랜잭션 생성
- 모델, 입력, gradient, 결과 원본을 체인에 저장
- 결과 hash만 제출하면 계산이 올바르다고 간주
- GPU 모델명과 자체 보고 성능을 검증 없이 신뢰
- 지리적으로 먼 GPU를 동기식 NCCL 클러스터처럼 취급
- 토큰 보상만으로 유용한 작업 수요가 자동으로 생긴다고 가정
- 작업자와 검증자를 같은 주체가 자유롭게 생성하도록 허용
- 체인이 멈추면 진행 중인 계산까지 즉시 실패하도록 강결합

## 15. 최종 정리

GPU 통신 자체를 블록체인으로 처리하는 것은 성능상 적절하지 않다. 실제 데이터는 P2P 또는 고성능 GPU 통신 기술로 전송해야 한다.

블록체인의 핵심 역할은 다음 한 문장으로 정리할 수 있다.

> **서로 신뢰하지 않는 GPU 노드들이 계산 작업의 배정, 수행 증명, 결과 확정과 보상을 하나의 검증 가능한 상태 전이로 합의하게 한다.**

이 역할까지 필요하지 않다면 블록체인을 제거하는 것이 옳다. 이 역할이 제품의 핵심이라면 GPU 계산 결과를 어떻게 저렴하고 신뢰성 있게 검증할지가 전체 프로젝트의 가장 중요한 연구 과제가 된다.
