## 1. Jira 협업 관리

### 1-1. 이슈 계층 구조

Jira 이슈 타입은 3단 구조로 되어 있다.

```
Epic                    ← 상위 (기능 덩어리)
  ├─ Story    ┐
  ├─ Task     ├─ 표준 레벨 (서로 형제 관계)
  └─ Bug      ┘
       └─ Sub-task      ← 하위 항목
```

가장 많이 오해하는 지점이 **Story와 Task의 관계**다. 둘은 상하 관계가 아니라 **형제**이며, 모두 Epic 밑에 나란히 붙는 같은 레벨이다. 따라서 하위 항목(Sub-task)을 쓰지 않아도 `Epic → Story/Task` 2계층만으로 구조가 성립한다.

**하위 항목을 쓰지 않는 구성의 장단점**

| | 내용 |
|---|---|
| 장점 | 계층이 얕아 관리 비용이 낮음 / 모든 작업이 보드에 카드로 노출됨 / 스토리 포인트·번다운 집계가 단순해짐 |
| 단점 | 이슈 하나가 커지면 진행 상황을 세분화해 표현할 방법이 없음 |
| 대응 | 아래 규칙으로 단점을 상쇄한다 |

> **핵심 규칙**
> "이건 하위 항목으로 쪼개야겠는데?" 싶은 순간 = **그 이슈가 너무 크다는 신호.**
> 하위 항목을 만들지 말고, **스토리를 더 잘게 쪼개거나 형제 Task로 분리해** 같은 Epic에 붙인다.

이 규칙이 성립하는 이유는, 하위 항목이 필요할 만큼 큰 이슈는 애초에 스프린트 단위 추정이 불가능한 크기이기 때문이다. 하위 항목은 큰 이슈를 관리 가능하게 만들어주는 게 아니라 **큰 이슈를 큰 채로 유지시키는 도구**에 가깝다.

### 1-2. 에픽 / 스토리 / 태스크 구분 기준

| | Epic | Story | Task |
|---|---|---|---|
| 정의 | 하나의 기능 영역·목표 | **사용자에게 가치가 전달되는** 최소 단위 | 사용자 가치는 없지만 **해야 하는** 작업 |
| 관점 | 제품 | 사용자 | 개발자 |
| 크기 | 1~3주, 스토리 5~15개 | **1~3일** (포인트 1~5) | 반나절~2일 |
| 완료 판정 | 하위 스토리 전부 Done | 사용자가 그 행동을 실제로 할 수 있음 | 산출물이 존재함 |
| 예시 | `[주문] 주문 생성 및 결제` | `구매자가 장바구니 상품을 주문할 수 있다` | `결제 PG사 샌드박스 연동 환경 구성` |

**판별 질문 3개**

1. "이걸 완료하면 사용자가 새로 뭘 할 수 있나?" → 답이 있으면 **Story**, 없으면 **Task**
2. "3일 안에 혼자 끝낼 수 있나?" → 아니면 쪼개거나 Epic으로 승격
3. "데모에서 보여줄 수 있나?" → 보여줄 수 있으면 Story 성격

**헷갈리는 케이스**

- **API와 화면을 따로 이슈로 만들까?**
  원칙적으로는 나누지 않는다. `구매자가 상품을 주문할 수 있다` 하나의 스토리로 묶고 백엔드·프론트가 함께 붙는 것이 스토리의 정의("사용자 가치의 최소 단위")에 맞다. 다만 파트가 완전히 분리된 조직에서는 분리하기도 하며, 이때는 **라벨로 파트를 구분하고 Epic으로 묶어** 추적해야 연결이 끊기지 않는다.
- **학습·조사·POC** → **Task**
- **인프라·개발 환경·CI/CD** → **Task**
- **버그** → 스프린트 중 발견된 건은 Bug 타입. 타입을 단순화하려면 Task로 통일해도 무방하다.

### 1-3. 이슈 작성 템플릿

**제목 규칙**

```
Epic   : [영역] 명사구
         예) [주문] 주문 생성 및 결제

Story  : (역할)로서 (행동)할 수 있다
         예) 구매자로서 장바구니의 상품을 한 번에 주문할 수 있다

Task   : 동사로 끝나는 작업 서술
         예) CI 파이프라인에 무중단 배포 스크립트 연동
```

**본문 (Story 기준)**

```markdown
## 배경
장바구니에 담은 상품을 개별 주문해야 해서 이탈률이 높다.

## 완료 조건 (AC)
- [ ] 장바구니에서 선택한 상품들을 하나의 주문으로 생성할 수 있다
- [ ] 재고가 부족한 상품이 있으면 주문 생성이 실패하고 해당 상품을 안내한다
- [ ] 주문 생성 성공 시 장바구니에서 해당 상품이 제거된다
- [ ] 결제 실패 시 주문은 '결제대기' 상태로 남는다
```

- **AC(Acceptance Criteria)가 핵심.** AC가 없는 스토리는 "언제 끝난 것인지"에 대한 합의가 없어서 리뷰 단계마다 해석 충돌이 생긴다. 3~5개면 충분하다.
- 체크박스로 작성하면 **리뷰어가 그대로 검수 체크리스트로 재사용**할 수 있다.

**주요 필드**

| 필드 | 이유 |
|---|---|
| 담당자 | 담당자 없는 이슈는 아무도 진행하지 않는다 |
| 스프린트 | 현재 스프린트 것만 보드에 노출 |
| 스토리 포인트 | 피보나치 `1, 2, 3, 5, 8` — **8을 넘으면 쪼갠다** |
| 라벨 | 파트·영역별 필터링용 (`BE` `FE` `INFRA` 등) |

> 스토리 포인트를 시간으로 환산하지 않는다(`3포인트 = 3시간`). 환산하는 순간 추정치가 아니라 약속이 되고, 추정이 보수적으로 왜곡된다. 포인트는 **다른 이슈 대비 상대 크기**로만 쓴다.

### 1-4. 커밋 · 브랜치 · MR 연결

**대전제: Jira 이슈 키를 모든 산출물에 남긴다.** Jira가 이슈에 부여하는 키(`PROJ-42` 형태)가 이슈 ↔ 코드를 잇는 유일한 열쇠다.

```
Jira 이슈 생성 (PROJ-42)
    ↓
브랜치 생성   : feat/PROJ-42-order-create
    ↓
커밋          : [feat] 장바구니 일괄 주문 API 구현 (PROJ-42)
    ↓
MR 제목       : [feat] 장바구니 일괄 주문 (PROJ-42)
MR 설명       : Closes PROJ-42
    ↓
머지 → Jira 이슈 Done
```

| 위치 | 형식 | 예시 |
|---|---|---|
| 브랜치 | `<타입>/<이슈키>-<영문요약>` | `feat/PROJ-42-order-create` |
| 커밋 | `[타입] 한글 요약 (이슈키)` | `[feat] 장바구니 일괄 주문 API 구현 (PROJ-42)` |
| MR 제목 | 커밋과 동일 형식 | `[feat] 장바구니 일괄 주문 (PROJ-42)` |
| MR 설명 | `Closes <이슈키>` 한 줄 포함 | `Closes PROJ-42` |

브랜치명에 이슈 키를 넣어두면 그 브랜치에서 만든 커밋·MR에 자연스럽게 키가 따라붙기 때문에, **이슈 키 누락을 막는 가장 효과적인 지점은 브랜치 생성 시점**이다.

**GitLab ↔ Jira 연동으로 되는 것과 안 되는 것**

`Settings → Integrations → Jira`에서 연동을 설정하면(Maintainer 권한 + Jira API 토큰 필요):

- ✅ 커밋/MR에 이슈 키를 쓰면 **GitLab 화면에서 Jira 이슈로 자동 하이퍼링크**
- ✅ **Jira 이슈에 해당 커밋·MR 링크가 댓글로 자동 등록** → 이슈만 보면 어떤 코드가 나갔는지 추적 가능
- ✅ `Closes` / `Resolves` / `Fixes` + 이슈 키를 커밋이나 MR에 쓰고 **기본 브랜치에 머지되면 Jira 이슈 자동 종료**
- ❌ Atlassian의 정식 **Smart Commits 문법**(`#comment 내용`, `#time 2h`, `#done`)은 **Bitbucket·GitHub 전용이며 GitLab에서는 동작하지 않는다.** GitLab 공식 문서가 한동안 "Smart Commit 지원"으로 모호하게 표기해 혼동이 있었던 부분이다. GitLab이 지원하는 것은 **① 이슈 키 언급 → 링크 생성, ② close 키워드 → 이슈 종료** 두 가지뿐이다.

연동이 불가능한 환경(사내망 정책, 권한 부족 등)이라면 자동 링크는 포기하고 **네이밍 규칙만 수기로 지켜도 된다.** 커밋 메시지에 이슈 키가 남아 있으면 `git log --grep="PROJ-42"`로 언제든 역추적이 가능하므로 실용적 목적은 대부분 달성된다.

### 1-5. 스프린트 운영 (1주 기준)

```
[월] 스프린트 플래닝
     - 지난 스프린트 미완료 이슈 처리 (이월 or 폐기)
     - 이번 스프린트 스토리 선정 → 담당자·포인트 배정
     - 소화 가능 포인트 = 인원 × 1주 소화량
       (첫 스프린트는 추정, 2회차부터는 직전 실측치를 사용 — 이걸 velocity라 한다)

[매일] 데일리 스크럼 10분
     - "어제 한 것 / 오늘 할 것 / 막힌 것"
     - 이슈 상태를 각자 직접 이동

[주말] 회고
     - 번다운 차트로 추정 정확도 확인
     - Keep / Problem / Try
```

**상태 컬럼은 4개면 충분**

```
To Do → In Progress → In Review → Done
```

`In Review`(MR을 올린 상태)를 별도 컬럼으로 두는 것이 중요하다. MR은 올렸는데 리뷰가 붙지 않아 멈춘 작업이 `In Progress`에 섞여 있으면, 병목이 "개발이 느린 것"인지 "리뷰가 안 붙는 것"인지 구분되지 않는다.

### 1-6. 에픽 분해 예시

이슈 계층을 실제로 잡아보면 이런 형태가 된다.

```
Epic  [주문] 주문 생성 및 결제
 ├─ Story  구매자가 장바구니 상품을 한 번에 주문할 수 있다        (5)
 ├─ Story  구매자가 주문 내역과 상태를 조회할 수 있다              (3)
 ├─ Story  구매자가 결제 완료 전 주문을 취소할 수 있다             (2)
 ├─ Task   결제 PG사 샌드박스 연동 환경 구성                      (2)
 └─ Task   주문 상태 전이 다이어그램 정의                         (1)
```

- Story는 전부 "사용자가 ~할 수 있다"로 읽히고, Task는 그렇지 않다.
- 포인트 합(13)이 Epic의 크기가 되고, 이 값으로 Epic 단위 진척률을 볼 수 있다.
- 조사·환경 구성처럼 사용자 가치가 없지만 반드시 필요한 작업이 Task로 같은 Epic 안에 들어간다. 이걸 이슈로 안 만들면 실제로 쓴 시간이 어디에도 기록되지 않아 velocity가 계속 부정확해진다.

### 1-7. 안티패턴

| 안티패턴 | 문제 | 대안 |
|---|---|---|
| 이슈가 `백엔드 개발` 하나 | 끝날 때까지 In Progress, 진척 측정 불가 | Epic으로 올리고 스토리로 쪼갠다 |
| AC 없이 제목만 작성 | 완료 기준이 사람마다 달라 충돌 | AC 3~5개 필수 |
| 작업을 끝낸 뒤 이슈 생성 | Jira가 기록용 장부로 전락, 계획 도구 기능 상실 | 플래닝 시점에 미리 만든다 |
| 커밋에 이슈 키 누락 | 나중에 "이 코드를 왜 짰는지"를 추적 못 함 | 브랜치명에 넣어 자동으로 따라붙게 한다 |
| 포인트를 시간으로 환산 | 추정이 약속이 되어 보수적으로 왜곡됨 | 상대 크기로만 사용 |
| 이슈 상태를 한 사람이 몰아서 정리 | 보드가 실시간 현황을 반영하지 못함 | 각자 자기 이슈를 직접 이동 |

## 2. 무중단 배포 (Zero-Downtime Deployment)

### 2-1. 왜 필요한가

가장 단순한 배포(`프로세스 종료 → 새 코드 반영 → 재시작`)는 그 사이 수십 초~수 분 동안 **모든 요청이 실패**한다. 무중단 배포의 핵심 아이디어는 하나로 요약된다.

> **먼저 새 버전을 띄우고 → 준비 완료를 확인하고 → 트래픽을 옮기고 → 그다음 옛 버전을 내린다.**

"내리고 올린다"가 아니라 **"올리고, 옮기고, 내린다"** — 순서가 전부다.

### 2-2. 배포 전략 4가지

| 전략 | 방식 | 자원 | 롤백 | 특징 |
|---|---|---|---|---|
| **롤링(Rolling)** | N개 인스턴스를 1~2개씩 순차 교체 | 거의 추가 없음 | 느림 (다시 롤링) | 배포 중 구/신 버전 **공존** → API 하위 호환 필수 |
| **블루-그린** | 동일 환경 2벌 운영, LB를 통째로 전환 | **2배** | **즉시** (스위치 되돌리기) | 구현이 단순하고 검증 후 전환 가능 |
| **카나리** | 신버전에 트래픽 일부(5%)만 → 지표 확인 → 점진 확대 | 소폭 추가 | 빠름 | 위험 최소화. 트래픽 분배·모니터링 인프라 필요 |
| **A/B 테스트** | 사용자 그룹별로 다른 버전 노출 | 소폭 추가 | 빠름 | 목적이 배포가 아니라 **기능 반응 측정** |

전략 선택 기준을 한 줄로 정리하면:

- 인스턴스가 여러 대이고 자원 여유가 없다 → **롤링**
- 인스턴스가 1~2대이고 롤백 속도가 중요하다 → **블루-그린**
- 사용자 규모가 크고 장애 비용이 크다 → **카나리**

### 2-3. "무중단"의 전제조건 4가지

어떤 전략을 고르든 아래가 없으면 무중단이 아니라 **중단 시간이 짧아진 배포**일 뿐이다.

**① 헬스체크 (readiness probe)**

새 인스턴스가 떴다고 바로 트래픽을 주면 안 된다. 프로세스는 기동됐어도 DB 커넥션 풀 생성, 캐시 워밍업, 스프링 빈 초기화 등이 끝나지 않은 상태다. `/health` 같은 엔드포인트가 200을 반환할 때까지 폴링한 뒤에 트래픽을 붙인다.

> **liveness와 readiness의 구분**
> - *liveness* : "죽었나?" → 실패 시 **재시작**
> - *readiness* : "받을 준비가 됐나?" → 실패 시 **트래픽에서 제외**
> 무중단 배포에서 필요한 건 readiness다. 둘을 같은 엔드포인트로 쓰면, 일시적으로 바쁜 인스턴스를 재시작해버리는 사고가 난다.

**② Graceful Shutdown (우아한 종료)**

옛 인스턴스에 `SIGTERM`을 보내면 → **새 요청 수신은 즉시 중단하되, 이미 처리 중인 요청은 끝까지 마무리**한 뒤 종료해야 한다. 이 처리가 없으면 전환 순간 진행 중이던 요청이 전부 실패한다. 로드밸런서 쪽 용어로는 connection draining이라고 한다.

대부분의 프레임워크가 설정으로 지원한다 (예: Spring Boot의 `server.shutdown=graceful` + `spring.lifecycle.timeout-per-shutdown-phase`).

**③ DB 마이그레이션 하위 호환 — Expand & Contract 패턴**

배포 중에는 구/신 버전이 잠시 공존하므로, **한쪽 버전만 아는 스키마 변경은 반드시 장애를 낸다.** 컬럼명 변경을 예로 들면:

```
❌ 한 번에:  ALTER TABLE ... RENAME COLUMN old TO new;   → 구버전 즉시 사망

✅ 3단계로:
   1) Expand   : new 컬럼 추가 (구버전은 old, 신버전은 둘 다 사용)
   2) Migrate  : 데이터 복사 + 신버전 배포 완료
   3) Contract : 충분히 안정화된 뒤 old 컬럼 제거 (다음 배포에서)
```

핵심은 **파괴적 변경(rename, drop, not-null 추가)을 배포와 같은 시점에 하지 않는 것**이다. 배포 한 번에 끝내려는 욕심이 무중단을 깨뜨린다.

**④ 무상태(Stateless)**

세션을 서버 메모리에 들고 있으면 인스턴스를 내리는 순간 사용자 로그인이 풀린다. 세션은 Redis 등 외부 저장소로 분리하거나 JWT로 처리해 인스턴스가 아무 때나 교체 가능한 상태로 만들어야 한다. 로컬 파일 업로드 저장도 같은 이유로 외부 스토리지로 빼야 한다.

### 2-4. 블루-그린 구현 흐름 (Nginx + Docker, 서버 1대 기준)

```
                    ┌─ :8081  app-blue  (현재 운영)
사용자 → Nginx ─────┤
        (upstream)  └─ :8082  app-green (신규 배포)
```

배포 스크립트가 수행하는 일:

```
1. 현재 활성 포트 확인             (nginx conf 또는 health 응답으로 판별)
2. 비활성 포트에 새 컨테이너 기동    (docker compose up -d app-green)
3. 헬스체크 폴링                  (curl :8082/health 가 200 될 때까지, 최대 60초)
4. 실패 시 → 새 컨테이너만 종료하고 배포 중단 (운영 트래픽 무손실)
5. 성공 시 → upstream을 8082로 교체하고 nginx -s reload
6. 일정 시간 대기 후 옛 컨테이너 종료  (드레이닝 시간 확보)
```

- **핵심은 `nginx -s reload`.** Nginx는 reload 시 기존 워커 프로세스가 처리 중인 연결을 끝까지 유지한 채 새 설정의 워커로 교체하므로, 이 전환 과정 자체가 무중단이다. `nginx -s restart`가 아니라 `reload`여야 한다.
- **4번이 블루-그린의 진짜 가치다.** 헬스체크에 실패해도 운영 트래픽은 여전히 옛 버전이 받고 있으므로, 배포 실패가 장애로 이어지지 않는다.
- 쿠버네티스를 사용하면 이 로직을 직접 작성할 필요 없이 `Deployment`의 `RollingUpdate` 전략 + `readinessProbe` + `maxSurge`/`maxUnavailable` 설정으로 대체된다. 다만 인스턴스가 한두 대인 규모에서는 도입 비용이 더 크다.
- 이 스크립트를 CI/CD 파이프라인의 `deploy` 스테이지에 연결하면 `기본 브랜치 머지 → 자동 무중단 배포`가 완성된다.

### 2-5. 적용 시 자주 놓치는 지점

- **장시간 실행되는 배치·워커 프로세스**
  요청-응답이 수 초로 끝나는 API와 달리, 수십 분 이상 걸리는 작업을 처리하는 워커는 graceful shutdown 타임아웃(보통 30초)으로 감당이 안 된다. → 종료 신호를 받으면 **"신규 작업 수신만 중단"하는 드레이닝 모드**로 진입시키고, 진행 중인 작업은 상태를 외부에 저장한 채 완료까지 수행하도록 설계해야 한다.
- **WebSocket 등 지속 연결**
  배포로 연결이 끊기는 것은 원천적으로 피할 수 없다. → **클라이언트 측 자동 재연결 로직**이 사실상 무중단 구성의 일부가 된다.
- **롤백 시나리오를 배포보다 먼저 검증**
  배포 스크립트는 성공 경로만 테스트하기 쉽다. 헬스체크 실패, 전환 후 오류 발견 등 **되돌리는 경로를 실제로 한 번은 돌려봐야** 무중단이라 부를 수 있다.
