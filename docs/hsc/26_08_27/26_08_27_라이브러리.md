# 1. 메세지 큐 (Message Queue)

## 한 줄 정의

보내는 쪽과 받는 쪽 사이에 끼워 넣는 **"우편함"**. 직접 호출 대신 메시지를 넣어두고, 받는 쪽이 준비되면 꺼내 처리한다.

## 왜 쓰나

### 직접 호출(동기)의 문제

```
주문 서버 → (HTTP 호출) → 이메일 서버
```

- 이메일 서버가 죽으면 주문도 실패
- 이메일 발송 3초 걸리면 사용자도 3초 기다림
- 트래픽 몰리면 이메일 서버가 터짐

### 큐를 끼우면

```
주문 서버 → [큐] → 이메일 서버
```

| 효과 | 설명 |
|---|---|
| 비동기 | 주문 서버는 큐에 넣고 즉시 응답 |
| 버퍼링 | 이메일 서버 죽어도 메시지는 큐에 남아있음 |
| 부하 분산 | 이메일 서버가 자기 속도로 꺼내서 처리 |
| 결합도 낮춤 | 서로 상대방 주소/상태를 몰라도 됨 |

## 핵심 개념

| 용어 | 의미 |
|---|---|
| Producer | 메시지 넣는 쪽 |
| Consumer | 꺼내서 처리하는 쪽 |
| Broker | 큐를 관리하는 서버 (RabbitMQ, Kafka 등) |
| Ack | "처리 완료" 신호. 없으면 재전달 |
| DLQ | Dead Letter Queue. 계속 실패하는 메시지 격리 |

## 두 가지 모델

- **Point-to-Point (큐)**: 메시지 1개 → Consumer 1개만 처리. 작업 분배용.
- **Pub/Sub (토픽)**: 메시지 1개 → 구독자 전부 받음. 이벤트 전파용.

## 대표 도구

| 도구 | 특징 |
|---|---|
| **RabbitMQ** | 전통적 MQ. 라우팅 규칙 유연. 처리 후 메시지 삭제 |
| **Kafka** | 로그 기반. 메시지 보존(재처리 가능), 초고성능 스트리밍 |
| **Redis (List/Stream)** | 이미 Redis 쓰면 가볍게 시작 가능 |
| **SQS** | AWS 관리형. 서버 관리 안 함 |

## 주의할 점

1. **순서 보장 안 됨** (기본적으로). 순서 필요하면 파티션 키 등 추가 설계 필요
2. **중복 전달 가능** (at-least-once). Consumer는 **멱등**하게 만들어야 함 — 같은 메시지 두 번 받아도 결과가 같도록
3. **디버깅 어려움**. 흐름이 끊겨 있어서 추적이 힘들다
4. **인프라 하나 늘어남**. 큐 자체가 장애 지점

## 언제 쓰면 안 되나

- 즉시 결과가 필요한 요청 (로그인, 조회) → 그냥 동기 호출
- 트래픽 적고 서비스 1개 → 스레드 풀이나 백그라운드 작업으로 충분

> **큐가 정말 필요해지는 신호**
> "이 작업 때문에 API 응답이 느리다" / "재시도 로직을 직접 짜고 있다" / "피크 트래픽에 하위 서비스가 죽는다"

# 2. 시스템 성능 4대 지표

## 지표는 독립이 아니라 인과 사슬

```
처리량이 처리 능력을 넘어서면
  → 대기 작업 수 증가
    → 지연시간 증가
      → 타임아웃/오류 증가
```

지표를 하나씩 보는 게 아니라, **어디서 사슬이 끊어졌는지** 찾는 도구다.

---

## 2-1. 지연시간 (Latency)

**요청 1건이 끝나기까지 걸린 시간.** 사용자가 실제로 체감하는 값.

### 가장 중요한 원칙: 평균을 보지 마라

```
요청 100건: 99건이 10ms, 1건이 5000ms
→ 평균 60ms   ("괜찮네")
→ p99  5000ms ("1%의 사용자가 서비스를 못 쓰고 있음")
```

| 지표 | 의미 |
|---|---|
| p50 (중위값) | 전형적인 사용자 경험 |
| p95 / p99 | 문제가 실제로 드러나는 구간 |
| p99.9 | 헤비 유저 / 대용량 데이터 사용자. 보통 가장 중요한 고객 |

> 요청을 많이 하는 사용자일수록 느린 요청을 만날 확률이 올라간다. 그래서 꼬리(tail) 지연이 매출과 직결된다.

### 측정 시 주의

어디부터 어디까지인지 정의해야 한다. 서버 처리 시간만? 큐 대기 시간 포함? 네트워크 왕복 포함?
서버는 10ms인데 사용자는 3초 기다리는 상황이 흔하고, 그 차이가 대개 **큐 대기 시간**이다.

---

## 2-2. 처리량 (Throughput)

**단위 시간당 완료한 작업 수.** RPS(req/sec), TPS, msg/sec.

### 핵심 구분

- **도착률 (Arrival rate)** — 들어오는 양
- **처리율 (Service rate)** — 소화하는 양
- **용량 (Capacity)** — 소화 가능한 최대치

`도착률 > 처리율`이 지속되면 시스템은 반드시 무너진다.
잠깐은 큐가 버텨주지만, 큐는 **용량 부족을 시간으로 바꿔주는 장치**일 뿐 해결책이 아니다.

### 함정: 처리량 숫자만 높은 건 의미 없다

```
"초당 10,000건 처리!"  단, p99 지연 8초
→ 실제로는 아무도 못 쓰는 서비스
```

처리량은 **항상 지연시간과 함께** 봐야 한다.
"p99 200ms 이하를 유지하면서 낼 수 있는 최대 처리량" — 이게 진짜 용량이다.

---

## 2-3. 대기 작업 수 (Queue Depth / Backlog)

**아직 처리되지 않고 쌓여 있는 작업 수.**
4개 중 가장 저평가되면서, **가장 빠른 조기 경보**다.

지연시간과 오류율은 이미 사용자가 피해를 본 뒤에 올라간다.
대기 수는 **피해가 발생하기 전에** 올라간다.

### 절대값이 아니라 추세와 기울기

| 패턴 | 해석 |
|---|---|
| 낮게 유지, 0 근처 진동 | 정상. 여유 있음 |
| 올라갔다 내려옴 | 정상. 큐가 제 역할(버퍼링) 중 |
| 계속 우상향 | **위험.** 처리 능력 부족. 절대 자연 회복 안 됨 |
| 0에 딱 붙어 있음 | 과잉 프로비저닝일 수 있음 (비용 낭비) |

### 리틀의 법칙 (Little's Law)

세 지표를 하나로 묶는 공식:

```
평균 대기 작업 수 = 도착률 × 평균 체류시간
L = λ × W
```

실무 활용:

```
큐에 5,000건 쌓임, 처리량 초당 100건
→ 지금 들어온 요청의 대기시간 = 5000 / 100 = 50초
```

현재 대기 수만 알면 **앞으로 발생할 지연시간을 예측**할 수 있다.
대시보드에 대기 수를 안 걸어두면 이 예측을 못 한다.

### 측정 대상은 큐만이 아니다

스레드 풀 대기, DB 커넥션 풀 대기, 디스크 I/O 큐, 로드밸런서 백로그 전부 해당.

---

## 2-4. 오류 / 타임아웃 비율 (Error & Timeout Rate)

**실패한 요청의 비율.** 다른 3개와 성격이 다르다 —
앞의 셋은 "느리다"를 말하지만, 이건 **"이미 망가졌다"**를 말한다.

### 반드시 분리해서 봐라. 원인이 다르다

| 종류 | 의미 | 원인 |
|---|---|---|
| 오류 (5xx) | 처리를 시도했지만 실패 | 버그, 의존 서비스 장애, 리소스 고갈 |
| 타임아웃 | 시간 내에 응답 못 함 | **용량 부족.** 지연시간 문제의 최종 형태 |
| 4xx | 클라이언트 잘못 | 보통 성능 지표에서 제외 (단, 급증하면 배포 사고 신호) |

**타임아웃은 독립 지표가 아니다.** 지연시간 분포의 꼬리가 타임아웃 임계값을 넘어간 결과다.
그래서 타임아웃이 늘면 반드시 대기 수를 확인해야 한다.

### 가장 위험한 패턴 — 재시도 폭풍 (Retry Storm)

```
느려짐 → 타임아웃 → 클라이언트 재시도 → 부하 2배
→ 더 느려짐 → 더 많은 타임아웃 → 부하 4배 → 전면 장애
```

타임아웃과 재시도는 시스템을 구하려는 장치인데, 잘못 설정하면 장애를 **가속**시킨다.
그래서 지수 백오프 + 지터, 서킷 브레이커가 필요하다.

---

## 2-5. 조합해서 읽는 방법

| 지연 | 처리량 | 대기 수 | 오류 | 진단 |
|:---:|:---:|:---:|:---:|---|
| ↑ | → | ↑ | → | **용량 부족.** 스케일 아웃 또는 처리 최적화 |
| ↑ | ↓ | ↑ | ↑ | **포화 / 붕괴 진행 중.** 부하 차단(shed) 필요 |
| ↑ | → | → | → | **의존 서비스 지연.** 내 시스템이 아니라 하위가 느림 |
| → | ↓ | → | ↑ | **기능 장애.** 배포 롤백 검토. 용량 문제 아님 |
| ↓ | ↓ | → | → | 트래픽 자체 감소. 상위(LB/DNS/클라이언트) 확인 |
| → | ↑ | ↑ | → | 정상 성장 중. 다만 용량 한계 접근 중 — 증설 계획 |

## 2-6. 대시보드 최소 구성

1. **p99 지연시간** — 사용자 체감 (평균 아님)
2. **처리량 + 도착률 겹쳐 그리기** — 벌어지는 순간이 용량 초과 시점
3. **대기 작업 수 추세** — 유일한 선행 지표. 기울기를 봐라
4. **오류율과 타임아웃율 분리** — 원인이 다르니 그래프도 분리

알람은 지연/오류에 걸고, **대기 수 기울기에 조기 경보를 하나 더** 걸어라.

> **요약**
> **처리량** = 시스템이 얼마나 일하는지
> **지연시간** = 사용자가 얼마나 기다리는지
> **대기 수** = 앞으로 얼마나 나빠질지
> **오류율** = 이미 얼마나 망가졌는지
>
> 대기 수 → 지연 → 오류로 번지므로, 조기 발견은 항상 **대기 수**에서 시작한다.

# 3. 비동기 처리 (Asynchronous Processing)

## 3-1. 한 줄 정의

**결과를 기다리지 않고 다음 일을 하는 것.**
작업을 "시작"하는 시점과 "결과를 받는" 시점을 분리한다.

## 3-2. 동기 vs 비동기

### 동기 (Synchronous)

```
요청 → [ 대기... 대기... 대기... ] → 응답 → 다음 작업
```

호출한 쪽이 결과가 나올 때까지 **멈춰 있다(block)**.
그 시간 동안 스레드는 아무 일도 못 하면서 메모리를 점유한다.

### 비동기 (Asynchronous)

```
요청 → 즉시 반환(약속) → 다른 작업 수행 → (결과 도착) → 이어서 처리
```

호출한 쪽은 **멈추지 않는다**. 결과는 나중에 콜백/이벤트/Future로 받는다.

## 3-3. 헷갈리는 4개 용어 정리

이게 비동기 학습에서 가장 많이 꼬이는 부분이다. **두 개의 축**으로 봐야 한다.

| 축 | 질문 | 값 |
|---|---|---|
| **동기 / 비동기** | 결과를 **누가 언제** 확인하는가? | 내가 직접 기다림 / 나중에 통보받음 |
| **블로킹 / 논블로킹** | 제어권을 **바로 돌려주는가?** | 안 돌려줌(멈춤) / 바로 돌려줌 |

조합하면 4가지:

| 조합 | 설명 | 예시 |
|---|---|---|
| 동기 + 블로킹 | 기다리며 멈춤. 가장 단순 | 일반 `read()`, JDBC |
| 동기 + 논블로킹 | 멈추진 않지만 내가 계속 물어봄 (폴링) | `while (!done) check()` |
| 비동기 + 논블로킹 | 통보받음. 진짜 비동기 | `CompletableFuture`, `async/await` |
| 비동기 + 블로킹 | 이론상 존재, 실무에서 무의미 | (거의 안 씀) |

> **핵심**: "비동기"는 결과 통보 방식, "논블로킹"은 함수가 즉시 반환하는지의 문제다. 다른 얘기다.

## 3-4. 왜 필요한가 — I/O 대기 시간

```
API 요청 1건 처리 = CPU 연산 5ms + DB 대기 50ms + 외부 API 대기 200ms
→ 총 255ms 중 CPU가 일하는 시간은 2%
```

동기 방식이면 나머지 98%(250ms) 동안 스레드가 **놀면서 점유만** 한다.
스레드 1개당 메모리 1MB라면, 동시 1만 요청 = 스레드 1만 개 = 10GB.

비동기는 대기 시간에 그 스레드를 다른 요청에 쓴다.
→ **적은 스레드로 많은 동시 요청 처리** (C10K 문제 해결의 핵심)

## 3-5. 비동기가 도움 되는 작업 / 안 되는 작업

| 작업 종류 | 비동기 효과 | 이유 |
|---|---|---|
| **I/O 바운드** (DB, 네트워크, 파일, 외부 API) | 매우 큼 | 대기 시간을 재활용 |
| **CPU 바운드** (암호화, 이미지 처리, 대량 계산) | **없거나 오히려 나쁨** | CPU는 어차피 100% — 컨텍스트 스위칭 비용만 추가 |

> **흔한 착각**: "비동기로 바꾸면 빨라진다" → 아니다.
> 비동기는 **처리량(throughput)**을 늘리지, 개별 요청의 **지연시간(latency)**을 줄이지 않는다.
> 오히려 스케줄링 오버헤드로 단건 지연은 조금 늘어날 수 있다.
> CPU 바운드는 비동기가 아니라 **멀티프로세싱/워커 분리**가 답이다.

## 3-6. 비동기 구현 패턴 (진화 순서)

### ① 콜백 (Callback)

```javascript
getUser(id, (err, user) => {
  getOrders(user, (err, orders) => {
    getItems(orders, (err, items) => { /* 콜백 지옥 */ });
  });
});
```

문제: 중첩 폭발, 에러 처리 산재, 순서 파악 불가 → **콜백 지옥**

### ② Promise / Future

```javascript
getUser(id)
  .then(getOrders)
  .then(getItems)
  .catch(handleError);   // 에러 처리 한 곳으로
```

체이닝으로 평탄화. 에러 전파 통일.

### ③ async / await (코루틴)

```javascript
try {
  const user   = await getUser(id);
  const orders = await getOrders(user);
  const items  = await getItems(orders);
} catch (e) { handleError(e); }
```

**동기 코드처럼 읽히지만 실제로는 비동기.** 현재 표준.

### ④ 리액티브 스트림 (Reactive)

```java
Flux.fromIterable(ids)
    .flatMap(this::fetchUser)       // 병렬
    .filter(User::isActive)
    .onBackpressureBuffer()         // 배압 제어
    .subscribe();
```

데이터 흐름 + **배압(backpressure)** 제어. 스트리밍/고부하에 적합. 학습 난도 높음.

### ⑤ 메세지 큐 (프로세스 간 비동기)

①~④는 **한 프로세스 안**의 비동기. 큐는 **서비스 간** 비동기다.
프로세스가 죽어도 작업이 남고, 재시도/추적이 가능하다. → 1장 참조

## 3-7. 반드시 알아야 하는 함정

| 함정 | 내용 |
|---|---|
| **에러 삼킴** | 비동기 작업의 예외는 호출자에게 자동 전파되지 않는다. `await` 없는 async 호출, 처리 안 한 Promise rejection은 **조용히 사라진다** |
| **실행 순서 보장 없음** | 여러 비동기 작업의 완료 순서는 시작 순서와 무관 |
| **경쟁 상태 (Race Condition)** | 동시에 같은 자원 접근 → 결과가 실행 타이밍에 따라 달라짐 |
| **동기 코드 한 줄로 전체 마비** | 이벤트 루프 모델에서 블로킹 호출 1개가 전체 스레드를 정지시킴 (`Thread.sleep`, 동기 파일 읽기) |
| **컨텍스트 유실** | 트랜잭션, 인증 정보, 로그 traceId 등 스레드 로컬 값이 비동기 경계를 못 넘어감 |
| **디버깅 난이도** | 스택 트레이스가 끊긴다. 로그에 요청 ID(correlation ID) 필수 |
| **무한 대기** | 타임아웃 없는 비동기 작업은 영원히 매달려 있을 수 있다 |
| **자원 고갈** | 동시성 제한 없이 fan-out하면 커넥션 풀/메모리가 먼저 터짐 |

## 3-8. 비동기 설계 시 필수 체크 3가지

1. **타임아웃** — 모든 비동기 작업에 반드시 걸어라. 없으면 대기 수가 무한히 쌓인다
2. **멱등성** — 재시도가 있으면 같은 작업을 두 번 해도 결과가 같아야 한다
3. **동시성 상한** — `Semaphore` 등으로 동시 실행 개수를 제한해라

## 3-9. 비동기와 성능 지표의 관계

2장의 4대 지표가 비동기에서 특히 중요해지는 이유:

| 지표 | 비동기에서의 의미 |
|---|---|
| 지연시간 | **끝에서 끝까지(end-to-end)** 재야 함. 요청 수락 시점 ≠ 처리 완료 시점 |
| 처리량 | 비동기의 주된 개선 대상. 여기가 오르면 성공 |
| 대기 작업 수 | **가장 중요.** 비동기는 부하를 큐로 미룬다 → 대기 수 안 보면 붕괴를 예측 못 함 |
| 오류/타임아웃 | 비동기는 실패가 **조용하다.** 명시적으로 계측하지 않으면 장애를 모른다 |

> 비동기 시스템에서 응답이 빠른 건 당연하다 (일을 미뤘으니까).
> 진짜 건강 신호는 **대기 작업 수가 안정적인가**다.

# 4. 비동기 학습 체크리스트

각 항목은 "설명할 수 있는가 / 코드로 쓸 수 있는가" 기준으로 체크.

## Phase 1 — 개념 기초 (여기가 안 되면 아래는 무의미)

- [ ] 동기 / 비동기의 차이를 그림으로 그려 설명할 수 있다
- [ ] 블로킹 / 논블로킹이 동기 / 비동기와 **다른 축**임을 설명할 수 있다
- [ ] 4가지 조합(동기블로킹 ~ 비동기논블로킹) 각각의 예시를 댈 수 있다
- [ ] I/O 바운드 vs CPU 바운드를 구분하고, 비동기가 어느 쪽에만 효과 있는지 안다
- [ ] "비동기는 지연시간이 아니라 처리량을 개선한다"는 말을 근거와 함께 설명할 수 있다
- [ ] 프로세스 / 스레드 / 코루틴의 차이와 각각의 비용(메모리, 스위칭)을 안다
- [ ] 컨텍스트 스위칭이 무엇이고 왜 비용인지 안다

## Phase 2 — 실행 모델

- [ ] 이벤트 루프의 동작 순서를 설명할 수 있다
- [ ] 스레드 풀 모델과 이벤트 루프 모델의 트레이드오프를 안다
- [ ] 이벤트 루프에서 블로킹 호출 하나가 왜 전체를 멈추는지 안다
- [ ] 마이크로태스크 / 매크로태스크 실행 우선순위를 안다 (JS 기준)
- [ ] 코루틴(경량 스레드)이 OS 스레드와 어떻게 다른지 안다
- [ ] `epoll` / `kqueue` / IOCP 같은 OS 레벨 다중화가 무엇인지 개념적으로 안다

## Phase 3 — 언어별 문법과 API (본인 주 언어 하나 먼저 끝내라)

### 공통

- [ ] Future / Promise가 "아직 없는 값"을 표현하는 객체임을 이해한다
- [ ] 여러 비동기 작업을 **병렬**로 실행하고 전부 기다릴 수 있다
- [ ] 여러 작업 중 **가장 먼저 끝난 것**만 취할 수 있다
- [ ] 비동기 작업에 타임아웃을 걸 수 있다
- [ ] 비동기 작업을 취소(cancel)할 수 있다

### JavaScript / TypeScript

- [ ] `Promise` 생성, `then` / `catch` / `finally`
- [ ] `async` / `await` 문법과 반환값이 항상 Promise인 것
- [ ] `Promise.all` / `allSettled` / `race` / `any` 차이
- [ ] `await`를 루프 안에 쓰면 직렬 실행되는 문제와 해결법
- [ ] `unhandledRejection` — 처리 안 한 Promise가 조용히 죽는 것
- [ ] `AbortController`로 요청 취소

### Java / Spring

- [ ] `CompletableFuture` — `supplyAsync`, `thenApply`, `thenCompose`, `allOf`
- [ ] `thenApply` vs `thenCompose` 차이 (flatMap 개념)
- [ ] `ExecutorService`와 스레드 풀 튜닝 (core / max / queue 크기)
- [ ] `@Async`와 프록시 기반 동작의 한계 (같은 클래스 내부 호출 안 됨)
- [ ] Virtual Thread (Java 21+) — 왜 비동기 코드 없이 비동기 성능을 내는지
- [ ] WebFlux / `Mono` / `Flux` — 리액티브 기초
- [ ] 비동기에서 `@Transactional`이 깨지는 이유

### Python

- [ ] `async def` / `await` / 코루틴 객체
- [ ] `asyncio.run` / `create_task` / `gather` / `wait_for`
- [ ] GIL이 무엇이고 왜 CPU 바운드에 `multiprocessing`이 필요한지
- [ ] 이벤트 루프에서 동기 함수를 안전하게 돌리는 법 (`asyncio.to_thread`)

## Phase 4 — 에러 처리와 신뢰성 (실무의 핵심)

- [ ] 비동기 예외가 호출자에게 자동 전파되지 않는 이유를 안다
- [ ] 처리하지 않은 비동기 예외를 전역에서 잡을 수 있다
- [ ] **타임아웃**을 모든 외부 호출에 설정한다
- [ ] **재시도**를 지수 백오프 + 지터로 구현할 수 있다
- [ ] 왜 지터(jitter)가 없으면 재시도가 동시에 몰리는지 안다
- [ ] **멱등성**의 의미와, 멱등 키(idempotency key) 설계 방법을 안다
- [ ] **서킷 브레이커** 패턴의 3상태(Closed / Open / Half-Open)를 안다
- [ ] 재시도 폭풍(retry storm)이 어떻게 장애를 증폭시키는지 설명할 수 있다
- [ ] `Semaphore` 등으로 동시 실행 개수를 제한할 수 있다
- [ ] 부하 차단(load shedding) — 넘치면 빨리 거절하는 게 나은 이유를 안다

## Phase 5 — 동시성 안전

- [ ] 경쟁 상태(race condition)의 예를 코드로 만들 수 있다
- [ ] 데드락의 4조건과 회피 방법을 안다
- [ ] 원자적 연산 / CAS가 무엇인지 안다
- [ ] 불변 객체를 쓰면 동시성 문제가 줄어드는 이유를 안다
- [ ] ThreadLocal 값이 비동기 경계를 못 넘는 문제와 대안을 안다
- [ ] 낙관적 락 / 비관적 락의 차이와 선택 기준을 안다

## Phase 6 — 프로세스 간 비동기 (메세지 큐)

- [ ] Producer / Consumer / Broker / Ack / DLQ를 설명할 수 있다
- [ ] Point-to-Point와 Pub/Sub의 용도 차이를 안다
- [ ] at-most-once / at-least-once / exactly-once 전달 보장의 차이를 안다
- [ ] 왜 실무에서 exactly-once가 어렵고, at-least-once + 멱등이 정답인지 안다
- [ ] 메시지 순서가 기본적으로 보장되지 않는 이유와, 필요할 때의 해법을 안다
- [ ] DLQ에 쌓인 메시지를 어떻게 처리/재투입할지 계획할 수 있다
- [ ] Kafka와 RabbitMQ의 근본적 차이(로그 보존 vs 큐 소비)를 안다
- [ ] Consumer가 처리 중 죽으면 메시지가 어떻게 되는지 안다
- [ ] 큐를 하나 추가하면 장애 지점도 하나 늘어난다는 점을 인지한다

## Phase 7 — 관측 (Observability) ★ 가장 많이 빠뜨리는 부분

- [ ] p50 / p95 / p99를 측정하고 있다 (평균이 아니라)
- [ ] 도착률과 처리량을 **함께** 그려서 보고 있다
- [ ] 큐 대기 작업 수를 계측하고, **기울기**에 알람을 걸었다
- [ ] 오류율과 타임아웃율을 **분리**해서 보고 있다
- [ ] 리틀의 법칙(`L = λ × W`)으로 대기시간을 추정할 수 있다
- [ ] 요청 ID(correlation ID)를 비동기 경계 전체에 전파한다
- [ ] 분산 트레이싱으로 끊긴 스택을 이어볼 수 있다 (OpenTelemetry 등)
- [ ] 스레드 풀 / 커넥션 풀의 사용률과 대기 수를 모니터링한다

## Phase 8 — 아키텍처 패턴 (필요해질 때)

- [ ] 이벤트 드리븐 아키텍처의 장단점을 설명할 수 있다
- [ ] 최종 일관성(eventual consistency)을 받아들이는 설계를 할 수 있다
- [ ] Saga 패턴 — 분산 트랜잭션 대안
- [ ] Outbox 패턴 — DB 저장과 메시지 발행의 원자성 문제 해결
- [ ] CQRS — 읽기/쓰기 분리
- [ ] 백프레셔(배압) — 소비자가 못 따라갈 때 생산자를 늦추는 것

Phase 1 (개념)  ──▶ 반드시 먼저. 여기 건너뛰면 나머지가 암기가 된다
      │
      ▼
Phase 3 (문법)  ◀──▶ Phase 2 (실행 모델)   ← 코드 쓰면서 같이
      │
      ▼
Phase 4 (에러/신뢰성)  ← 실무 투입 최소 요건
      │
      ▼

      │
      ▼
Phase 5 (동시성) ─▶ Phase 6 (큐) ─▶ Phase 8 (아키텍처)

## 실습 과제 제안

1. **동기 → 비동기 전환 측정**
   외부 API 3개를 순차 호출하는 코드를 병렬로 바꾸고, 지연시간·처리량 변화를 직접 측정
2. **의도적으로 큐 터뜨리기**
   Consumer를 1개로 제한하고 부하를 걸어, 대기 수 → 지연 → 타임아웃 사슬을 눈으로 확인
3. **재시도 폭풍 재현**
   백오프 없는 재시도를 넣고 부하를 걸어, 오류율이 어떻게 증폭되는지 확인 → 백오프+지터 추가 후 비교
4. **멱등성 깨보기**
   같은 메시지를 두 번 처리시켜 중복 데이터를 만들고, 멱등 키로 막기

## 한 문장 요약

> **메세지 큐**는 서비스 간 비동기를 위한 우편함이고,
> **비동기**는 대기 시간을 재활용해 처리량을 올리는 기법이며,
> **4대 지표**는 그 시스템이 언제 무너질지 알려주는 계기판이다.
> 세 개는 따로 배울 수 없다.
