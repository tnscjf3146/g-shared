## 1. 이 프로젝트가 뭔가

### 한 문장

**놀고 있는 GPU를 가진 사람이, 남의 AI 연산을 대신 해주고 돈을 받는 장터.**

### 조금 더

- **의뢰자**: "문장 10,000개를 벡터로 바꿔줘" 하고 돈을 맡긴다
- **공급자**: 자기 GPU로 계산해서 결과를 넘긴다
- **검증자**: 결과가 진짜인지 확인한다
- 확인되면 공급자가 돈을 받는다

여기서 "벡터로 바꾸는 것"을 **임베딩**이라 부른다. 문장을 숫자 목록(예: 1,024개의 실수)으로 바꾸는 AI 연산이다. **이 프로젝트에서 임베딩이 뭔지는 몰라도 된다.** "GPU가 오래 걸려서 하는 계산"으로만 이해하면 충분하다.

### 그러면 문제가 하나 생긴다

> 남이 대신 계산한 결과인데, **정직하게 했는지 어떻게 아는가?**

공급자가 대충 계산하거나, 작은 모델로 싸게 돌리거나, 아예 랜덤 숫자를 채워 보낼 수도 있다. 의뢰자는 10,000개를 다 다시 계산해볼 수 없다 — 그럴 거면 맡길 이유가 없다.

### 이 프로젝트의 답

```
① 공급자가 결과 10,000건을 "지문" 하나(32바이트)로 요약해서 공개 장부에 못 박는다
② 못 박은 "다음에" 무작위로 1%(100건)를 뽑는다
③ 검증자가 그 100건만 다시 계산해서 대조한다
④ 하나라도 어긋나면 돈을 안 준다
```

**②의 순서가 전부다.** 어디를 검사할지 미리 알면 그 부분만 정직하게 하고 나머지를 속일 수 있다. 결과를 먼저 고정하고 **그 뒤에** 검사 위치를 뽑기 때문에 속일 수 없다.

그리고 계산은 10,000건인데 검사는 100건이다. **1%만 보고 100%를 담보받는다.** 이 비대칭이 이 사업이 성립하는 유일한 이유다.

## 2. 왜 블록체인을 쓰나

신입이 가장 먼저 드는 의문: **"그냥 우리 서버에 기록하면 안 돼요?"**

정당한 질문이고, 답이 있다.

### 서버에 기록하면 생기는 문제

| 상황 | 서버 방식 |
|---|---|
| 공급자가 "나 결과 냈는데 서버가 안 받아줬다"고 주장 | 서버 운영자(우리) 말을 믿어야 함 |
| 우리가 공급자 돈을 안 주고 싶으면 | 그냥 안 주면 됨 |
| 검사 위치를 우리가 정하면 | 우리가 공급자와 짜고 알려줄 수 있음 |
| 우리 서버가 꺼지면 | 아무도 돈을 못 받고 못 돌려받음 |

즉, **서버 방식은 "우리를 믿어라"가 전제**다. 그러면 이 프로젝트는 그냥 또 하나의 중개 플랫폼이고, 중개 수수료를 떼는 기존 회사들과 다를 게 없다.

### 블록체인이 바꾸는 것

블록체인은 **누구도 혼자 고칠 수 없는 공개 장부**다. 거기에 이것들을 올린다.

- 돈이 예치됐다는 사실
- 결과의 지문(머클 루트)
- 검사 위치 (블록 해시로 뽑음 — 아무도 미리 못 안다)
- 검증자의 판정
- 돈이 누구에게 갔는가

이러면 **우리 서버가 사라져도** 공급자는 장부를 직접 읽어 일을 잡고, 결과를 내고, 돈을 받을 수 있다. 이게 이 프로젝트의 핵심 주장이다.

> **판정 기준 한 줄**
> "우리 서버가 사라지면 시스템이 **멈추는가**, **불편해지는가**?"
> 멈추면 중개자. 불편해지면 편의 레이어. **우리는 편의 레이어여야 한다.**

이 문장을 외우면 이 프로젝트의 설계 결정 대부분이 이해된다.

## 3. 작업 하나의 일생

작업 하나가 태어나서 끝날 때까지를 따라가보자. **상태 이름(대문자)은 블록체인 위의 컨트랙트에 저장된 값**이다. 우리 서버는 이걸 읽어서 화면에 보여준다.

### 1단계 — 의뢰자가 일을 올린다

```
의뢰자: "이 파일(입력 CID) 10,000건을 BGE-M3 모델로 임베딩해줘"
        → createJob                                  상태: CREATED
```

`CID`는 파일의 주소다. 파일 내용이 바뀌면 주소도 바뀐다.
모델 이름과 함께 **가중치 해시**도 올린다 — "정확히 이 모델 파일을 써라"라는 뜻. (최근에 추가됨, 8절)

### 2단계 — 의뢰자가 돈을 맡긴다

```
의뢰자: 대금 P 예치                                   상태: FUNDED
```

**실행 전에 돈이 먼저 잠긴다.** 이게 관문 ①. 돈이 안 잠기면 공급자는 일하고 못 받을 위험을 진다.
아무도 안 잡으면 시간이 지나 → `REFUNDED` (환불).

### 3단계 — 시스템이 GPU를 추천한다

```
Matcher: "이 일은 3090급 이상 권장, 예상 40~70초. 추천 순위 ①②③"
```

**추천이다. 배정이 아니다.** 서버가 "너 해"라고 정할 수 없다 — 공급자의 지갑을 서버가 움직일 수 없기 때문. 실제로 잡는 건 다음 단계에서 공급자가 직접 한다. (이름이 `Scheduler`에서 `Matcher`로 바뀌었다, 8절)

### 4단계 — 공급자가 준비하고, 잡는다

```
공급자: 사전 점검 — 모델 파일 있나? 해시 맞나? VRAM 충분한가?
        통과하면 → acceptJob                          상태: ASSIGNED
```

관문 ②. 이 순간부터 **시계가 돈다.** 기한 = 예상 시간 상한 × 3. 넘기면 → `SLASHED`.

**여기서 중요한 규칙 하나**: 우리 서버는 **이 상태가 되고, 요청한 사람이 바로 그 공급자일 때만** 입력 파일을 내려준다. 아니면 아무나 데이터를 가져간다.

사전 점검이 `acceptJob` **앞에** 있는 이유: 모델 다운로드가 3분 걸리면 시작도 못 하고 기한을 넘긴다. **준비 다 하고 잡는다.** (최근에 순서가 바뀌었다, 8절)

### 5단계 — 공급자가 계산한다

```
공급자: 컨테이너에서 실행 → 벡터 10,000개
        200건마다 "37/50 완료" 진행률 보고 → 우리 서버 (표시 전용)
        결과 파일 업로드 → 머클 루트 계산
```

**진행률은 공급자가 스스로 말한 값이다.** 검증된 게 아니다. 화면에서 온체인 값과 시각적으로 구분해야 한다 (점선 + "미검증" 배지).

### 6단계 — 결과를 제출한다

```
공급자: submitResult(결과 CID, 머클 루트)             상태: SUBMITTED
```

**공급자 자기 지갑 키로 서명한다.** 우리 서버는 전달(릴레이)만 한다. 서버가 대신 제출하면 서버가 결과를 조작할 수 있게 되기 때문.

### 7단계 — 의뢰자가 이의를 제기할 시간

```
(데모에서 2분)
화면: ⚠ AI 이상 점수 0.82 — 이의 제기를 권합니다   [이의 제기]
```

AI가 결과를 훑어서 "이상해 보인다"고 **알려준다.** 하지만 **버튼을 누르는 건 사람이고, 예치금을 거는 것도 사람이다.** AI가 자동으로 검증을 시작하지 않는다. (이게 왜 중요한지는 6절)

```
├─ 아무 일 없음 → 시간 지나면 → COMPLETED    공급자 돈 받음
└─ 의뢰자가 예치금 D를 걸고 raiseDispute → VERIFYING
```

### 8단계 — 검증

```
raiseDispute 트랜잭션의 블록 해시로 검사할 100건 선정
  (아무도 미리 못 안다 — 트랜잭션이 확정되는 순간 정해진다)

검증자: 그 100건만 다시 계산 → 원본과 비교 → settle

  ├─ 일치   → COMPLETED    공급자 돈 받음, 검증자 보수
  └─ 불일치 → SLASHED      의뢰자 환불,  검증자 보수
```

### 끝나는 방법은 셋뿐

| 상태 | 뜻 |
|---|---|
| `COMPLETED` | 정상 종결. 공급자가 받음 |
| `REFUNDED` | 아무도 안 잡아서 환불 |
| `SLASHED` | 기한 초과 또는 부정. 공급자 못 받음 |

### 전체 그림

```
CREATED ─▶ FUNDED ─▶ ASSIGNED ─▶ SUBMITTED ─┬─▶ COMPLETED
              │          │                   │
              │          │                   └─▶ VERIFYING ─┬─▶ COMPLETED
              │          │                                  └─▶ SLASHED
              │          └─(기한 초과)─▶ SLASHED
              └─(아무도 안 잡음)─▶ REFUNDED
```

## 4. 데이터는 어디 있나

**백엔드 신입이 가장 많이 하는 실수: "이건 DB에 있겠지."** 아니다.

이 시스템에는 저장소가 **세 곳**이다.

| 저장소 | 성격 | 비유 |
|---|---|---|
| **온체인** (블록체인) | 느리고 비싸고 **아무도 못 고침** | 공증 사무소 |
| **파일 저장소** (IPFS 등) | 크고 싸고 내용 기반 주소 | 창고 |
| **우리 DB** | 빠르고 싸고 **우리가 고칠 수 있음** | 메모장 |

### 무엇이 어디에

| 데이터 | 어디 | 우리 서버는 |
|---|---|---|
| 작업 상태 (`FUNDED` 등) | 온체인 | 읽어서 **캐시만.** DB를 진실로 삼지 말 것 |
| 대금·예치금 금액 | 온체인 | 읽기만 |
| 머클 루트 (결과 지문) | 온체인 | 읽기만 |
| 검사할 100건의 위치 | 온체인 | 읽기만 |
| 검증자 판정 (참/거짓) | 온체인 | 읽기만 |
| 상태가 바뀐 시각 | 온체인 (블록 타임스탬프) | 타임아웃 계산에 씀 |
| 입력 파일 원본 | 파일 저장소 | 보관·중계. `ASSIGNED`일 때만 공급자에게 |
| 결과 벡터 10,000개 (~15MB) | 파일 저장소 | **절대 온체인에 안 올림** |
| 진행률 (37/50) | 우리 DB | 공급자 자기신고. 미검증 |
| 실행 이력·벤치마크 | 우리 DB | AI 예측 학습 재료 |
| 사용자 계정·인증 | 우리 DB | 금융망 1원 인증 |

### 원칙

- **돈과 판정에 관한 것 → 온체인.** 아무도 못 고쳐야 하니까
- **크기가 큰 것 → 파일.** 온체인은 바이트 단위로 돈이 드니까
- **편의 정보 → DB.** 없어져도 시스템은 돌아가야 하니까

> 온체인 값은 화면에 **실선 + 트랜잭션 해시 링크**로, 자기신고 값은 **점선 + "미검증" 배지**로.

## 5. 팀은 뭘 만들고 있나

백엔드 산출물은 **둘**이다.

### D4. 체인 게이트웨이 — Spring Boot (사람 3)

```
web3j 래퍼      컨트랙트 함수를 자바 메서드로 감쌈
이벤트 인덱서    체인에서 일어난 일을 읽어 DB에 넣음
조회 API        프론트와 에이전트가 쓰는 REST
자산 브리지     금융망 가상계좌 연동 (원화 ↔ 시스템)
```

**설계 제약: 게이트웨이는 권한이 없다.**
읽기만 한다. 상태를 바꾸는 트랜잭션은 각 노드가 자기 키로 직접 보낸다.
게이트웨이가 상태를 바꿀 수 있으면 → 우리가 중개자 → 프로젝트 주장 무너짐.

3주차 게이트 판정 항목: **"백엔드를 꺼도 한 바퀴가 돈다."**

### D3. 에이전트 — Python (사람 4)

각 참여자의 컴퓨터에서 돌아가는 자동 프로그램(데몬). 골격은 전부 같다.

```
이벤트 구독 → 조건 판단 → 트랜잭션 전송
```

| 노드 | 하는 일 |
|---|---|
| 공급자 노드 | 일감 감시 → 수락 → 실행 → 머클 트리 → 제출 |
| 검증자 노드 | 검사 위치 수신 → 재실행 → 비교 → 판정 제출 |
| 의뢰자 노드 | 등록 → 결과 수령 → 자가 표본 검사 → 이의 제기 |
| 키퍼 | 타임아웃 감시 → 대신 호출 (7절 ①) |
| 부정 노드 | 공급자 노드에 "속이기" 플래그 하나. 시연용 |

**왜 파이썬인가**: 계산 커널(AI 담당 산출물)을 `import`해야 한다. 공급자와 검증자가 **같은 코드**로 계산해야 비교가 성립한다. 자바로 다시 짜면 "누구 소수점 오차가 맞냐" 논쟁이 시작된다.

### 도구

| 도구 | 용도 | 누가 |
|---|---|---|
| **Hardhat** | 로컬 블록체인 띄우기, 배포, 테스트 | 전원 |
| **web3j** | 자바에서 체인 읽기·쓰기 | 사람 3 |
| **web3.py** | 파이썬에서 체인 읽기·쓰기 | 사람 4 |
| **MetaMask** | 지갑. 수동 확인, 시연 | 전원 |
| **Sepolia** | 공개 테스트넷 (가짜 돈) | 후반 |
| **Etherscan** | 트랜잭션·이벤트 확인 사이트 | 전원 |
| **금융망 API** | 가상계좌 (`autoTransfer=false`) | 사람 3 |

`autoTransfer=false`가 핵심: 입금이 연결계좌로 바로 안 넘어가고 `pendingAmount`로 **묶인다.** 이게 에스크로 역할. `settleVirtualAccount`로 풀어준다.

## 6. 절대 규칙

코드 짜기 전에 외운다. 전부 **"우리 서버가 권력을 갖지 않는다"**의 변형이다.

| # | 규칙 | 어기면 |
|---|---|---|
| 1 | **DB를 진실로 삼지 않는다.** 상태의 원본은 체인 | 우리가 상태를 만들면 그게 중앙 권한 |
| 2 | **`submitResult`는 공급자 키로 서명.** 우리는 릴레이만 | 우리가 결과를 조작할 수 있게 됨 |
| 3 | **입력 파일은 `ASSIGNED` + 배정된 공급자에게만** | 아무나 데이터 가져감 |
| 4 | **AI는 권고까지.** 자금의 스위치로 쓰지 않는다 | AI가 틀리면 돈이 잘못 감 |

### 규칙 4가 특히 중요한 이유

이번에 팀원이 그린 흐름도가 이렇게 읽혔다: *"AI가 이상하다고 하면 검증한다."*

그러면 **AI가 "정상"이라 하면 검증 없이 정산**되고, AI가 놓치면 부정이 통과한다. 심사에서 *"검증은 누가 시작합니까? AI가?"*에 "네"라고 답하는 순간 끝이다.

**고친 것**: AI는 배너를 띄운다. 누르는 건 의뢰자. 예치금 거는 것도 의뢰자.
**판단은 사람이, 자금은 사람 손에서.** AI가 완전히 틀려도 돈은 안전하다.

## 7. 블록체인 처음이면 걸리는 것 8가지

일반 웹 개발 감각으로 접근하면 여기서 하루씩 날린다.

### ① 컨트랙트는 스스로 움직이지 않는다

크론 없음, 타이머 없음. **누군가 트랜잭션을 보내야만** 상태가 바뀐다.
"2분 뒤 자동 승인"은 자동이 아니다 — 2분 뒤에 **누군가 `settle()`을 호출**해야 한다. 그래서 **키퍼** 데몬이 있다.

### ② 이벤트가 알림이다

DB 트리거도 웹훅도 아니다. 컨트랙트가 `emit JobFunded(...)`하면 로그가 남고, 우리가 구독하거나 폴링해서 안다.
- WebSocket 구독은 **끊긴다.** 재연결 시 놓친 블록 복구 로직 필요
- `fromBlock` 커서를 DB에 저장, 재시작하면 거기서부터

### ③ 트랜잭션은 보냈다고 끝이 아니다

보내면 해시가 나오고 **확정은 나중**. 실패(revert)할 수도 있다. 확정 전에 "됐다"고 응답하면 안 된다.

### ④ 되감기(reorg)

방금 읽은 이벤트가 취소될 수 있다. 몇 블록 기다린 뒤 확정으로 취급. 로컬 Hardhat에선 안 겪지만 Sepolia에선 겪는다.

### ⑤ nonce

한 계정에서 트랜잭션을 연달아 보내면 순번이 충돌한다. 동시에 여러 개 보낼 일이 있으면 `pending` 기준으로 관리.

### ⑥ 읽기는 공짜, 쓰기는 유료

조회(`view`)는 가스 무료. 상태 변경은 전부 유료. **그래서 온체인에 최소한만.** 벡터 10,000개를 올리자는 생각이 들면 잘못 가고 있는 것.

### ⑦ 온체인에 비밀은 없다

Solidity의 `private`은 **다른 컨트랙트의 접근만** 막는다. 노드는 전체를 읽을 수 있다. 비밀이 필요하면 커밋-리빌.

### ⑧ 소수점이 없다

EVM은 실수 연산을 못 한다. 코사인 유사도 비교는 **오프체인**에서, 컨트랙트엔 **판정 `bool`만** 올린다.

> 이 8개의 원리를 알고 싶으면 → [26_08_27_블록체인_이해.md](26_08_27_블록체인_이해.md) Phase 1~3, 6

## 8. 최근에 바뀐 것 (2026-08-26)

**중간에 합류했으면 이 절이 가장 중요하다.** 옛 문서·옛 대화와 지금이 다른 지점.

### 담보(S)는 1단계에서 꺼둔다

원래 설계엔 공급자도 판돈(담보 S = 대금의 50%)을 걸게 되어 있었다. **1단계는 이 값을 0으로 배포한다.** 코드는 넣되 끈다. 2단계에 켠다.

그래서:
- `acceptJob`은 `msg.value == 0`으로 호출된다. 담보 잔액이 0으로 나와도 **버그 아님**
- 1단계 `SLASHED` = "대금 못 받음"이지, "판돈 몰수"가 아니다
- 옛 리뷰 문서의 "담보 관련 지적"은 **무시해도 된다.** 리뷰 뒤에 범위가 바뀐 것

### 팀원 제안 흐름 검토 결과 — 5개 조정

| # | 원래 제안 | 조정 후 | 이유 |
|---|---|---|---|
| ① | AI가 이상하면 검증 | AI는 **권고 배너**, 발동은 의뢰자 | 규칙 4 |
| ② | 10,000건을 200건씩 쪼개 **여러 사람**에게 | 한 사람이 다 함. Chunk는 **진행률 단위**로만 | 47명 성공 3명 실패를 부를 상태가 없음. 한 명만 잠수해도 전체 멈춤 (확률 92%) |
| ③ | `Scheduler`가 GPU **배정** | `Matcher`가 GPU **추천** | 서버는 남의 지갑을 못 움직임. 강제력이 없으니 이름도 바꿈 |
| ④ | 블록체인이 맨 끝에서 "기록" | 블록체인이 흐름을 **관통** — 돈 예치·수락이 실행 **전** | 끝에만 있으면 "작업 큐 + 감사 로그"와 다를 게 없음 |
| ⑤ | `acceptJob` 후 모델 다운로드 | 모델 준비 **먼저**, 그 다음 `acceptJob` | 다운로드가 3분 먹으면 시작도 못 하고 `SLASHED` |

**상태 추가 0, 전이 추가 0, 자금 흐름 수정 0.** 전부 오프체인 조정이거나 필드 하나 추가.

### 제안에서 얻은 것 3개

- **모델 신원 확인** — `createJob`에 `weightsHash` 추가. 워커가 실행 전 대조. "더 작은 모델로 싸게 돌리기" 공격을 막는 방어가 이제야 생겼다
- **Chunk → 층화 표본** — Chunk 경계를 알면 "Chunk마다 최소 1건 검사"를 강제할 수 있다. 국소 조작 미적발률 13% → 0
- **예상 처리시간 산출** — `ASSIGNED` 기한 = 예상 상한 × 3인데, 그 상한을 만들 모듈이 어디에도 없었다. 이 제안이 그렸다

### 멀티워커 분산은 보류

"시간 되면 한다." 할 때는 Chunk를 하위 단위로 만들지 말고 **독립 Job N개로 발행.** 상태표를 한 줄도 안 고친다.

## 9. 아직 안 정해진 것

막히면 여기 걸려 있을 확률이 높다. **누구에게 물어야 하는지**까지.

### ⚠️ 결정 1. 돈이 어디에 있는가 — 최우선, 미결

| 안 | 내용 | 영향 |
|---|---|---|
| (a) 금융망 보관 | 컨트랙트는 판정만, 실제 이체는 우리 서버가 `settleVirtualAccount` | 자산 브리지 커짐. **우리 서버가 사라지면 돈이 안 움직임** — 2절 판정 기준 위반 |
| (b) 온체인 정산 | 에스크로·정산을 컨트랙트가 직접. 금융망은 환전만 | 브리지 작아짐. 판결이 스스로 집행됨 |

문서는 **(b)를 권한다.** 이게 안 정해지면 **사람 3의 작업 전체가 막힌다.**
→ 물을 사람: 컨트랙트 담당 + 팀 리더

### 결정 2. 작업 하나의 크기

- 하한: 이의 예치금 `D = P × 0.1`이 `raiseDispute` 가스비보다 커야 함. 아니면 이의 제기가 손해
- 상한: 데모 타임아웃 3분 안에 끝나야 함
- 실측 실행시간 + Sepolia 가스비 넣고 역산해야 나옴
→ 물을 사람: AI 담당(실행시간) + 컨트랙트 담당(가스비)

### 결정 3. 워크로드 모델 확정 — 실측 후

→ 물을 사람: AI 담당

| **MetaMask** | 브라우저 지갑 프로그램 |
| **Hardhat** | 내 컴퓨터에 가짜 블록체인을 띄우는 개발 도구 |
| **Sepolia** | 공개 테스트 블록체인. 가짜 돈. 실제 네트워크 지연·되감기를 겪어볼 수 있음 |
| **Faucet** | 테스트넷 가짜 돈 무료로 주는 곳 |
| **Etherscan** | 블록체인 탐색 사이트. 트랜잭션·이벤트 확인 |
| **에스크로** | 제3자가 돈을 맡아뒀다가 조건 충족 시 넘겨주는 것 |
| **CID** | IPFS 파일 주소. 내용이 바뀌면 주소도 바뀜 → 내용 위조 불가 |
| **해시** | 데이터의 지문. 1비트만 바뀌어도 완전히 달라짐. 역산 불가 |
| **머클 루트** | 데이터 N개를 트리로 묶어 만든 32바이트 대표 지문 |
| **머클 증명** | "이 항목이 그 루트 안에 있었다"를 해시 몇 개로 증명. 10,000건이면 14개 |
| **머클 서브트리** | 머클 트리의 중간 가지. Chunk(200건)가 여기 대응 |
| **표본 검증** | 전부 안 보고 일부만 뽑아 검사. 1% 보고 100% 담보 |
| **층화 표본** | 구간(Chunk)마다 최소 1건씩 강제로 뽑는 방식. 국소 조작 방지 |
| **코사인 유사도** | 벡터 두 개가 얼마나 같은 방향인지. 재계산 결과 비교에 씀 |
| **챌린지 기간** | 일단 맞다고 치되 반박할 시간을 주는 구간. `SUBMITTED` 상태 |
| **이의 제기 / raiseDispute** | 의뢰자가 예치금 D를 걸고 "검증해달라"고 요청 |
| **슬래싱 / SLASHED** | 원래는 판돈 몰수. 1단계에선 "대금 미지급" |
| **담보 (S)** | 공급자가 거는 판돈. **1단계에선 0** |
| **키퍼** | 타임아웃 등 조건이 되면 대신 트랜잭션을 보내주는 봇 |
| **Matcher** | GPU 추천 모듈. 배정 권한 없음 (구 Scheduler) |
| **Chunk** | 200건 단위. 진행률 보고 + 머클 서브트리 단위. **온체인 단위 아님** |
| **weightsHash** | 모델 파일의 해시. "정확히 이 모델을 써라" |
| **커밋-리빌** | 먼저 답의 해시만 내고(커밋) 나중에 답 공개(리빌). 베끼기 방지 |
| **reorg (되감기)** | 확정된 줄 알았던 블록이 뒤집히는 것. 몇 블록 기다리면 안전 |
| **nonce** | 계정별 트랜잭션 순번. 연달아 보내면 충돌 가능 |
| **릴레이 / 가스 대납** | 남이 서명한 트랜잭션을 대신 전송하고 수수료만 내주는 것 |
| **1원 인증** | 계좌에 1원 보내서 입금자명으로 본인 확인 |
| **가상계좌 / autoTransfer / pendingAmount** | 금융망 API. `autoTransfer=false`면 입금이 바로 안 넘어가고 `pendingAmount`로 묶임 = 에스크로 |
| **게이트 판정** | 주차별 통과 조건. 3주차: "백엔드를 꺼도 한 바퀴가 돈다" |

> 이 모든 게 **우리 서버 없이도** 돌아가야 한다. 서버는 편하게 해주는 것뿐이다.
