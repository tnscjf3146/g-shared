| 1 | 크라우드 펀딩 + 스마트 컨트랙트로 먹튀 방지 | 구조가 "펀딩 → 제작비 일부 선지급 → 완성 후 잔금"인데, **선지급 제작금을 먹고 도망가는 건 컨트랙트로 못 막음** |

**확정 아이디어 개요**

- 기술 분담: **블록체인**(사용량 정산·장부·에스크로) / **AI**(작업 스케줄링, 적합 GPU 배치) / **P2P**(노드 네트워크)
- 블록체인을 쓰는 이유(팀 설명): GPU 사용량 기반 정산을 에스크로 형태 스마트 컨트랙트로 처리 + 검증단(작업 품질 검증) 추가 + 사기 신고 시 장부 조회해 해당 공급자 환수/제재

### 1-2. 코치의 핵심 질문 — "장부와 실제 GPU 사용의 연결고리" (03:00~10:00)

코치가 세션 내내 반복한 질문:

> 블록체인 장부에 쓰는 애가 있을 텐데, **그 전에 "GPU를 진짜 이 작업에 썼다"를 누가 어떻게 확정하나?** 이 연결고리가 없으면 장부는 그냥 흘려버리는 기록이다.

구체적 공격 시나리오 (코치 + 팀):
1. **개인 작업 위장**: 공급자가 자기 게임/작업을 돌리면서 "GPU 바쁨"만 체크되면 돈 받음. 반대로 사용자가 요청 안 했는데 GPU 돈다고 과금되면 안 됨
2. **부분 학습 사기**: 검증에 쓰일 데이터만 골라 학습해 테스트 통과, 나머지는 미학습 상태로 반환
3. 프로세스 레벨에서 "1번 프로세스가 준 작업"인지 구별은 되겐지만 프로세스명 조작 가능. CPU/명령어 레벨까지 내려가면 상상의 나래 → **POC 영역**

코치 비유 — **원격 검침**
- 블록체인 활용 사례로 자주 나오는 게 원격 검침 (전기/가스 사용량을 사람 없이 기록, 이해관계자가 나중에 조작 못 하게)
- 차이점: 전기/가스는 "**얼마나** 흘렀나"만 재면 되지만, 우리는 "**A 가스인지 B 가스인지**"까지 구별해야 함 → 훨씬 어려움
- 태양광 전기를 한전에 팔 때 "내가 얼마 공급했는지" 신뢰 문제와 같은 구조

**결론**: 이 연결고리는 블록체인 멘토도 해결해 줄 수 없는, 우리가 풀어야 하는 문제. 회사라면 관련 경험자를 헤드헌팅해서라도 데려올 사안.

### 1-3. 기존 서비스와의 차별점 (10:00~22:00)

- 이미 존재: **RunPod**(AWS식 GPU 클라우드, 개인 참여 가능), **G-Cube**(국내 유휴 GPU 공유 플랫폼), Colab 등
- 코치: "기능상 크게 다를 것 같지 않다. **왜 체인에 올라가야 하나? 그 업체들은 체인 없이도 잘 운영한다**" — 소비자 입장에선 사용량이 명확히 보이기 때문
- 팀 답변: 개인이 공급자가 되니까 **신뢰성 문제**가 생긴다 → 이걸 체인으로
- 코치가 인정한 셀링 포인트: 음원 플랫폼 정산 불신 사례처럼, "우리는 투명하게 정산한다, 스마트 컨트랙트라 속일 수 없다"는 문장은 데모/IR에서 먹힘. **단, 1-2 연결고리가 전제**
- 차별점 후보 정리:
  1. 개인 공급자 신뢰성을 체인 정산으로 보장
  2. 사용자가 GPU를 직접 고르지 않고 **AI가 작업에 맞는 GPU 등급을 자동 배치** (비용 효율 판단)
  3. 공급자 많으면 가격 하락하는 시장 사이클 → 클라우드보다 저렴

### 1-4. 시나리오 구체화 요구 (12:40~28:00)

코치가 계속 파고든 것: "사용자가 웹 화면에 딱 들어왔어. **그래서 뭘 하는데?**"

- 팀 예시: **광고용 상품 이미지 대량 생성** (상품 종류별 이미지, GPU 파워 많이 필요)
- 이어지는 질문들:
  - 이미지 그리는 **모델은 누가 제공하나?** 사용자가 올리나 / 플랫폼이 구비하나 / 공급자 노드에 미리 받아놔야 하나 → **미정, 결정 필요**
  - "작업을 맡기는 것"인지 "인프라(IaaS)를 대여하는 것"인지 → 팀: 작업 위탁. 특정 디바이스를 사용자가 지정하지 않고 플랫폼이 등급별 비용 효율 판단해 배치
  - 최소 과금 단위는 물리 디바이스 × 시간
- AI 파트 설명 주의: "규칙 지정해서 학습시킨다"고 하니 코치가 "자체 모델? 파인튜닝?" 추궁 → 실제론 **정교한 프롬프트/LLM 호출** 수준. 표현을 정확히 할 것
- 벤치마킹 성능 지표로 GPU 등급 나누고, 작업 → LLM에 던져 필요 등급 추정하는 방식 언급

**프로젝트 매니징 조언**

- 기능이 명확해야 UI 구성이 나오고, 그래야 프론트와 커뮤니케이션 가능
- 화면: 수요자 화면 / 공급자 화면 / 전체 노드 현황 — 시나리오가 명확해야 각 측면 화면이 나옴

### 1-5. POC 필요 영역 (28:30~35:00)

코치가 짚은 3가지, **병렬로 빨리**:
1. **작업 추적**: 공급자 GPU가 사용자 작업을 실제로 수행 중인지 플랫폼이 확인 가능한가 (1-2의 연결고리)
2. **네트워크**: 공급자–플랫폼–사용자 간 네트워크가 어떻게 이루어지는지, 공급자가 참여하려면 얼마나 복잡한 세팅(설치 등)이 필요한지
3. **블록체인 기본 구축**: 팀에 경험이 없으니 시나리오와 무관하게 누군가 스마트 컨트랙트/체인 구축을 먼저 해볼 것
   - SSAFY에서 **자체 체인 제공 가능성** 언급됨 → 그러면 직접 구축은 안 해도 됨. 토큰 증권 관련 언급도 있었음

**POC 실패 시 두 갈래**
- 주제를 다른 걸로 돌린다
- 연결고리는 약하다고 인정하고, 나머지(체인 정상 동작, AI 추천·래핑, 참여 노드 상태 모니터링, UI)에서 우위를 찾는다 → 이것만으로도 큰 공사

## 2. 팀 회의 — 모델 정의와 진행 방식 (12:39)

### 2-1. 정리된 대화 로그

**[00:00~01:40] AI 스케줄러 vs 사용자 모델 선택**
- 처음 구상은 "AI가 적합한 모델을 추천 + 스케줄링"이었는데, 코치 세션에서 지적받음
- 정리: **작업을 돌린다는 건 이미 쓰고 싶은 모델이 있다는 뜻** → 적합한 모델을 우리가 골라주는 건 말이 안 됨 → **모델은 사용자가 지정**
- 모델이 정해지면 어떤 GPU가 필요한지도 정해진 상태 → 굳이 "자동 분할/자동 배치 AI"까지 필요 없음. 모델이 요구하는 VRAM·성능 조건만 넘기면 됨
- 모델 선택 시 사실상 크기(VRAM)만 봐왔다는 경험 공유

**[01:45~05:30] "모델"이 뭔지 정의가 애매하다**
- 허깅페이스에서 내려받는 사전학습 모델인지, 우리가 CNN/RNN 직접 쌓은 모델인지 → 사용자는 둘 다 원할 수 있음
- 외부 GPU에 데이터가 오가는 이상 **데이터 보안 문제** 발생 → 6주 MVP에서 파이프라인 보안(TEE 등)은 불가능 → **공개 데이터 / 비민감 데이터만 허용**으로 제한
- "학습시킨다"의 의미 재확인: 학습이 아니라 **GPU를 쓰는 작업 전반**(추론 포함). 결과물은 학습된 모델 파일이 아니라 **작업 결과**
- 작업 종류(객체 인식, 이미지 생성 등)에 따라 결과 형태가 다 다름 → 무슨 작업을 지원할지 명확히 해야 함 → "그게 시나리오"

**[05:30~10:15] POC와 진행 방식**
- POC 뜻 질문 → 답: "**진짜 죽어도 안 되는 것**을 소거하는 작업". 레퍼런스가 있어 우리 실력으로 될 것 / 원리적으로 불가능한 것 구분
- 코치 조언 해석 논쟁: "시나리오 작성과 POC를 **병렬**로" = 다 같이 시나리오 짜면서 각자 POC 파트 맡기
- 반론: **기능이 구체화되지 않으면 시나리오가 안 나옴** → 기능부터 정하자
- 합의: **기능 먼저 → 유저플로우**. 진행 중 POC가 필요한 지점이 나오면 그 부분만 POC로 넘기고 나머지 상세화는 계속. 역할 분담은 기능 정한 뒤 유저플로우 시작 전에
- 점심 후 10~20분 회의로 POC 팀 / 시나리오 팀 나누기 제안

**[11:15~12:00] 마무리**
- 도메인 지식 있는 사람이 해줘야 할 일을 우리가 하는 상황 인정. SSAFY 입장에선 "된다/안 된다 + 시연용 완성"이면 충분
- 한 팀원 의견: **네트워크는 새로 만들 게 없고, 작업 추적 POC가 제일 중요**

### 2-2. 요약
- **모델은 사용자가 지정**, 플랫폼은 모델 요구사항(VRAM 등)에 맞는 GPU만 매칭 → AI 자동 배치 기능 축소
- 데이터는 **공개/비민감 데이터로 제한** (보안 구현 불가)
- "작업" = 학습+추론 포함 GPU 작업. 지원 작업 종류 확정 필요
- 진행: **기능 정의 → 유저플로우 → 막히는 곳만 POC 분리**
- 최우선 POC = 작업 추적

## 3. 팀 회의 — 대시보드 (14:20)

### 3-1. 진행 방식 (01:45~02:15)
- 기능부터 정한다
- 아이디어 주축 인원이 설명하고, 나머지는 **모르는 입장에서 명확히 이해될 때까지 질문**하는 방식

### 3-2. 대시보드 논의 (02:45~07:00)

**들어갈 것**
- 가용 GPU 목록
- 작업 등록
- 내 GPU 등록 / 내가 등록한 GPU 사용 현황
- 전체 워크로드 현황 (어느 정도 돌아가고 있는지)

**쟁점 1 — 전체 현황을 사용자가 봐야 하나?**
- "그건 관리자 뷰 아닌가" vs "완성도 있게 보이니 넣자"
- 정리: 사용자는 어떤 GPU가 등록돼 있고 뭐가 동작 중인지 → 사이트 활용량을 읽을 수 있음. 공급자는 내 GPU가 얼마나 동작하는지. 관리자 권한은 없어도 그런 대시보드는 제공

**쟁점 2 — 수요자/공급자 화면 분리?**
- 한 사람이 수요자도 공급자도 될 수 있음 → 로그인 시 역할 분리는 의미 없음
- 로그인은 **개인 지갑** 기반. 지갑 단에서 수요자/공급자 구분 불필요
- **결론: 대시보드 통합**. 항목은 다 적어두고 필요하면 나중에 분리

### 3-3. G-Cube 벤치마킹 (07:45~11:00)

- 공급자/수요자 화면 **합쳐져 있음** → 우리 통합 결정과 일치
- 워크로드 현황(내가 올린 작업 상태), 모니터링, 모델 선택 UI 존재
- 아이폰 웹에서 레이아웃 깨짐 → "우리가 더 잘 만들 수 있다"
- 자기들이 직접 올려보고 검증된 것만 올린다는 운영 방침 확인

## 4. 팀 회의 — 흐름 확정 (15:47)

### 4-1. 정리된 대화 로그

**[00:00~02:30] 모델 = 사전학습 모델**
- 모델 정의 재논의. 허깅페이스 모델(예: Qwen)을 받아서 뭘 할 수 있나 → 이미 만들어진 것으로 추론
- 이전 프로젝트 경험(YOLO): 사전학습 모델을 받아 우리 데이터로 추가 학습 → "우리가 하려는 것도 이거랑 다를 게 없다"
- 도메인 최적화 / 없는 클래스 추가 학습이 사용자가 원하는 것

**[02:30~03:50] 모델 이미지 준비**
- 몇 가지 모델을 **Docker 이미지로 미리 만들어 둠**. 이미지는 Docker Hub 또는 AWS ECR 같은 곳에
- 기존에 만들어진 이미지가 있으면 쓰고, 없으면 우리가 만들어서 제안하는 방식

**[04:30~06:20] 허깅페이스 이해 격차**
- 팀원 간 AI 이해 차이 드러남: "허깅페이스에 프레임워크만 있고 모델은 없는 거냐", "가중치 없는 깡통이냐" 질문 → 이미 어느 정도 학습된 가중치가 있음
- 실제 이런 GPU 공유 서비스 대부분이 모델을 서비스 측에서 올려주지는 않음

**[10:25~15:00] RunPod 구조 분석과 차별점**
- RunPod: 사용자가 원하는 작업·모델·GPU를 **직접 선택하고 입력**해야 함. 워크로드(템플릿) 등록 과정이 매우 복잡
- **우리 차별점: RunPod의 2·3·4단계(컨테이너/템플릿 설정)를 우리가 대신 해준다.** 사용자는 모델 선택만
- 모델 전달 방식: 전체 모델을 주고받기엔 너무 큼 → **LoRA 어댑터**로 학습된 부분만 전달
- 공급자가 GPU 공유하려면 무언가 설치해야 함 → 그 설치 시 모델 이미지를 함께 받게 할지 논의. 노드 GPU 정보를 마켓에 등록해두고, 모델 정보도 같이
- 정리: **모델은 사용자가 정하고, AI는 GPU만 분류**. 필요하면 "이 모델은 어떤 GPU가 좋나" 정도만 LLM에 물어보는 수준

**[15:00~17:30] 1차 목표와 상태 관리**
- 1차: GPU 있는 PC에 작업 던지고 → 결과물 → **결과를 체인에 기록**. 검증까지는 1차에서 안 함
- 학습이면 LoRA 파일을, 추론이면 결과물을 돌려줌
- 작업 상태(진행/예외/중단)가 계속 바뀌므로 **상태 전이를 깔끔하게, 안정성 위주**로. 상태도 체인에 올릴 생각
- 로드맵: 1대1 매칭 → 결과 반환 → 체인 연결까지 완료 → 안정화되면 정산 기능, 검증 등 고도화

**[17:30~19:00] 잡담** (수익성, 사피 서버 등)

**[19:15~22:50] 흐름 재정리 — Docker 이미지 필수**
- **Docker 이미지 패키징 필수**. 사용자가 모델 선택 → 모델에 맞는 GPU 파워를 우리가 매칭
- 결과 전달: 파일 전달밖에 없음. 안 되면 구글 드라이브 / 퍼블릭 레포 등 대안
- RunPod은 컨테이너 설정을 사용자가 하지만 우리는 이미지만 주므로 설정 불필요. 헬스체크로 노드 상태 확인
- 우려: 학습은 한 대에서 통째로 돌려야 하는데, 분산 처리하면 **추론밖에 못 함**. 추론만 하면 사용자마다 원하는 클래스(사과, 토끼…)가 다르므로 사전학습 모델만으로는 의미가 없음 → 학습 지원은 필수

**[26:00~30:00] 학습 방식과 P2P 역할**
- 학습은 **1대1(한 대가 통째로)**. 여러 대가 나눠서 학습은 안 됨 → 그러면 P2P 의미가 약해짐
- P2P 재정의: 학습 결과(LoRA 파일) 주고받기, **분산 추론**(여러 GPU에 나눠 추론)에 사용
- 구조: **사용자 / 워커 / 공급자** 3주체. 사용자가 워커에 작업 전달 → 워커가 적정 GPU 골라 넘김 → 결과물은 공급자가 사용자에게 직접
- 중간에 게시판(레지스트리) 하나 두고 서로 보면서 IP로 직접 통신. **주소를 체인에 올려서** 중앙 제어 없이 매칭
- "원래 이 구조로 이해하고 있었는데" — 팀원 간 구조 이해가 달랐음을 확인

**[33:30~34:30] 유스케이스 예시**
- GPU 없는 노트북 사용자가 이미지 데이터를 밀어주고, 원격 GPU에서 학습 → 결과 모델 파일 받음 → 테스트 돌려서 성능 확인

**[38:00~42:30] 파인튜닝 논쟁과 흐름 재확인**
- "왜 갑자기 사용자가 파인튜닝한다는 얘기가 나오나" → 흐름을 짜다 학습 부분에서 막힘
- 재확인: **학습 = 1대1 매칭, 결과로 LoRA 어댑터 반환**. 사용자가 LoRA + 데이터셋을 주면 **분산 추론으로 평가(성능 지표)**
- 평가 방식(다중 검증)은 미결정

**[43:30~48:00] 마무리**
- 진행 전 다 같이 개념(LoRA, 분산 추론 등) 이해하고 가자 → 10분 휴식 후 개념 공유
- 최종 1차 목표 낭독:
  > 외부 유휴 GPU와 **1대1 매칭**해서 사용자에게 필요한 **학습**을 돌리고, 학습된 **LoRA 어댑터 파일**과 데이터셋을 업로드하면 **다중 검증·분산 처리로 성능 지표**를 뽑아준다. 즉 **학습 + 추론**.

### 4-2. 요약
- **모델**: 허깅페이스 사전학습 모델을 **Docker 이미지로 패키징**해 제공. 사용자는 모델만 선택
- **차별점**: RunPod에서 사용자가 직접 해야 하는 컨테이너·템플릿 설정을 우리가 대신
- **학습**: 1대1 매칭, 한 대에서 통째로. 결과는 **LoRA 어댑터**
- **추론/평가**: LoRA + 데이터셋 업로드 → 여러 GPU에 **분산 추론** → 성능 지표
- **P2P**: 학습 결과 파일 전달 + 분산 추론에 사용. 사용자/워커/공급자 3주체, 주소를 체인에 올려 중앙 제어 없이 매칭
- **체인**: 1차는 결과물·작업 상태 기록. 정산·검증은 안정화 후 고도화
- **데이터**: 공개/비민감만
- 팀원 간 AI·구조 이해 격차 확인 → 개념 공유 세션 필요
