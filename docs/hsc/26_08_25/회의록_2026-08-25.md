## 2. 오전 회의 — 크라우드 펀딩 주제 검토

### 2-1. 기존 안의 문제점
- 원안: 크라우드 펀딩 플랫폼 + 블록체인으로 **① 자금 흐름 투명화 ② 제품 품질 검증(밸리데이팅)**
- 품질 검증(밸리데이터)은 실물 상품에 대해 P2P 다중 검증이 불가능 → 전수검사도 비현실적 → **밸리데이팅은 제외, 중계·정산만 하자**는 쪽으로 정리
- "블록체인이 왜 먹튀를 막나?" 에 대한 답이 약함
  - 거래 내역 공개는 되지만 먹튀 자체를 막지는 못함
  - 배송 완료 전 지급 보류(에스크로)는 블록체인 없이도 가능
- 와디즈 등 기존 플랫폼이 이미 있고, 사이트 하나 만든다고 유저·판매자가 오는 구조가 아님
- 원가·단가 공개 아이디어는 판매자가 꺼려서 현실성 낮음

### 2-2. 검토된 파생 아이디어 (대부분 기각)
- 전자지갑/코인 결제 → "그럼 크라우드 펀딩일 이유가 없고 그냥 쇼핑몰" (기각)
- 리뷰·거래내역 위변조 방지(네이버 리뷰 조작 등) → 컨설턴트 의견: "리뷰가 체인에 올릴 만큼 가치가 있나" (기각)
- 후원 권리 양도(내가 펀딩한 걸 재판매), 크라우드 상장 → 논의만
- 증명서 발급·공증 플랫폼(성적/졸업증명서 수수료 문제) → 잡담 수준
- 더치트 블록체인 버전 / 사기 번호 공개 → 법적 문제 (기각)
- 중고차 이력·보험 → 이미 다른 팀이 함 (기각)
- 폴리마켓(예측시장) → 국내 불법 (기각)

### 2-3. 대안 부상: GPU 분산 연산 (P2P)
- 개인이 보유한 **유휴 GPU를 P2P로 연결 → 작업 배분 → 결과 수신 → 스마트 컨트랙트로 정산**
- 블록체인 당위성: 사용 리소스량·작업 완료 여부의 위변조 방지, 개인 간 정산 신뢰
- 구성 요소: ① GPU 리소스 분산 네트워크 ② 작업 분배/평가 로직 ③ 스마트 컨트랙트(정산)
- 우려: 실제로 되는지, GPU 제공자에게 줄 보상이 메리트가 있는지, 사용자 입장 가격 경쟁력
- 결정: **가격/상품 경쟁력은 논외로 하고 "구현 가능성 + 당위성"만 보자**

### 2-4. 게임 안
- 팀원 상당수가 게임(2D 픽셀 멀티플레이, 아이템 P2P 거래) 선호
- 반론: 게임은 개연성·당위성이 없고, 블록체인 팀이 게임 만드는 건 "배보다 배꼽"
- 팀장 직권으로 "게임 금지"가 반복적으로 언급됨 (반농담)

### 2-5. 오전 액션
- 구현 가능성 조사 담당 지정 (팀장 외 1명 자원)
- 크라우드 펀딩을 살릴 방법 추가 조사 (담당 미확정)
- 게임 쪽 아이디어 조사 2명 (옆자리 페어)

## 3. 오후 회의 — GPU 주제 심화

### 3-1. 주제 후보 재정리
- 후보: ① GPU 분산 연산 ② 크라우드 펀딩 ③ 블록체인 게임 ④ AI 에이전트
- "블록체인 P2P는 자소서에 쓸만한 유일한 도메인인데 우리 팀만 골랐다" / 다른 도메인 희망 질문에 답 없음 → 도메인 변경 없이 진행
- 투표/사다리로 정하자는 의견 있었으나, **GPU로 우선 진행**하고 GPU 외 대체 주제 하나를 같이 정해두기로

### 3-2. GPU 매칭 구조 논의 (핵심)
- 흐름: 사용자가 작업(코드/파일) 업로드 → 체인에 올라온 참여자 GPU 스펙 인지 → 적절한 GPU에 배분 → 결과 취합 → 정산
- **"작업에 알맞은 GPU를 AI가 선정한다"** 부분에 이견
  - 회의적 입장: 모델마다 레이어·하이퍼파라미터가 달라 필요 연산량 판단이 매우 어렵다, 자체가 논문급
  - 대안: 사용자가 직접 GPU/모델 선택 → 그러면 관리 서버 필요
  - LLM 조회 결과: 코드 점수화(예: 100점 만점 60점) 후 미리 등급화한 GPU에 매칭하는 방식은 100줄 내외로 구현 가능
- 1:1 매칭이면 분산 처리가 없어 P2P 의미가 없음 → **여러 독립 작업을 여러 참여자에게 분산**하는 구조여야 함
- 중앙 매칭 서버 문제: 서버가 죽으면 전체 중단 → 중앙 서버 없이 참여 노드들이 "나 할 수 있음"을 알리고 요청자가 고르는(경매/입찰식) 구조가 P2P에 맞음
- 대규모 AI 학습은 불가능. **타깃 작업은 이미지 생성·영상 프레임 추출·이미지 분류 등 단순 병렬 작업**으로 한정
  - 반론: "그 정도는 GPU 없어도 되지 않나" → 양(만 장~십만 장)이 많으면 의미 있음
- 하이브리드(중앙 서버 + P2P) 언급, 결론 미정
- GPU 중간 이탈 시 스마트 컨트랙트에서 정산 처리 필요 (이슈로 기록)

### 3-3. 인프라·비교
- 서버 신청 여부: "노트북만 준다"는 정보 → 별도 서버 불필요 판단
- 보상 참고치: GPU 제공자 전기료가 시간당 40~60원 수준이라는 언급(정확한 수익 구조는 미정)
- "AWS보다 싸다"는 자료 있으나 팀 내 회의적

### 3-4. 역할 (잠정)
- 구현/매칭 로직 조사: 팀장 + 자원자 1명
- 매칭 알고리즘 구상: 1명 ("아까 말한 매칭 생각하고 있을게요")
- 프론트: 사용자 입력 UI 위주, 심플 웹 (블록체인 잘 모르는 2명이 담당 예정)
- 기획/요구사항 → Jira 작성 (에픽-스프린트 구조, 저번 프로젝트 양식 재사용)
- 팀 내 우려: 팀 6명 중 블록체인·P2P를 이해하는 사람이 소수 → 알고리즘 설명 자료 필요

### 3-5. 대체 주제
- 게임(스컬/메이플 류 2D, 유저 제작 컨텍츠) — 여전히 팀원 선호 높음, GPU 실패 시 후보
- AI 에이전트(MCP 등) — 학습량 과다로 부담

## 4. 결정 사항
1. 크라우드 펀딩 원안은 **당위성 부족**으로 보류. 밸리데이팅 기능은 폐기.
2. **P2P 유휴 GPU 분산 연산 + 스마트 컨트랙트 정산**을 1순위로 조사·진행.
3. 주제 평가는 **구현 가능성 / 블록체인 당위성** 두 기준만 사용.
4. **Plan B(예제 코드 기반 최소 구현)** 를 병행 준비.
5. GPU 외 대체 주제 1개를 함께 정해둠(게임 유력).
