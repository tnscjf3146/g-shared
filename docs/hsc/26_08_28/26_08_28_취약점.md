# 유휴 GPU 공유 서비스의 한계와 위험성

> 2026-08-28 정리. Gemini 대화(https://gemini.google.com/app/ca74aaf28b5cb7f3) + Claude 후속 논의 종합.

## TL;DR
- P2P GPU 공유의 보안 사고는 이론이 아니다. Vast.ai·Salad·io.net 등 실제 플랫폼에서 컨테이너 탈출, 가정망 침투, 180만 건 시빌 공격이 발생했다.
- 모든 사고의 공통 전제는 "Docker 격리면 충분하다"였고, 전부 깨졌다. 방어의 본체는 마이크로VM + 런타임 감시이며 AI 검열은 보조 수단이다.
- 블록체인은 "플랫폼도 못 바꾸는 증거"를 위해 **코드 해시만 퍼블릭 L2에 앵커링**하는 범위에서 쓴다. 지금은 기능 구현이 우선이고, 아래 위험은 숙지한 상태로 확장 가능한 구조를 잡는 것이 목표다.

## 1. 주요 사고 및 위험 사례

### 1-1. 컨테이너 탈출 및 호스트 권한 장악 (임차인 → 호스트)
임차인이 제출한 코드가 Docker 등 OS 레벨 격리를 뚫고 호스트 PC를 장악. **실제 P2P GPU 플랫폼에서 반복적으로 발생한 위협.**

| 공격 경로 | 실제 사례 | 의미 |
|---|---|---|
| **하드웨어 취약점** | [GPUThor](#a1) (2026.08) — Rowhammer로 ECC 우회 → 비특권 GPU 프로그램이 호스트 루트 셸 (1.1분) | 소프트웨어 격리를 아무리 강화해도 GPU 메모리 자체가 공격면 |
| **컨테이너 런타임 취약점** | [NVIDIAScape](#a2) CVE-2025-23266 — Dockerfile 3줄로 탈출 → 호스트 루트. CVSS 9.0 | **Docker + NVIDIA Toolkit 조합 전체**가 한 번에 노출. 패치 지연된 개인 호스트가 가장 위험 |
| **플랫폼 CLI/에이전트 결함** | [Vast.ai 심링크](#a3) (2025) — 플랫폼 CLI가 루트로 심링크를 따라가 호스트 전체 파일 열람 | 컨테이너가 아닌 **플랫폼 도구**가 구멍. "임차인은 격리됨"이라는 공식 주장이 깨짐 |
| **호스트 내부망 노출** | [Salad 1.6.0](#a4) (2024) — 임차인 컨테이너가 호스트 가정 LAN의 IoT·XP·라우터 스캔 | 피해가 PC 한 대가 아니라 **가정 전체**로 확산 |
| **인증/권한 우회** | [Akash](#a5) (2024) — 소유자 사칭으로 임의 인스턴스 명령 실행 | 탈중앙 마켓의 컨트롤 플레인 자체도 공격면 |

- 피해 범위: 자격증명 유출, 랜섬웨어, 봇넷 경유지, 가정 내 IoT 침투 → **예치금 보상으로 복구 불가능한 피해.**
- 공통점: 다섯 사례 모두 "Docker 격리만으로 충분하다"는 전제에서 출발했다가 깨졌다.

### 1-2. 데이터 유출 · 자원 탈취 (호스트 → 임차인)
| 위협 | 실제 사례 | 의미 |
|---|---|---|
| **GPU 메모리 잔여 데이터 유출** | [LeftoverLocals](#b2) CVE-2023-4969 — 같은 GPU의 다른 프로세스가 미초기화 메모리를 덤프해 LLM 프롬프트·가중치 복원. 쿼리당 181MB | 악의적 호스트뿐 아니라 **직전 임차인**도 위협. 세션 간 VRAM 제로화 필수 |
| **호스트에 의한 VRAM/RAM 덤프** | (구조적 — 호스트가 물리 장비를 통제하므로 원리상 항상 가능) | 소비자용 GPU에는 TEE가 없어 **근본 해법 없음** → 기밀 워크로드는 타깃에서 제외 |
| **은닉 채굴로 연산력 탈취** | [Vast.ai 템플릿](#b1) (2024) — 렌탈 템플릿에 채굴 코드 은닉, 임차인 GPU가 XEL 채굴에 쓰임 | 임차인은 "느린 학습"으로만 체감. **템플릿/이미지 무결성 검증** 필요 |

### 1-3. 하드웨어 혹사 및 발열
- RTX 3060 등 소비자용 카드는 24시간 100% 부하 설계가 아님. 채굴·극단 연산 시 열 응력으로 수명 급감.
- 직접 사고 보도는 없으나, 위 [Vast.ai 은닉 채굴](#b1) 사례처럼 **호스트도 모르는 채굴**이 돌 수 있음 → 온도·전력 상한을 플랫폼 에이전트가 강제해야 함.

### 1-4. 플랫폼 구조 공격 (시빌 · 호스트 자원 오용)
| 위협 | 실제 사례 | 의미 |
|---|---|---|
| **시빌 공격 / 보상 파밍** | [io.net](#c1) (2024.04) — 공용 인증 토큰 유출로 **약 180만 개 가짜 GPU**가 보상 파밍. 활성 GPU 60만 → 1만 | 보상·토큰 모델이 있으면 **반드시 표적이 됨**. 하드웨어 실존 증명과 계정별 인증이 초기부터 필요 |
| **호스트 자원의 무단 재판매** | [Salad 대역폭](#c2) (2025.10) — 호스트 IP를 VPN 출구 노드로 재판매. 로그인 3만 회 실패 통지, ISP 경고, 법적 통지, 집단소송 | **플랫폼 자체가 가해자**가 될 수 있음. "보상금 < 피해액"의 실례 |

### 위협 요약
```
임차인 → 호스트 : 컨테이너 탈출(HW/런타임/CLI), 내부망 침투, 하드웨어 혹사
호스트 → 임차인 : VRAM 덤프, 잔여 메모리 유출, 은닉 채굴
제3자 → 플랫폼  : 시빌/보상 파밍, 컨트롤 플레인 권한 우회
플랫폼 → 호스트 : 자원 무단 재판매, 법적 책임 전가
```

## 2. 서비스가 널리 활성화되지 않는 본질적 이유

| 이유 | 내용 |
|---|---|
| **초고속 인터커넥트 부재** | 대규모 학습은 수백~수천 GPU를 NVLink / InfiniBand로 직결해야 함. 인터넷 기반 P2P는 지연·병목 때문에 대규모 학습 자체가 불가능. |
| **기업 보안·컴플라이언스 미달** | 보안 인증 없는 개인 PC에 기밀 데이터 전송 불가. ISO 27001, 개인정보보호 규정 위배. |
| **가동률(SLA) 보장 불가** | 중앙 클라우드 99.9%+ vs P2P는 호스트 PC 종료·정전·인터넷 단절에 무방비. 수일짜리 작업이 한 번에 소실될 수 있음. |

→ 현재 시장은 **개인 개발자·학생의 단발성 렌더링, 소규모 모델 테스트** 용도에 머무름. 남는 시장은 단일 GPU 워크로드(추론·파인튠·렌더링).

## 3. 기술적 방어 수단과 한계

### 호스트 보호
| 수단 | 내용 | 대응 사례 |
|---|---|---|
| **마이크로VM 격리** (Kata, Firecracker) | 커널 공유 Docker 대신 독립 하드웨어 가상화. **방어의 본체** | NVIDIAScape, Vast.ai 심링크 |
| Rootless Docker + AppArmor/SELinux/Seccomp | 탈출 성공 시에도 관리자 권한 차단, 악성 syscall 제한 | — |
| **eBPF 런타임 감시** (Falco) | 실행 시점의 비정상 syscall·네트워크 연결 실시간 탐지 | 동적 로딩 |
| **네트워크 egress 격리** | 사설 IP 대역(10/8, 192.168/16, 172.16/12)·호스트 LAN 아웃바운드 차단. 채굴 풀 포트/도메인 차단 | Salad 내부망 |
| **런타임·드라이버 패치 강제** | 호스트 에이전트가 Container Toolkit·드라이버 버전 검사, 취약 버전은 매칭 제외 | NVIDIAScape |
| **플랫폼 도구 최소 권한** | CLI/에이전트가 루트로 심링크를 따라가지 않도록 (`O_NOFOLLOW`, 저권한 사용자) | Vast.ai 심링크 |
| 온도·전력 상한 | 에이전트가 강제. 초과 시 작업 중단 | 하드웨어 혹사 |
| 하드웨어 분할 (vGPU/MIG) | VRAM·컴퓨팅 유닛 물리 격리 — **소비자용 GPU 미지원** | — |

### 임차인 보호
| 수단 | 내용 | 대응 사례 |
|---|---|---|
| **세션 간 VRAM 제로화** | 임차 종료 시 GPU 메모리 전체 덮어쓰기. 소비자용에서 가능한 유일한 메모리 유출 완화책 | LeftoverLocals |
| **템플릿/이미지 무결성** | 플랫폼 이미지 해시 서명, 임차인이 검증 후 실행. 예상 외 아웃바운드(채굴 풀) 탐지 시 알림 | Vast.ai 은닉 채굴 |
| **하드웨어 실존 증명** | 호스트 등록 시 GPU attestation(연산 챌린지, 디바이스 ID 서명) + 계정별 개별 토큰. 공용 토큰 금지 | io.net |
| 기밀 컴퓨팅 (TEE) | H100 등 데이터센터 GPU만 지원 | — |
| 동형 암호 | 수백 배 느려 실용성 없음 | — |
| 연합 학습 | 원본 데이터 미전송 — 적용 범위 제한적 | — |

→ 소비자용 GPU에서 임차인 데이터를 하드웨어로 보호할 방법은 없다. **"기업 기밀 데이터는 타깃 고객이 아니다"라고 명시하는 것이 정직한 포지셔닝.**

## 4. AI 기반 사전 검열의 실효성

### 기대 효과
- 알려진 패턴(Stratum 채굴 프로토콜, 랜섬웨어, 단순 탈출 스크립트) 즉각 차단.
- 난독화 코드의 의도(Semantics) 추론.
- 저수준·스크립트 키디형 공격의 대부분을 저비용으로 자동 필터링.

### 치명적 한계
- **동적 로딩**: 정상처럼 보이는 스크립트가 실행 후 외부에서 암호화 바이너리를 받아 메모리에 로드 → 정적 스캔으로 탐지 불가.
- **바이너리 검사 불가**: 수 GB Docker 이미지, 컴파일된 CUDA 확장(.so) 내부 분석은 현재 기술로 불가능에 가까움.
- **오탐(False Positive)**: VRAM 직접 제어, 분산 통신 등 정상 최적화 코드를 의심 → 정당 사용자 이탈.
- **적대적 회피**: 공격자도 LLM으로 우회 코드 생성 → 끝없는 군비 경쟁.
- **비대칭성**: 한 번만 뚫려도 호스트는 치명타.

→ **AI 정적 검사는 보조 수단.** 마이크로VM + eBPF 런타임 감시를 겹친 다계층 방어(Defense-in-Depth)가 필수.

## 5. 블록체인 + 경제적 유인 모델

### 핵심 아이디어
1. **코드 영구 기록**: 제출 코드를 블록체인/IPFS에 기록 → 사후 검증 객관성 확보, 고의 무고(False Reporting)와 AI 오탐 방지.
2. **플랫폼 책임 분담**: 중개 수수료 일부로 **보상 풀(Insurance Pool)** 조성 → 보상금 < 피해액 비대칭성 보완. 수수료를 받는 명분.
3. **AI 지속 강화**: 악성 판정된 코드를 AI가 재학습.
4. **스테이킹 / 슬래싱 / 평판**: 임차인 예치금 → 악성 입증 시 몰수·피해자 보상, 블랙리스트 등재.

### 허점
- **무고·오탐**: 정상 임차인이 호스트 거짓 신고나 AI 오탐으로 슬래싱될 위험. 판정 주체의 공정성 문제 → [6장 미해결 과제](#판정-공정성--미해결-과제와-최소-대응)에서 다룸.
- **시빌 공격 / 꼬리 자르기**: 일회용 지갑 수천 개로 소액 예치 후 공격, 정지되면 새 지갑으로 재시도. [io.net에서 실제 발생](#c1).

### 시빌 공격 방어
- **시빌 공격**: 한 공격자가 지갑을 수천 개 만들어 소액 예치 후 공격, 정지되면 새 지갑으로 반복(꼬리 자르기). 지갑 생성 비용이 0이라 블록체인 환경에서 특히 치명적.
- 방어의 본질: **"계정 하나를 버리는 비용" > "공격 한 번의 이득"** 이 되도록 만드는 것. 완전 차단이 아니라 경제적으로 손해나게 하는 것이 목표.

| 방법 | 내용 | 트레이드오프 | 완화안 |
|---|---|---|---|
| **차등 스테이킹** | 신규 지갑은 GPU 가격에 준하는 예치금(100%), 정상 거래 쌓일수록 단계적 완화(→50→20→5%) | 신규 정상 사용자도 장벽. 200만 원 예치면 AWS가 나음 | 저사양·단기 거래 온보딩 티어, 보상 풀 연계 보증 보험 |
| **SBT / DID** | KYC·GitHub 증명을 거친 사용자에게 양도 불가 신분 토큰. 블랙리스트 시 연결된 신원 전체 퇴출 | P2P 익명성과 상충, 신원 보관 부담 | 제3자 DID 발급자가 신원 보관, 플랫폼은 "검증됨"만 확인. 임차인 필수 / 호스트 선택 |
| **샌드박스 Dry Run** | 호스트 전달 전 플랫폼 격리 노드에서 1~2분 실행. 채굴 풀 연결·탈출 시도 적발 시 즉시 슬래싱 | 타이머로 검증 시간 이후 발동하면 우회. 노드 운영 비용 | 실행 시간 랜덤화, 호스트 측 Falco와 이중 적용 |
| **기기·네트워크 지문** | IP 대역·환경 지문·코드 제출 패턴으로 동일인 클러스터 식별, 지갑 바꿔도 차단 | VPN·공용 IP 오탐, 개인정보 수집 | 즉시 차단 대신 예치금 상향·검증 강화 트리거로만 사용 |

- 어느 하나도 단독으로는 뚫리지만 **네 겹을 통과하는 비용이 공격 이득을 넘으면 시빌 공격은 경제적으로 소멸**함.
- 전제는 마이크로VM 격리. 격리가 없으면 한 번의 성공이 호스트 전체를 잃는 비대칭성이 그대로 남음.
- APT급 공격자는 완전히 막지 못함 → 남은 위험은 **플랫폼 보상 풀**로 흡수.

## 6. 블록체인 설계 결론

### 왜 블록체인인가 — 동기 재정의
- 단순 P2P 거래 기록이 아니라 **"플랫폼(중앙 서버) 자체를 신뢰할 수 없다"**는 것이 핵심 동기.
- 즉 "우리 서비스가 책임을 피하려고 코드를 바꿔치기하면?"이라는 질문에 답해야 함.

### 원문이 아닌 해시를 올린다
- 목적(사후 판정 + AI 학습용 원문 확보 + 조작 불가)은 **체인에 해시, 원문은 IPFS**로 동일하게 달성됨.
- IPFS는 내용 = 주소(CID). 한 글자만 바꿔도 체인의 해시와 불일치 → 플랫폼도 바꿔치기 불가.
- 원문을 체인에 넣으면: 비용(GB 단위 코드 저장 비현실적), 기밀성(퍼블릭 체인 전체 공개), 불변성 역효과(악성 코드가 영구 배포 채널이 됨).

**추천 구조**
```
임차인 코드 → 암호화 → IPFS 업로드 → CID
체인 기록: { 거래ID, CID, 제출시각, 임차인 주소 }
```
- 평상시: 암호화 상태로 보존.
- 분쟁 시: 사전 합의 조건(신고 + 예치금)으로 복호화 키 공개 → 판정 → 슬래싱.
- AI 학습: **악성 판정된 코드만** 복호화해 학습셋에 추가. 정상 코드는 기밀 유지.

### AI 지속 강화 — 판정 결과를 학습 데이터로 환류
- 체인에 기록된 코드는 단순 증거가 아니라 **AI 필터의 학습 데이터셋**이 됨. 사고 한 건이 다음 방어선을 강화하는 선순환 구조.
- 흐름:
  ```
  악성 판정 확정 → IPFS 원문 복호화 → 라벨링(악성/패턴 유형)
  → AI 필터 재학습 → 신규 제출 코드에 즉시 적용
  ```
- 체인이 보증하는 것: 학습 데이터의 **출처와 무결성**. "이 코드가 실제로 거래에 제출되어 악성 판정을 받았다"는 사실이 위조되지 않았음을 누구나 검증 가능 → 학습셋 오염(Data Poisoning) 방지.
- 정상 판정 코드는 복호화하지 않으므로 학습셋에 들어가지 않음. 임차인 기밀 보장과 양립.
- 한계: 정적 코드 학습이므로 동적 로딩·바이너리 우회는 여전히 잡지 못함. 런타임 감시(Falco) 로그도 함께 라벨링해 학습해야 실효성이 커짐.

### 어디에 기록하나 — 퍼블릭 L2
- 신뢰는 "체인이냐 DB냐"가 아니라 **"누가 장부를 쓰느냐"**에서 나옴. 플랫폼 외부의 독립된 노드가 보증해야 "우리는 못 바꿉니다"가 주장이 아닌 증명이 됨.
- 거래별 해시 또는 하루치 머클루트를 Polygon/Base 등 퍼블릭 L2에 기록. 건당 수 원 수준.
- 스마트 컨트랙트 함수 하나(`record(tradeId, hash)`)로 구현 가능, 노드 운영 부담 없음, 기밀성·비용·검증 가능성 모두 충족.

### 판정 공정성 — 미해결 과제와 최소 대응
- 해시 앵커링은 **"무엇이 제출됐는가"**를 증명하지만 **"그것이 악성인가"**는 증명하지 못함.
- 슬래싱 판정 주체가 플랫폼(또는 플랫폼 AI)이면 신뢰의 뿌리는 여전히 중앙에 있음. **이 부분이 설계의 진짜 핵심.**

**최소 대응 (지금 설계에 넣을 수 있는 것)**
| 단계 | 내용 | 효과 |
|---|---|---|
| ① 선보상 | 신고 접수 즉시 호스트에게 플랫폼 보상 풀에서 선지급. 임차인 예치금은 **동결만** 하고 몰수하지 않음 | 호스트는 즉시 구제, 임차인은 아직 손실 없음 |
| ② 이의제기 기간 | 72시간 동안 임차인이 반론 제출 가능. 판정 근거(AI 판정 로그, Falco 로그, 코드 해시)를 임차인에게 공개 | 오탐·무고 시 임차인이 방어할 기회 |
| ③ 판정 근거 앵커링 | 판정 결과와 근거 로그의 해시도 체인에 기록 | 플랫폼이 나중에 판정 사유를 바꿀 수 없음 |
| ④ 확정 후 정산 | 이의 없거나 기각 시 예치금 → 보상 풀 환입. 이의 인정 시 예치금 반환 + 허위 신고 호스트 평판 하향 | 양방향 억제력 |

**장기 후보**: 다수 검증 노드의 코드 재실행 합의, 제3자 감사 기관, 분쟁 전문 커뮤니티 배심(스테이킹 기반). 프로젝트 범위 밖이지만 ③ 덕분에 나중에 붙일 수 있음.

## 7. 개인적인 견해

- **기능 구현이 먼저다.** 위에 정리한 보안 문제를 전부 해결한 뒤에 만들기 시작하면 프로젝트 기간 안에 아무것도 나오지 않는다. 우선 GPU 매칭·거래·실행이 동작하는 핵심 흐름을 완성하는 것이 순서다.
- **그럼에도 불구하고 숙지하고 이해하고 있어야 할 문제다.** 이 문서의 사고 사례들은 실제 P2P GPU 플랫폼이 "격리는 충분하다"고 믿고 서비스하다가 깨진 기록이다. 구현 단계에서 어떤 결정(Docker vs 마이크로VM, egress 정책, 템플릿 서명, 인증 토큰 구조)이 나중에 어떤 취약점으로 이어지는지 알고 있어야, 지금은 못 막아도 **나중에 막을 수 있는 구조**로 만들 수 있다.
- 정리하면: 지금 구현할 것과 알고만 있을 것을 구분한다. 알고만 있는 것은 이 문서에 남겨두고, 발표 때 "우리는 이 위험을 알고 있고 이렇게 확장할 계획이다"라고 말할 수 있으면 충분하다.

### 시사점
- **"Docker 격리만으로 충분하다"는 전제는 이미 여러 번 깨졌다** (A2, A3, A4). 마이크로VM 격리가 선택이 아닌 필수라는 근거.
- 임차인 데이터 유출은 이론이 아니다 (B2). 소비자용 GPU에서는 하드웨어 해법이 없으므로 **타깃 워크로드를 기밀성 낮은 것으로 한정**해야 함.
- 시빌 공격은 실제로 발생했고 규모가 크다 (C1, 180만). 차등 스테이킹·계정별 인증이 필요한 근거.
- 호스트 피해는 금전 보상으로 회복 불가한 형태(법적 통지, 가정망 침투)로 나타난다 (A4, C2) → 플랫폼 보상 풀 + 사전 차단 병행이 필요.
