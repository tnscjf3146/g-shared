# P2P GPU 공유 서비스 플로우 정리

> 2026-08-28. 팀 다이어그램 기준 정리. 관련: [26_08_28_취약점.md](./26_08_28_취약점.md)

## 1. 메인 흐름 (사용자 → 결과)

```
사용자
  │
  ▼
[웹 화면]  대시보드 · 가용 GPU 조회 · GPU 등록 · 로그인 · 워크로드 현황 · 토큰 충전
  │
  ▼
[워크로드 등록]  템플릿(Docker image) + 학습 데이터 (P2P 전송)
  │        ▲
  │        │  ← [AI Scheduler]  GPU 벤치마크 성능 + 비용 효율성 기반 GPU 선택 (XGBoost?)
  │
  ▼
[GPU 저장소]  등록된 GPU 노드 중 적정 노드 매칭
  │
  ▼
[GPU Worker]  (공급자 측 에이전트)
  ├ GPU 상태 모니터링
  ├ 작업 수신 (P2P)
  ├ Docker 컨테이너 실행/관리
  └ 작업 상태 보고
  │
  ▼
[공급자 PC]  Docker Image 기반 실행 환경에서 AI 학습/추론 → 결과 생성 (P2P)
  │
  ▼
[작업 결과]  → 사용자에게 반환
```

- **[워크로드 현황]** — 워크로드 등록 후 진행 상태를 보여주는 화면. 결과로 연결됨. *(미완)*

## 2. 블록체인 계층 (메인 흐름과 병행)

| 컴포넌트 | 역할 |
|---|---|
| **평점/신뢰도** | GPU 제공자의 평점·신뢰도 기록 |
| **작업/결과 기록** | 작업 요청과 결과를 체인에 기록 |
| **결제/정산** | 토큰 기반 결제, 작업 완료 시 스마트 컨트랙트로 자동 정산 |
| **스마트 컨트랙트** | 정산 규칙 정의, 분쟁 해결 |

## 3. 역할별 정리

| 역할 | 하는 일 |
|---|---|
| **사용자(임차인)** | 로그인 → 토큰 충전 → 워크로드 등록(이미지 + 데이터) → 현황 확인 → 결과 수령 |
| **공급자(호스트)** | GPU 등록 → Worker 에이전트 실행 → 작업 수신·실행 → 결과 반환 → 토큰 정산·평점 획득 |
| **플랫폼** | 웹, AI Scheduler(GPU 선택), GPU 저장소(매칭), 블록체인 기록·정산 |

## 4. 데이터 흐름 특징

- **P2P 구간**: 학습 데이터 전송, 작업 수신, 결과 반환 → **큰 데이터는 플랫폼 서버를 거치지 않고 사용자 ↔ 공급자 직접 전송**. 플랫폼은 매칭·기록·정산만.
- **블록체인**에는 작업 요청/결과·평점·정산만 기록. 코드·데이터 원문은 올리지 않음 (취약점 문서의 "해시만 앵커링" 결론과 일치).

## 5. 미확정 사항

| # | 항목 | 내용 | 시점 |
|---|---|---|---|
| 1 | **AI Scheduler 타깃** | XGBoost가 예측할 값이 미정 — 예상 실행 시간? 완료 성공률? 가격 대비 성능 점수? 이게 정해져야 학습 데이터 구조가 나옴 | 구현 전 |
| 2 | **워크로드 현황** | Worker의 "작업 상태"가 어디로 보고되어 현황 화면에 뜨는지 연결 없음 | 진행 중 |
| 3 | **블록체인 ↔ 메인 흐름 연결점** | 하단 4개 박스가 위 흐름의 어느 단계에서 호출되는지 없음. 예상: 워크로드 등록 → 작업 기록 / 작업 결과 → 결과 기록 + 정산 + 평점 / 분쟁 → 스마트 컨트랙트 | 구현 전 |
| 4 | **결과 검증** | 공급자가 보낸 결과가 제대로 실행된 것인지 확인 주체 없음. 없으면 정산이 "결과 파일 도착 = 완료"로 동작 | 구현 전 |
| 5 | **토큰 충전 방식** | 원화 → 토큰? 자체 토큰? 스테이블코인? 법적 검토(전자금융·가상자산)와 연결 | 진행 중 |
